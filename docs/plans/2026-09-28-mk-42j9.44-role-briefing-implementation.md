# Role briefing: implementation notes (mk-42j9.44)

Implements the three items `docs/plans/2026-09-28-mk-42j9.38-role-briefing-template.md` §7 left open. The design itself (sections, provenance rule, §4 acceptance gate, §5 open-decisions criteria) is closed and unchanged here.

## 1. Assembler location — layered, not either/or

Built `scripts/assemble-briefing.py` as the deterministic core (no model in the loop), plus `commands/brief.md` as the doc-recommended primary/interactive entry point — a thin wrapper that calls the script for sections 1/2/3a/4/5/6/7 and adds the one doc-sanctioned model-in-loop step, a scoped `/recall`-style fan-out for §3.3b ranked context.

**Why layered rather than picking one:** the doc's own recommendation (`commands/brief.md`) is right for the interactive case, but rotation and lane-spawn are non-interactive callers — a slash command has no meaning to a bash script calling `dispatch.sh`. A bare script has no natural home for the model-in-loop §3.3b step. Splitting the deterministic core out lets both callers share it: `commands/brief.md` for a human or an agent turn, `scripts/assemble-briefing.py` directly for rotation/lane-spawn. This is a strict refinement of the doc's recommendation, not a deviation from it — §3.3b was always meant to be interactive-only per the doc's own framing of it as an advisory ranking step.

## 2. Rotation / lane-spawn wiring

### 2b. Lane-spawn — implemented

`scripts/dispatch.sh` gained `--brief-bead <ID>` (+ `--brief-bd-cwd <DIR>` for when the tracker holding the bead isn't the dispatched repo). When set, dispatch.sh runs `assemble-briefing.py` and prepends its rendered output to the prompt, the same way `--inject-docs` prepends CLAUDE.md/AGENTS.md. A failing §4 gate is reported to stderr and the briefing is prepended anyway — a lane that starts with a briefing saying "NEXT: UNKNOWN, this bead has no live directive" is better informed than one with no briefing at all; withholding it would hide real information.

### 2a. Rotation successor — Clavain-side contract only (Quilan implementation is out of scope here)

mk-42j9.25 F4 ("rotation successors carry forward the source's live model + effort") is Quilan-owned and still unlanded — there is no rotation-successor spawn code to wire the briefing into yet. What Clavain can provide now, and does, is the callable contract a rotation spawner will need:

- **Interface**: `python3 scripts/assemble-briefing.py --bead <ID> --repo <REPO> [--bd-cwd <DIR>] [--role <ROLE>] --out <FILE>`. Exit 0 = §4 gate passed, exit 2 = gate failed (problems on stderr, file still written). This mirrors `route-spawn.sh`'s existing `--seat-out <file>` convention (resolve once, write a receipt file, let the caller decide what to do with a failure) rather than inventing a new pattern.
- **Content contract**: the file at `--out` is the complete markdown briefing (sections 1–7, §3b left as a placeholder — a rotation successor is non-interactive, so it gets the deterministic core only, same as lane-spawn). A rotation successor should treat it as *opening material to prepend*, not a prompt on its own — same convention as dispatch.sh's `--brief-bead`.
- **Gate handling**: a rotation spawner should read the exit code and surface a gate failure the same way dispatch.sh does (log it, prepend anyway) rather than either blocking the rotation or silently upgrading a FAIL to a PASS.
- **Tracker resolution**: a rotation spawner running from Quilan's own working directory must pass `--bd-cwd` explicitly if the bead's tracker isn't reachable from there — this is the same bd-cwd-vs-repo-root gap `--brief-bd-cwd` exists to cover in dispatch.sh (see script docstring for the underlying cause: bd resolves its tracker from cwd, independent of which repo is being briefed).

Landing the Quilan side of this (calling the script, prepending its output, handling the gate) is tracked as follow-up work against mk-42j9.25 F4, not part of this bead.
