# Per-change quality scorecard

**Design only, 2026-09-27.** This proposes an offline reduction of existing evidence, a versioned JSON result, and a project-scoped rollback recommendation. It adds no receipt fields, database tables, daemon, or model-selection framework. Implementation and rollout are not authorized by this document. Thresholds and the two operational proxies below need mk's decision; other-frontier review remains a gate.

**Goal.** An efficiency change can be retained only after attributable, comparable outcomes hold in each exposed project. A cheap run with unknown quality or usage cannot pass. A regression in one project cannot be averaged away by another project's improvement.

**Consumers.** Lane A (`mk-42j9.25`, Sonnet-default rollout) and lane C (review-packet A/B) consume the same JSON contract. Quilan consumes a rollback recommendation through an integration adapter, preserving `routing-receipt.ts`. Clavain records the resulting exception through its existing routing policy. Those are proposed connections, not claims of deployed integration.

## 1. Data model and attribution

### Frozen change specification

One small JSON experiment specification accompanies the existing task/cohort evidence. It is input to a proposed `scripts/quality-scorecard.py`, not a new database or receipt version. Its SHA-256 is `change_revision`; changing a setting, cohort, rule or exclusion creates a new revision and experiment epoch. It records:

- `schema_version: 2`, `change_id` (owning bead, e.g. `mk-42j9.25`), `kind` (`routing-default|effort|ttl|rotation-threshold|review-packet`), and the exact before/after setting values and units.
- Full landed commit OIDs, policy-file hashes, installed configuration hashes, affected roles, expected executed model/effort/tier tuples, effective exposure intervals, and immutable project identities. A Git commit is evidence of a code change; it is not the activation timestamp.
- Project aliases, tracker namespace, default branch, lineage membership, bead enrollment, arm assignment, artifact/reviewer bindings, the frozen rule version and explicit exclusions. Each binding has an existing receipt/commit/export reference. An unsubstantiated manually typed binding is not gate evidence.
- Assignment unit and seed, scheduled UTC observation windows, workloads and reviewer protocol, known concurrent changes, prior execution profiles and setting values for rollback. Assignment and exclusion rules are frozen before outcomes. Retrospective reconstruction is labeled `before-after`, never relabeled randomized A/B.
- `attribution_deadline_days` (default 3): the frozen deadline (§4), counted from the moment a candidate's status becomes `triggered-pending-attribution` — never from the underlying finding's review-start anchor or the escape's close anchor (§2) — after which an unresolved candidate becomes `unknown`. `declared_surface` (roles, deliverable kinds, file/path scope, or an explicit affected-component list; nullable — a null/absent surface means every candidate proceeds straight to attribution review, with no prefilter, §4). For `kind: ttl` only, `ttl_price_table_ref` (`Hash` of the pinned per-TTL cache-write/read price table in effect for the experiment; required for `kind: ttl`, absent for every other kind, §4).

For model and effort experiments, the actual executed tuple and profile must match the assigned exposure. TTL, rotation and packet changes may leave policy hash/model unchanged: join their pre-recorded activation/configuration or existing enrolled manifest to the lineage/session, then to bead and receipt. **Time or a bead title alone is not proof of exposure.** If existing configuration/assignment evidence cannot supply this binding, those rows are `unattributed`; they cannot establish a treatment effect. This design does not add a TTL, rotation, lineage or change field to governed receipts.

### Exact read/reduction path

1. **Snapshot.** Read consistent database snapshots/transactions, an authoritative Beads snapshot **and transition history**, and Git objects plus fresh remote default-branch ref evidence. Record capture time, watermarks and hashes. No `immutable=1` shortcut that silently drops SQLite WAL contents. Ref freshness must cover the entire outcome horizon; a failed fetch or missing history is unknown, not a failed landing or zero defects. Read all needed pre-window history, not just records inserted inside the window.
2. **Routing rows → attempts.** Project-map `project_dir`; validate context version 1; require SQL/context dispatch and bead IDs to agree when both are present. Collapse repeated lifecycle rows per attempt, ordered by `(decided_at,id)`. Retain all source IDs, earliest `started` and final terminal `completed|failed` row. Conflicting terminal results invalidate the attempt; pending rows do not become completed through elapsed time. Retries remain distinct attempts but share the deliverable. Use `context.executed_profile_ref`, with only S2's documented `resolved_profile.profile_ref` fallback, plus `execution.{backend,model,reasoning_effort,service_tier}`. Never use the primary profile as actual exposure. Preserve failure class, exclusions and policy profile/hash.
3. **Attempts → enrollment/cohort.** Match the namespaced bead and project, verify artifact/reviewer bindings, then assign by frozen lineage/session membership and change interval. Already-enrolled S8 cohorts match their existing envelope/hash. A dispatch spanning a configuration flip, conflicting bead IDs, overlapping assignments, a wrong actual tuple, or missing effective-setting evidence gets an explicit exclusion/reason. Keep its costs in the assigned-arm diagnostic; do not quietly turn fallbacks into successful treatment samples. Gate-quality per-protocol comparisons require complete intended exposure; assignment-based diagnostics retain every enrolled bead and failure.
4. **Interstat → bead/cohort, independently of receipt count.** Match `agent_runs.bead_id` to the namespaced enrollment **and** match `session_id` to the project's bound native/parent session set. An empty bead tag can inherit a binding only when the complete run belongs to exactly one enrolled bead. Multiple possible beads/projects/arms are unknown, never evenly divided. A parent session ID can link several child runs, but each run is counted once; it cannot uniquely link a child to one dispatch. Require explicit native evidence for an attempt-level join. Aggregate usage first, then join aggregated totals to cell keys. Never join raw runs to all review receipts on bead ID.
5. **Usage reconciliation.** Parsed run totals cover an entire transcript and can span time, models and beads (S5). A whole-run sum is allowed only when that whole run is bound to one cell. Otherwise use existing `agent_run_usage.run_id=agent_runs.id` model/day buckets when they fit wholly within one assignment/window and reconcile exactly to parent totals. If finer boundaries are necessary, use existing transcript evidence and S6's response de-duplication through the existing attribution path, or mark burn unknown. Do not prorate by run count, duration or bead count. Parent/coordinator and child usage must be disjoint; shared coordinator burn is assigned once to its enrolled arm, not once per child. Unsupported Codex/other-provider usage in `agent_runs` remains missing; do not report Claude-only savings as whole-bead savings.
6. **Beads/Git → outcomes.** Normalize tracker history to `{event_id,namespace,bead_id,time,old_status,new_status,evidence_ref}` and snapshot metadata to `{namespace,bead_id,issue_type,priority,created_at,status,closed_at}`. These are reducer input records, not claimed native `bd` field names. Resolve the installed adapter's actual history/export interface before implementation; this session could not verify it. Git provides full-OID commit links, ancestry, revert bodies and fixed default-branch snapshots. Join these facts to enrolled bead/deliverable keys, then reduce each metric as specified below.

This separates three questions: assignment, actual exposure and outcome. Every output cell reports all three. Legacy receipts with no bead/subject binding are useful inventory but cannot silently populate scored denominators.

## 2. Five metrics and observable definitions

All windows are half-open UTC intervals. Event follow-up is `(anchor,anchor+604800 seconds]`; an event exactly at seven days counts. A complete observation has `as_of >= anchor+604800` and both tracker/Git coverage through that point. Partial observations are censored, even if they have no observed defect. Known adverse events may be displayed early, but a bead's own metric resolution still requires that bead to reach its full observation window (§4's per-bead resolution) — an early sighting does not shortcut maturity.

Block membership is explicit per metric: findings use the bead's first required review-start time (all its enrolled deliverables stay in that block); escapes/rework and durable-close throughput use its first acceptance-close time; burn uses request time with the repair reassignment below. A bead can therefore be in different blocks for different metrics, but never in two blocks for the same metric. A required review that has not completed remains missing in its original block, not dropped or moved to a later clean block. Report each metric's own population rather than asserting that every metric has the same denominator. An unstarted required review is missing evidence for its enrolled population and blocks a keep; it cannot disappear because it has no review timestamp.

### Review findings per deliverable, by severity

For severity `s`, value = sum of initial independent validation findings of severity `s` / number of fully scored deliverables. Use one preselected validation channel per artifact kind, with the same rubric, reviewer model/effort and stage in both arms. If a fixed panel is required, define a panel as one channel and sum its fixed slots; require every slot to be scored. Counts are **reported findings**, not deduplicated unique defects; S2 has no finding IDs. Never union or average an opportunistically changing panel.

Use the first successful completed review of the frozen first-review revision in each required slot. Failed/no-body attempts remain costs and missing-review evidence. A later clean re-review cannot erase the original findings. Validate `source in {verdict,body}`, nonnegative integer counts, and `total = P0+P1+P2+P3`; `unknown`, null, absent, inconsistent or non-review output is unscored. A known zero is a zero only after these checks. Report scored/eligible deliverables and provenance by source; an unscored required deliverable/slot makes that bead's finding status `unknown` (§4's per-signal resolution) — it does not disable or bypass the gate.

**Lane C trap:** fewer findings by a weaker reviewer is not evidence of better quality. The review packet itself is lane C's deliverable. A fixed independent validator audits its omissions and false positives against the same subject and rubric, and that validator's findings are the common quality metric. The tested reviewer's raw counts are diagnostics only. Paired shadow reviews must be of the same frozen subject; shadow artifacts have no invented closures, throughput or escaped-defect outcomes. Real downstream metrics require a bounded live A/B after the shadow comparison. Count-only receipts cannot establish recall or finding correctness without that independent evidence.

### Escaped defects within seven days

The headline is **distinct affected closed beads / mature first-close beads**, not a sum of three overlapping signals. Keep separate counts and evidence for each signal. Anchor to the bead's first acceptance close in its enrolled cohort; never reset the clock on re-close. Include closed beads that remain open at maturity, as defects rather than exclusions. A multi-deliverable bead is counted once in the union.

| Signal | Falsifiable rule | Limits / unknown condition |
|---|---|---|
| Reopened bead | A historical `closed → any nonclosed status` transition within the follow-up interval. Count the bead once in this signal, retain every transition ID. Comments, dependency updates and edits that leave status closed are not reopens. | A latest `closed_at` snapshot cannot prove absence of an intermediate reopen. Missing ordered transition history makes the signal unknown. Administrative reopens still count in v1; no retrospective narrative exclusions. |
| Revert | A commit reachable from the recorded default-branch tip has a canonical `This reverts commit <full-or-unambiguously-resolved-OID>.` body referencing a bead-linked accepted commit, and its committer time falls in the interval. Verify both objects and ancestry; a title containing “revert” alone is insufficient. | Unmerged local reverts are not landed reverts. Manual semantic undo without a link is not detectable by this rule. Revert-of-revert does not erase the first escape. A revert of a shared commit affects each explicitly linked bead, once each. Squash mapping must be explicit; no patch-similarity guess. |
| Failed landing, observable v1 proxy | At first close, the bead has an explicit candidate commit set. At maturity, at least one required candidate is still not ancestor of the fresh recorded default-branch tip, and no explicit squash/cherry-pick replacement link proves delivery. This is `closed_without_landing_7d`. | A missing commit link, object, fresh ref or replacement mapping is **unknown**, not failure. A rejected push or failed CI run repaired before maturity cannot be reconstructed from bd+git alone. This proxy must not be described as observing every failed landing. |

Commit links come from explicit bead/acceptance records or an exact bead token in the commit subject/trailer, constrained to the project's namespace and enrollment interval. Multiple beads in a commit remain explicit many-to-many links; vague free-text mentions are ambiguous. `checkout.after` supplies candidate evidence but is not alone an acceptance/landing claim (S1). Code deliverables without commit links cannot clear this metric. A committed documentation deliverable uses the same rule; no-code/non-Git work is outside v1's promotion cohort.

“At maturity” requires the default-ref state **at that bead's seven-day cutoff**, from existing timestamped Git ref/reflog evidence or a preserved source snapshot. Today's tip cannot erase a failure by including a commit that landed on day ten. A commit's author/committer timestamp is not evidence of when a remote ref acquired it. If historical ref evidence is absent, report landing-at-cutoff unknown; a retroactive `git log --before` filter cannot repair the gap. A prospective evaluation may preserve source ref snapshots with the existing experiment evidence, without changing receipts, but must not claim exact historical membership from an observation taken too late. Revert detection deliberately uses committer time as its observable event timestamp; flag that limitation and require cutoff-ref reachability as well, so a revert merged after seven days cannot count as a seven-day escape.

The union is positive if any known signal is positive. It is zero only if all three are observable and zero; otherwise it is unknown. Subtype rates use the same mature-bead denominator and are diagnostics; the union is the gate. Report manual-undetected-revert and repaired-failed-push limitations in the fixed metric definition, not as false zero counts.

**Revision note (option A: per-bead tri-state, not a bound pair).** The first draft left it unstated whether a bead with an unresolvable signal (missing ordered transition history, absent cutoff-ref evidence, unrecoverable ancestry) stays in the escape denominator; a later revision tried to fix this with a `escaped_min`/`escaped_max` bound pair feeding an SPRT, which a review found reintroduced directional bias when the same bound was applied to both arms. Under the hard-gate rule (§4) there is no rate or bound to compute at all: each mature bead's escape status is classified independently as `clear`, `triggered-pending-attribution`, `attributed` or `unknown` (§4's per-bead resolution). A single `attributed` bead fires `regressed` outright once its attribution review resolves it (a bare `triggered`/`triggered-pending-attribution` status does not, by itself, per §4's P1-D fix); `unknown` and unresolved `triggered-pending-attribution` beads never count as `clear` and therefore block `holds` until they resolve (§4's "no vacuous holds" rule). This is strictly simpler than the bound pair and has no charitable/uncharitable-reading asymmetry to get wrong, because there is no aggregate rate either bound was ever protecting.

An unknown share above a declared ceiling (`max_unknown_share`, default 0.15 of mature beads per cell) is still reported as a data-quality diagnostic, but it no longer changes the verdict logic: under the hard gate, even a single `unknown` bead already withholds `holds` (§4), so a ceiling on the unknown *share* would only matter for a rate the design no longer computes. Retain `max_unknown_share` purely as an advisory diagnostic in `Cell.diagnostics`, not a frozen-spec gating field.

**Canonical cutoff-ref evidence source.** "At maturity" (line 102 above) requires timestamped default-branch ref history at each bead's seven-day cutoff. The implementer must name one canonical, continuously-retained clone as the source of that history — this design designates **zklw's local `main` reflog** (per the zklw-canonical infrastructure convention: zklw is the dedicated dev server and the source of truth for git state, often ahead of GitHub, per `~/.codex/AGENTS.md` § "zklw — Dedicated Dev Server") as that single source, used consistently as both the ref that supplies cutoff-time history and the definition of "landed" throughout this section — never `origin/main`, which only advances when zklw fetches or pushes and can lag the actual landed state zklw itself produced. Because there is no pooling window under the hard-gate rule, the retention requirement is no longer derived from a maximum pooling window; it is instead set directly from the widest span any bead's own evidence can span: enrollment at the earliest point in a project's evaluation history (the baseline blocks' start, `t0−21d`, §3) through the final evaluation point (`t0+21d`, §3), plus each bead's own seven-day follow-up horizon, plus margin for report re-runs against older `as_of` dates — approximately 42 days of coverage by that derivation, plus margin; this design sets the retention requirement at **60 days**, verified at implementation time rather than assumed (prior drafts' 63-day and 119-day figures were both derived from now-removed pooling/baseline-gating assumptions and are superseded). Git's default `gc.reflogExpire` (90 days) already exceeds 60 days, but is a default, not a guarantee, and must be set explicitly for the canonical clone rather than relied on silently. Prefer ref snapshots taken prospectively at each bead's own cutoff over reconstructing history from today's reflog. A clone's reflog records local fetch/push time, not the remote's receipt time, and expires on its own schedule; where the zklw clone's history does not cover a bead's cutoff (retention gap, clone created after the fact, or the clone itself was rebuilt), that bead's failed-landing signal is `unknown`, not reconstructed from `git log --before` on today's tip. This is a named single source specifically so "unknown everywhere" becomes a rare, auditable gap rather than the default outcome.

### Rework turns per bead

**Proposed v1 operational unit: an additional acceptance cycle, not a chat/API turn.** For an enrolled bead, sort its authoritative transitions. The first nonclosed→closed transition ends initial work. Every subsequent closed→nonclosed transition starts one rework cycle, even when no correcting commit or re-close arrives. End that cycle at its next close or mark it open at the seven-day cutoff. Repeated edits, commits and reruns while nonclosed do not add cycles. A revert or failed-landing signal without a reopen is reported separately as untracked rework; do not infer chat turns from commits.

Metric = number of cycles started through the first-close seven-day horizon / number of mature first-close beads. Every reopened bead remains in the denominator. Report cycle start/end IDs, open cycles and correction commit links where available. This is exactly computable from historical bd status plus Git links, with no new instrumentation. It undercounts pre-close revision work and conflates administrative reopenings; label its definition `acceptance-cycles-v1` everywhere. If mk means actual conversational rework turns, that requirement is **unobservable from bd+git** and needs a separately approved definition/source; this design does not smuggle in a new receipt field.

**Advisory only (§4).** Rework is computed and reported as above, but per §4 it is never compared against a threshold and never produces `regressed`/`holds`/`insufficient` on its own — a reopen event that also fires the escaped-bead union (§4's hard gate) is caught there, so rework needs no gating role of its own and no overlap correction against that gate.

### Beads closed per hour

For a fixed enrolled production population and block, count distinct beads whose **first** acceptance close is in the block and whose status at close+7d is closed with an observed landing. Divide by the block's calendar hours. Re-closing a bead never increases throughput. A bead open at maturity contributes zero closes; its work and burn still count. Display gross first closes as a diagnostic alongside durable closes.

This is project output per calendar hour, **not human labor or summed agent duration**. Do not use interstat `wall_clock_ms` as a work-hours denominator: its availability is not guaranteed by S4, and concurrent work would be double-counted. Baseline and treatment must contain the same number of enrolled lineages and the same declared capacity schedule; retain outages in elapsed hours. Unequal capacity, material external outages or demand changes make the causal comparison insufficient. For A/B, compare the same treatment lineages' own baseline, with fixed control lineages separately; do not compare a six-lineage rate to a nine-lineage rate.

**Advisory only (§4).** Throughput is computed and reported as a plain before/after delta per block; it is never compared against a threshold and never produces `regressed`/`holds` under the hard-gate rule.

### Weighted burn per closed bead

Numerator = **all** attributable production burn in that arm/block, including failed attempts, retries, validation, shared coordination allocated once, work on unfinished/abandoned beads and seven-day repairs allocated back to the block of first close. Denominator = the durable distinct closes defined above. Each request belongs to exactly one budget block: ordinary work uses request time; a repair within a closed bead's follow-up horizon uses that bead's first-close block instead. Remove it from its chronological block. Cross-block and open-work allocation is audited; do not drop expensive failures by inner-joining only closed beads. Separately report shadow/measurement overhead and a total including that overhead; do not mistake experiment cost for steady-state cost.

Per request/run burn = input + 1.25×cache_creation + 0.1×cache_read + 5×output, using S6's weights. Interstat's `cache_creation_tokens`/`cache_read_tokens` map to the burn reader's `cache_creation_input_tokens`/`cache_read_input_tokens`; `total_tokens` and dollars are not substitutes. Unknown/null token components remain unknown. Use exact decimal or integer quarter/tenth units until display; round only presentation.

## 4. Exact v1 regression and keep rule

**Revision note (mk's ruling of 2026-09-27, "option A").** The first draft used a bare per-block threshold (findings 1/2/5); the first revision replaced it with a pooled sequential probability ratio test (SPRT) across all seven metrics. A second review found the SPRT construction itself broken in ways that cannot be patched in a bounded delta: zero margins on the most important metrics collapse the null and alternative hypotheses (false-rollback approaches 50%, not the declared `α`); the sampling models are wrong for heavy-tailed, clustered real data; the error-budget split undercounts tests; and a vacuous-holds bug lets an empty gating set trivially satisfy "holds" at Clavain's real volume (1–17 beads/week). Rather than attempt a third statistical design, mk ruled option A: **replace the statistical rule with hard, single-event gates that need no sample floor, and push real statistical gating to a follow-on bead once pooled volume supports it** (`mk-42j9.43`, filed with the R1–R6 findings as its starting notes). This section is a full replacement of the SPRT/pooling machinery, not a patch to it: `block_length_days`, `max_pooling_blocks`, `alpha_project`, `alpha_metric`, `beta`, `min_margin_fraction`, the Bonferroni split and the null-simulation fixture requirement are all removed, not merely deprecated.

**Revision note 2 (mk's ruling on the .33 delta review, 2026-09-27).** The delta review of the option-A rewrite found four blocking defects: findings could only be classified at bead maturity even though §2 defines separate finding/escape anchors, letting a confirmed P0 on an unclosed bead hide indefinitely (P0-1); the attribution window's second condition was tautological (the window is defined from the anchor, so it was always true), meaning every treatment bead's first-review P1 was attributed with no real filter (P1-1); the TTL efficiency check gated on a per-cell cost diagnostic rather than a defined saving, so it was vacuously always true (P1-2); and comparison-era tolerance/control-drift/stratum-floor language remained live in §2, §3 and §7 (P1-3). mk ruled on P1-1 to adopt the reviewer's option (a): a hard gate produces `triggered-pending-attribution`, never `regressed` directly, until a required attribution review (an agent's first pass is acceptable, provided the reviewer is not the bead's own producer) resolves it to `attributed` or `not-attributed`; rollback additionally needs mk's own confirmation; `holds` is blocked while attribution is pending; and an unresolved attribution past a stated deadline becomes `unknown`, which also blocks `holds`. mk additionally ruled to narrow the automatic trigger with a declared-surface prefilter (option (b)) as a prefilter only, never a substitute for the review. This section, and the corresponding parts of §1, §2, §3, §5 and §7, incorporate that ruling.

### Attribution: which change owns a finding or escape, and its window

A finding or escape is a **candidate** for attribution to change `change_id`/`change_revision` when both hold:

1. The underlying bead is enrolled in that change's treatment population under §1's assignment rules (frozen lineage/session membership, arm assignment, project/enrollment binding). An in-flight bead that crossed activation mid-work is excluded per §3's enrollment rule, not attributed to either arm. A bead excluded for fallback or contamination (§1 step 3) is not silently dropped from the gate: it is reported as a distinct `Exclusion` and remains a `promotion_eligible` blocker even though it does not enter the candidate population — a treatment that keeps falling back must not read as clean.
2. The event's own timestamp falls inside that bead's own follow-up window as already defined in §2: a finding's window is its bead's first required review-start time plus the follow-up interval `(anchor,anchor+604800 seconds]`; an escape's window is its bead's first acceptance-close time plus the same interval. The bead's anchor must itself fall inside the change's effective exposure interval from §1 — not after an approved rollback of this change, and not after a later concurrent change's own activation supersedes it. This is the real filter that condition 1 alone cannot provide: exposure interval and follow-up window are independent facts, since a validly enrolled bead can still be reviewed after the change's own exposure interval has closed (e.g. following an approved rollback). No pooling, no cross-block aggregation: each bead's own window is evaluated once.

A finding or escape whose bead is not enrolled in the change, or whose event falls outside the bead's own window or the change's exposure interval, is not a candidate for this change — it is background noise reported elsewhere (if at all), never mixed into this change's gate.

**Declared-surface prefilter (option b, applied first).** Where the frozen change specification (§1) declares an affected surface (roles, deliverable kinds, file/path scope, or an explicit affected-component list), a candidate whose deliverable or affected surface does not intersect the declared surface is excluded before attribution review — it is reported as background noise, per the rule above. This narrows volume; it is not a substitute for the attribution review below. A change with no declared surface skips the prefilter entirely: every candidate proceeds to review.

A candidate that survives the eligibility/window test and the prefilter is **pending attribution** (below); it is not yet `regressed`.

### Hard gates: single-event triggers, no statistics

Three signals are **mandatory gates** and can never be reclassified as advisory, regardless of volume:

- Any **P0 finding** resolved `attributed` (below), on any deliverable, in any block.
- Any **P1 finding** resolved `attributed`, on any deliverable, in any block.
- Any **escaped defect** resolved `attributed` (§2's reopened/reverted/failed-landing union, unchanged definition), on any bead, in any block.

Each is a **single-event trigger**: one `attributed` occurrence is sufficient to fire it. There is no threshold, no rate comparison, no minimum count, and therefore no sample floor to reach before the gate can fire — the first attributed P0, P1 or escape fires it, whether that is bead 1 of 1 or bead 40 of 40. This is what makes the gate well-defined at Clavain's real per-project volume: a rate-based test needs enough beads to distinguish signal from noise, but "did this specific attributed event happen" needs exactly one bead.

**Per-signal resolution point, not one shared "maturity" gate.** §2 defines two different anchors — first review-start for findings, first acceptance-close for escapes — and each signal resolves independently, at its own point:

- **Finding status** (P0/P1/P2/P3) resolves as soon as the bead's required first-revision review slot(s) are scored (§2's "first successful completed review of the frozen first-review revision"): `triggered` if any scored slot reports a P0/P1, `clear` if every required slot is scored with none, `unknown` if a required slot is unscored/invalid. This needs no seven-day wait and no bead close — a P0 confirmed on day 0 of a bead that never closes is `triggered` immediately, satisfying "reported immediately, not held pending further evidence." The gating population for finding status is **every enrolled treatment bead** with a scored required review, not only close-mature ones.
- **Escape status** resolves at the bead's first-close plus seven-day follow-up horizon, exactly as §2 defines it. **Bounded candidacy (mk's 2026-09-27 final ruling on the .33 round-3 review, Scope cut 2, addressing P1-F).** The escape-candidate population is bounded to the change's evaluation window (§3's final evaluation point, `t0+21d`): a bead still open at the end of that window has escape status `unknown`, finalized at that boundary rather than left open-ended against an ever-advancing `as_of`. A bead that closes before the window ends but has not yet reached its own close+7d follow-up is `unknown` only until that follow-up elapses, per the ordinary per-signal resolution above — re-running the report after that point resolves it normally. The gating population for escape status remains the close-mature population, per §2, plus these window-bounded still-open-at-`t0+21d` beads, reported as `unknown`.
- This is the direct fix for the prior draft's gap: a confirmed P0 on an unclosed bead is `triggered` on finding status the moment its review is scored, and can reach `regressed` (via attribution, below) immediately — it no longer waits on a close+7d "maturity" it may never reach.

**Attribution review: `triggered-pending-attribution` before `regressed`.** A `triggered` finding or escape status, above, does not by itself produce `regressed`. It produces `triggered-pending-attribution` for that bead/signal, which then requires an attribution review:

- The review's first pass may be performed by an agent, but the reviewer must not be the bead's own producer (the entity/session that produced the deliverable or authored the change under evaluation) — the same producer/reviewer separation already required elsewhere in this canon.
- The review records which surface of the change the finding or escape touches — the specific deliverable, role, file/path, or affected component — as evidence (`Trigger.evidence_refs`, §5).
- The review resolves the candidate to exactly one of:
  - `attributed` — the finding/escape is caused by, or inseparable from, the declared change; it counts toward `regressed`.
  - `not-attributed` — the finding/escape is caused by something else (a pre-existing defect, an unrelated concurrent change, reviewer error); it does not count toward `regressed`, and the review records a `reason` for the determination. It is then treated as `clear` for verdict purposes.
- **Rollback needs mk's confirmation separately from the attribution review.** An `attributed` finding/escape makes the project `regressed` and sets `repin.required=true` (§ Verdict aggregation), but the actual rollback action (§6) still requires mk's explicit confirmation before Quilan executes it — the attribution review decides the scorecard verdict, not the rollback action.
- **Deadline (P0-A fix, mk's 2026-09-27 final ruling on the .33 round-3 review).** Each `triggered-pending-attribution` candidate carries a frozen attribution deadline (`attribution_deadline_days`, §1, default 3 days), counted from **the moment this candidate's status became `triggered-pending-attribution`** — i.e. from finding-status/escape-status resolution time (the per-signal resolution points above), never from the underlying finding's review-start anchor or the escape's close anchor (§2). Counting from the underlying anchor was a defect: an escape's status does not resolve to `triggered-pending-attribution` until close+7d, so a deadline measured from the close anchor would already be expired the instant the candidate is classified, making every escape permanently `unknown` and the escape gate unable to ever fire `regressed`. Counting from status-assignment time gives every candidate the full `attribution_deadline_days` window regardless of signal type. A candidate unresolved past that deadline becomes `unknown` for its signal — not `clear`, not `attributed` — which blocks `holds` under the no-vacuous-holds rule below, exactly as any other `unknown` does.
- Until a candidate's attribution resolves, the bead/signal cannot contribute to `holds`.

**Per-bead resolution, not a rate.** For each candidate bead/signal, classify as one of:

- `clear` — the signal is confirmed negative for this bead (per the per-signal resolution point above), or an attribution review resolved a `triggered` candidate `not-attributed`.
- `triggered-pending-attribution` — the signal is confirmed positive and awaiting attribution review (above).
- `attributed` — an attribution review confirmed the change caused it; this is what fires `regressed` (below).
- `unknown` — a required signal cannot be established (missing ordered transition history, absent cutoff-ref evidence, an unscored or invalid review), or a `triggered-pending-attribution` candidate has passed its attribution deadline unresolved. §2's existing unknown-handling rules (never treated as a known zero) apply unchanged. **`unknown` is final (mk's 2026-09-27 final ruling on the .33 round-3 review, P1-A).** Once a candidate's status is set to `unknown` for a given report/`rule_version`, it is not later revised to `attributed`, `not-attributed` or `clear` even if a late attribution review eventually resolves the underlying question — a late review is recorded in the tracker/notes as supplementary evidence for a possible new experiment revision (§8 decision 3's remedy), never as a correction to this or any past scorecard's verdict. Re-running the report at a later `as_of` can still resolve a *different, still-pending* candidate normally; it cannot revisit one already `unknown`.

A single `attributed` bead/signal is sufficient to fire the gate: `regressed`. `triggered-pending-attribution` and `unknown` never fire the gate by themselves, but they also cannot be counted as `clear` — see "no vacuous holds" below. This replaces the first revision's `escaped_min`/`escaped_max` dual-bound arithmetic (which existed only to feed an SPRT boundary test): there is no rate to bound, so there is nothing to bias by applying the same bound to both arms. The reviewer's finding-5 concern (one reopen event firing both the escape signal and a rework cycle, "spending a budget twice") no longer applies either, since there is no shared false-rollback budget to spend — escape is a hard gate and rework is purely advisory (below), so the same event can appear in both without double-counting anything.

### Mandatory gating set; no empty set, no vacuous holds

The gating set is always exactly `{P0, P1, escaped-bead union}` — it is never empty, never shrunk to fit volume, and never reclassified as advisory for any project or lineage. This directly satisfies mk's "an empty gating set is forbidden" instruction: unlike the SPRT design, feasibility never enters the classification, because none of these three signals needs a sample floor.

`holds` requires **all** of:

1. At least one enrolled treatment bead has a resolved finding status, and at least one close-mature bead has a resolved escape status, for the change in that project/lineage (i.e., there is actual evidence, not zero exposure — a project with no scored evidence cannot hold on the strength of having observed no problems, because it has observed nothing). Report `Coverage.enrolled_beads_scored` and `Coverage.mature_beads` (§5) as the counts.
2. Every candidate bead/signal is `clear` — zero `attributed`, zero `triggered-pending-attribution`, and zero `unknown`. An unresolved bead/signal keeps the project out of `holds` until it resolves (to `clear`, to `not-attributed` — treated as `clear` — or to `attributed`, which fires `regressed`); it can never be silently dropped from the population or treated as passing. This is the direct fix for the vacuous-holds bug: "holds" cannot be produced by evidence that never arrived, and it cannot be produced while an attribution review is still pending.

There is no third, kind-specific condition: TTL changes are gated identically to every other kind (mk's 2026-09-27 final ruling on the .33 round-3 review, Scope cut 1, addressing P1-C — see "TTL changes" below).

If neither `regressed` (an actual `attributed` bead/signal) nor the full `holds` condition above is met — e.g., some beads remain `triggered-pending-attribution` or `unknown`, or there is no scored evidence yet — the verdict is `insufficient`. `insufficient` is not a default keep: lane A's own rollout stage gate governs whether a change stays exposed while evidence remains incomplete, per §6; this scorecard states the fact, not the disposition. A permanently unresolvable `unknown` (e.g. a permanent ref-retention gap, §2, or a bead still open at the evaluation window's end per the bounded-candidacy rule above) blocks `holds` for that bead/signal indefinitely, and is final per the per-bead resolution section's "`unknown` is final" rule; the stated remedy is an explicitly approved new experiment revision (§8 decision 3), not a heuristic override.

### TTL changes: efficiency evidence, advisory only

**Scope cut 1 (mk's 2026-09-27 final ruling on the .33 round-3 review, addressing P1-C).** TTL changes are quality-gated identically to every other kind: the P0/P1/escape hard gates above apply unchanged, and there is no TTL-specific `holds` requirement. The prior round's "efficiency required for `holds`" rule is removed outright — the review found that a raw baseline-minus-treatment cost difference, with no volume normalization, can reward a quieter or lower-volume treatment period as a false "saving," and no volume-normalization requirement is imposed here because the check is advisory-only precisely to avoid depending on that unnormalized number for a gate.

`ttl_cost_saving_usd` is retained as a reported **advisory** efficiency diagnostic:

- Define `ttl_cost_saving_usd = baseline_cost_usd − treatment_cost_usd`, computed over comparable cells — the same lineages' B-block and T-block — by applying the pinned per-TTL price reference (`ttl_price_table_ref`, §1) to each cell's actual cache-write/cache-read/input/output token counts.
- Report `usage_complete` (§5's `Coverage.usage_complete`) alongside it; an incomplete-usage cell yields `ttl_cost_saving_usd: null`, reported as such rather than assumed zero or positive.
- This value and its sign are a trend diagnostic only (`TtlEfficiency`, §5, explicitly labeled advisory): it is never compared against a threshold, never produces `regressed`/`holds`/`insufficient`, and is scoped to `ProjectResult` reporting only — matching every other advisory metric's scope (see "Everything else" below). A human or lane A's own judgment reads this trend, exactly as with burn's other advisory deltas.
- `api_equivalent_cost_usd` (§5's `Diagnostic` list) remains a separate per-cell cost diagnostic; it was never a gate input and stays that way.

A follow-on normalized/gated efficiency design remains out of scope here and is tracked under the same deferred-statistical-gating work as the rest of this section's advisory metrics (`mk-42j9.43`), should mk later want TTL efficiency to gate anything.

### Everything else: advisory trend only, never gates

P2 findings, P3 findings, rework cycles (§2, unchanged diagnostic-only definition), beads-closed-per-hour throughput, weighted burn per closed bead, and TTL efficiency (`ttl_cost_saving_usd`, above, for `kind: ttl` only) are computed and reported identically to their definitions, but are **advisory trend diagnostics only**: they are never compared against a threshold, never produce `regressed` or `holds`, and never gate `promotion_eligible`. Report each as a plain before/after delta per block (`Comparison.adverse_delta`, `Comparison.saving_fraction` for burn) with no `worse`/verdict semantics attached — a human or lane A's own judgment reads the trend; the scorecard does not adjudicate it. This is a permanent v1 disposition, not a placeholder pending a feasibility calculation: promoting any of these to a gate is future work for `mk-42j9.43`, requiring an actual statistical design (frozen margins, a correctly specified sampling model, a correct multi-test budget) reviewed and ratified before it gates anything.

### Verdict aggregation

For each project:

1. `regressed` if any bead/signal in any treatment lineage resolves to `attributed` (above). Report the triggering bead, signal, lineage and evidence in a `Trigger` record (§5); a single confirmed, attributed event is sufficient and is reported as soon as attribution resolves, not held pending further evidence. A regressed lineage makes its project regressed even if sibling lineages are clean.
2. `holds` only when every treatment lineage in the project satisfies the `holds` conditions above (scored evidence exists, zero `attributed`/`triggered-pending-attribution`/`unknown` among candidate bead/signals — identically for `kind: ttl`, per Scope cut 1 above), and assignment/exposure evidence is complete per §3's confound checks that still gate `holds` under the hard-gate rule (exact actual profile/model/effort/policy hash, instrument-epoch separation, fixed-except-treatment settings, and concurrent-change exclusion — §3). Workload-stratum balance and control-population drift are advisory-only diagnostics (§3) and do not by themselves block `holds`.
3. Otherwise `insufficient`, with the exact reason (`no_mature_beads`, `unresolved_bead_status` — covering both `triggered-pending-attribution` and deadline-expired `unknown` — or an existing confound exclusion reason). There is no TTL-specific reason code: `no_demonstrated_ttl_saving` is removed (Scope cut 1).

Evaluate once per scheduled report (`--as-of`), not on a checkpoint/stopping-rule schedule — there is no sequential test whose validity depends on a stopping rule, so re-running the report as more beads mature simply reflects more attributed evidence; a later `regressed` from a newly matured `triggered` bead is not a "second chance" at a budget, because no budget exists. A regressed change/project remains reverted until an explicitly approved new experiment revision, unchanged from the prior design's re-instatement rule. Changing the rule version invalidates cached decisions.

## 5. Output contract

**Choose JSON on stdout.** Proposed command: `python3 scripts/quality-scorecard.py --spec <frozen-spec.json> --as-of <UTC>`. One UTF-8 JSON document, newline terminated; diagnostics only on stderr. Exit 0 means a valid report, including `regressed` or `insufficient`; exit 2 means malformed/unsupported input and no stdout document. Missing optional evidence yields a valid insufficient report, not a success-looking empty array. Lane consumers inspect verdicts and eligibility, never process exit status as a keep vote.

The caller may save the exact stdout bytes with its existing experiment artifacts and hash them for an action reference. No database migration, shared writable scorecard store or “latest” filename is part of the interface. Results are reproducible from snapshot/spec hashes and `as_of`. Publish the normative v1 field tables and metric definitions by extending **`docs/canon/reasoning-routing-operations.md`, immediately after `### Receipt attribution fields`, as `### Quality scorecard contract`** (S2). Add a link to this rationale there during implementation. Do not put this object into the calibration reader's `agents` schema (S7).

**Revision note (option A: hard-gate contract).** Under §4's hard-gate rule, a verdict is produced by per-bead boolean/integer-count logic (was this bead's escape/finding status `triggered`, `clear` or `unknown`), not by a statistical boundary crossing — so the exact-decimal-vs-IEEE-754-double concern the prior revision raised for log-likelihood ratios no longer applies; there is no floating-point verdict boundary left to misread. `Comparison.worse`, `Metric.verdict`, `LineageResult.verdict`, `ProjectResult.verdict`, and `Report.overall` remain **authoritative as emitted**: a consumer must treat them as the decision, and must never recompute a verdict from `Cell.value`/`raw_value` or `Comparison.adverse_delta`/`saving_fraction`, which are diagnostic display values only. For the three hard-gate metrics (P0, P1, escaped-bead union), `Comparison.worse=true` means at least one bead/signal in that cell has resolved to `attributed` (§4's per-bead resolution) — a raw `triggered` or `triggered-pending-attribution` status alone is never sufficient, since those states have not yet cleared attribution review. `Cell.adverse_beads` is the count of `attributed` beads (§4's P1-D fix, mk's 2026-09-27 final ruling on the .33 round-3 review — the prior wording counted merely `triggered` beads, which would let an unreviewed candidate read as adverse before attribution); `Cell.diagnostics` carries a `pending_attribution_beads` entry (candidates still `triggered-pending-attribution`) alongside `unknown_beads`, so a consumer can see why a cell is `insufficient` rather than `holds` without recomputing anything. For the advisory-only metrics (P2, P3, rework, throughput, burn), `Comparison.worse` is always `null` — they report a delta, not a verdict — and `Metric.verdict` for those is always `null` (per the `Metric` row below), since it never contributes to `LineageResult.verdict`/`ProjectResult.verdict`; `reason_codes` includes `advisory_only` on every comparison for these metrics so a consumer cannot mistake a reported delta for a gate.

All fields below are required unless explicitly nullable. Unknown is JSON `null`, not zero/empty text. `Timestamp` is RFC3339 UTC ending in `Z`; `Hash` is 64 lowercase hex; `OID` is a full repository-format object ID; `ID` is a nonempty string. Counts are nonnegative integers, rates finite numbers. Objects are closed in v1; reject unknown fields, duplicate keys, nonfinite numbers, booleans used as counts, fractional schema versions and future schema versions. A compatible reader upgrade is required for new fields; bump `schema_version` for contract changes. `rule_version` changes only decision semantics and is separately allowlisted by consumers.

## 6. Regression → Quilan action → Clavain record

For each regressed project, `repin.required=true` targets **all still-exposed treatment lineages for that change in that project**, leaving controls and unrelated projects alone. A regressed lineage triggers its project even if other lineages offset the mean. This intentionally honors the bead's project boundary; lane A must not translate it into a shared BB-project default write. A stricter per-lineage-only rollback is an open mk decision, not an implicit consumer reinterpretation.

**`repin.required=true` is a recommendation surfaced to mk; it is never by itself sufficient authorization for Quilan to execute a rollback (§4's attribution-review rule, restated here per mk's 2026-09-27 final ruling on the .33 round-3 review, P1-G: rollback needs mk's confirmation separately from the attribution review that set the verdict).** The scorecard reports `repin.required` and leaves `repin.rollback_confirmation_ref` null (§5); mk's separate confirmation, once given, populates that reference through the existing approval channel. The adapter's action pipeline must gate on that reference being non-null, not on `repin.required` alone.

The action key is SHA-256 of the canonical tuple `(change_revision,project_key,rule_version,B1/B2/T1/T2 boundaries,sorted target lineage IDs)`. Quilan persists that key through its existing operational journal/rollout state **when its owner implements the adapter**; this document does not claim a particular journal schema. Duplicate reports cannot repeat a turn/handoff or overwrite a subsequent human pin. Before acting it checks current configuration/policy, role eligibility, project membership, manual pin state against the expected binding, **and `repin.rollback_confirmation_ref` is non-null (P1-G, above)** — a null reference blocks the action pending mk's separate confirmation, exactly like any other unmet pre-action check, regardless of `repin.required`. A changed binding blocks the action for reconciliation; it does not restore a guessed default.

The proposed adapter restores each prior eligible execution profile and the setting that caused the regression, then resolves a fresh governed receipt through the selected policy with the original role and producer exclusions. It maps to S9's unchanged envelope: `policySha256`, `providerId`, `model`, `reasoningLevel`, optional `policyTier`, `producerExclusion`, `quotaFloor`, `role`, `reason`, `dispatchReceipt`. `dispatchReceipt` retains the full original nested resolver result. Backend→host provider mapping must use the installed adapter/catalog, never assume `claude` equals a BB provider name. The target catalog validates model and effort; all policy floors and exclusions still apply. The old receipt is rollback evidence, not a reusable dispatch authorization.

Same-provider restoration applies to the next natural eligible execution; cross-provider restoration needs the supported handoff/spawn path, not a tell with an incompatible model. Existing manual pins win. No wake-up just to change idle threads, no shared `proj_personal` default write, and no role collapse from planning/validation/coordination to `lane`. These are necessary integration requirements in light of S12, not current behavior claims. The dry-run and live isolated canary must demonstrate restoration across a successor before live A/B starts.

Clavain's policy record uses `config/routing.yaml`'s existing `reasoning.profiles` overlay: proposed name `scorecard-<project-slug>-<change-slug>`, scope `project:<slug>`, and only the affected `roles` mapped to the recorded prior profile refs (S10). Store the scorecard hash and reason beside the scoped change in the existing experiment evidence/commit; do not add unrecognized YAML fields and assume `ic` enforces them. Lane A's proposed project resolver/rollout state must select that overlay and retain reverted exceptions across later default flips. Different prior tuples for the same project/role cannot fit one overlay: keep lineage-specific runtime state and mark policy persistence blocked pending mk's scoped-record decision, rather than pick one arbitrarily.

Runtime restore and policy commit are separate durable steps. A runtime failure leaves the action pending/failed and pauses new exposure; a policy-write failure does not undo a runtime restore. Never label both applied from an attempted command or a green scorecard. The consumer retains actual action evidence in its existing receipt/journal path, and retries idempotently. Existing verification, signing, branch protection and publication authority still govern the policy change. The design does not authorize this planning task to perform either step.

**Present integration gate:** S9's admitted mismatch and lack of production caller disprove the assumption that this path is ready. Escalate that premise to the task owner now. The implementing owners must fit a versioned adapter to real evidence and demonstrate runtime application plus scoped policy persistence. Preserve `routing-receipt.ts`'s contract; do not rewrite it to make synthetic fixtures pass.
