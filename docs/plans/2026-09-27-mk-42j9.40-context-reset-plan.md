# Context-reset rule for untrusted content and approval-gated actions — observe-mode hygiene measure

**Bead:** `mk-42j9.40` · **Epic:** `mk-42j9` · **Owner:** Clavain lane D
**Status:** mk-authorized Phase 2, narrowed scope (2026-09-27). Implement as an **observe-mode hygiene measure only**: detect exposure to untrusted content and approval-gated actions, record would-be resets and resets-per-session frequency, and **do not force any reset**.

**This rule is NOT a security boundary.** It does not stop persistent poisoning of durable records (bead notes, CanonGraph decisions, `AGENTS.md`/`CLAUDE.md`, auto-memory, or the working tree itself). It is a hygiene/telemetry measure that tells us how often exposure and approval-gated actions occur, so mk can later decide whether and how to enforce. Any doc or guidance this work touches must say so plainly, not imply enforcement exists.

**Scope moved out to `mk-42j9.42`, not built here:** artifact/digest-level origin taint and positive attestation, a tamper-resistant taint store, and making zklw's autosync timers taint-aware (or pausing them). Every section below that depended on those mechanisms is marked **`→ mk-42j9.42`** and reduced to a forward-design reference. **Promotion past `observe` mode requires `mk-42j9.42` landing first** — this plan builds no enforcement path.

## 1. Definitions and detection surfaces

These definitions are used for **recording only** in this phase. Nothing below causes a block or a forced reset.

### Untrusted content

“Untrusted” describes **provenance**, not whether text looks malicious. A trusted transport can carry untrusted text; storing external content in a repository does not make it first-party content.

| Content | Classification | Detection surface |
|---|---|---|
| Fetched pages, search snippets, downloaded documents | Untrusted, including apparently reputable sources | `WebFetch`, `WebSearch`; equivalent `web.run` search/open operations and this host’s `web__run`; pre-call tool identity and post-call result event |
| Browser pages, DOM text, screenshots, OCR, console output originating from visited sites | Untrusted | Actual browser/fetch tools used by interbrowse skills; `Skill` invocation is an early hint, not sufficient coverage |
| Third-party MCP responses and resource bodies | Untrusted by default | Fully qualified MCP tool name; resource-read server and URI; connector result origin |
| Harness-labelled external or pasted material | Untrusted within the labelled region | Harness-origin message metadata or transcript delimiters; quoted marker text supplied by a document cannot change classification |
| `curl`, `wget`, remote command output, or scripts returning external material | Untrusted when that material reaches the model | `Bash`/terminal command classification, registered wrapper metadata, and post-call provenance |
| `Task`/`Agent` results, bb child-thread results, or equivalent collaboration outputs | Untrusted if the producer encountered untrusted content; unknown when producer coverage is missing | Child session/epoch and exposure receipt joined to the result event |
| External text copied into a local file, generated summary, transcript, or memory | Remains untrusted | Recorded source-to-artifact provenance where feasible; observe mode logs a best-effort record, not a guarantee |

The following **do not trigger exposure by default**:

- The user’s own direct instructions and chat messages. External material quoted or explicitly pasted within those messages remains data.
- First-party repository files from the trusted project baseline.
- Normal workspace-owned output from internal tools such as `bd show`, `git status`, and `git log`.
- Internal tool receipts with validated provenance and fixed, expected fields.
- Child results with verified coverage showing no external exposure.

**Unknown provenance is recorded as `unknown`, not `clean`.** In observe mode this only affects what gets logged; it does not gate anything.

### Approval-gated actions

An action family that, if this rule were enforcing, would need a fresh execution context. In `observe` mode, detecting one of these only produces a log record — the action proceeds under whatever existing authority rules already govern it (`.35`/`.37`, ordinary approval gates). This section exists so the recorded frequency data is meaningful, not to gate anything yet.

| Action family | Examples | Detection surface |
|---|---|---|
| Remote source changes | `git push`, including tags, deletion, `--force`, and `--force-with-lease` | Terminal executable/subcommand/options; wrapper intent; Git/API mutation tools |
| PR publication and integration | `gh pr create`, `gh pr merge`, equivalent connector/API calls | Tool identity and operation; parsed shell command |
| Release and production operations | Deploy, release, production switch, qualification steps requiring approval, signing, package publication | Repository-owned command registry identifying executable/subcommand and effects |
| External publication | Posting artifacts, updating public content, sending messages, changing remote metadata | Connector/API operation, destination and payload digest |
| Destructive or override operations | Forceful mutations, destructive cleanup, overriding protected state | Command semantics and current contract; not the word `--force` alone |
| Explicit authority boundaries | Any operation labelled “fresh approval,” “human-launched,” or equivalent by the current contract | Trusted policy loaded at session startup and action-intent classification |

For this repository, include `ic publish --auto` and release entry points identified in [agents/development.md](/home/mk/projects/.clavain-laneD/agents/development.md).

Ordinary reads, local searches, reversible edits, local tests, builds, and authorized local commits are not recorded as approval-gated actions.

### Required detector state

Maintain state per **host session and context epoch**, linked to the bb thread.

Record:

- Session, thread, parent, role, epoch and policy version.
- Exposure state observed: `clean`, `exposed`, or `unknown`.
- Triggering tool-event IDs and source classes.
- Research-batch boundary (see §3) as observed, for frequency accounting.
- Approval-gated action family detected, with a would-be-reset flag — **recorded, never enforced, in this phase.**

Use hashes and opaque references in log rows. Do not log credentials, page bodies, approval text, or sensitive URL query strings.

### Origin-tagging and write-taint → `mk-42j9.42`

The pre-narrowing plan proposed tagging every write to an authority-bearing path/store (`AGENTS.md`/`CLAUDE.md`, bead notes, CanonGraph decisions, auto-memory, the working tree) with the writing epoch's exposure state, then blocking writes to those paths from exposed/unknown epochs. Both cross-lab reviews and the fix-delta re-review found this mechanism, even fully built, insufficient — it tags the proposer rather than the artifact, so a clean successor re-proposing an identical carried action, or an exposed epoch poisoning the working tree directly, both defeat it. Building the correct version (artifact/digest-level taint plus positive attestation, and a tamper-resistant store) is **entirely out of scope for this phase** and tracked under `mk-42j9.42`. **Observe mode implements no write-taint of any kind and gates no writes.** This is the concrete meaning of "not a security boundary against persistent poisoning" above: an exposed context can still write anywhere a clean context could, including bead notes, `AGENTS.md`, and memory, with nothing in this phase noticing or stopping it — only future reads of *external* content are recorded.

## 2. Where detection lives

### Recommended split

| Layer | Responsibility in observe mode | Why it cannot act alone |
|---|---|---|
| Clavain `PreToolUse`/`PostToolUse` hooks | Classify reads and actions; record exposure and would-be resets to a log | Hooks may be absent, bypassed, malformed, or unable to observe nested commands |
| Existing audit backstop | Reconcile tool history against the recorded log for coverage gaps | Detection after the fact cannot itself change behavior — nor should it in this phase |

Quilan and the `mk-42j9.35` spawn wrapper are **not integrated in this phase**. Observe mode records within a single running context; it does not rotate anything, so it needs no replacement coordinator. Their integration contract is deferred to the promotion decision (see §6).

Use the family established by [hooks/gauge-gate-executor-spawn.sh](/home/mk/projects/.clavain-laneD/hooks/gauge-gate-executor-spawn.sh) for the shell/jq classification pattern, but **return `"decision": "allow"` unconditionally** — this phase's hook only appends an evidence row, patterned after `scripts/pattern-f-verdict.sh`, and never returns `block`.

Do not build another daemon, scheduler, or general authorization service.

### Event handling

1. **After an external read result:** record exposure state for the epoch (`clean` → `exposed`) and log the triggering event.
2. **Before a tool call classified as an approval-gated action (§1):** if the epoch is `exposed`/`unknown`, log a would-be-reset record (epoch, action family, elapsed reads/time since first exposure). **Do not block the call.**
3. **At child-result ingestion:** log producer provenance if available; if raw exposed content is visibly present, log the receiving context as exposed. Do not join or propagate blocking state — there is none to propagate.
4. **At startup/resume:** log epoch state as `unknown` unless a fresh session start is recorded; this is informational only in this phase.

Do not run slow logic inside the blocking hook path; append-only logging must stay fast and must fail open (a logging failure never blocks a tool call).

### Bypasses and failure behavior

Support common command forms (`git -C … push`, absolute paths, `env …`, known wrappers) for **detection accuracy**, not enforcement — an unrecognized form simply produces an under-count in the frequency data, not a missed gate. Record coverage gaps explicitly (a "detector did not classify this call" counter) rather than silently treating them as clean.

**Everything in this phase fails open by design**, since nothing is gated. A malformed hook envelope, a logging-store write failure, or an unrecognized command form all result in "no record for this event," never in a blocked action — there is no action-blocking path to preserve.

### Hook-originated actions, host-level paths, non-bb hosts

`hooks/auto-push.sh`, `hooks/auto-publish.sh`, zklw's autosync timers, `hooks/dotfiles-sync.sh`, `hooks/context-gateway.sh`, and non-bb hosts (interactive sessions, headless `dispatch.sh` runs, in-session subagents) are all **out of scope for recording in this phase** beyond what the ordinary hook surface already sees. In particular:

- **Autosync taint-awareness or pausing is explicitly `mk-42j9.42` scope**, not this bead's. This phase makes no changes to `git-autosync-repair.timer`/`git-autosync-promote.timer` and does not attempt to observe them.
- Non-bb hosts get no special handling in this phase — if the same hook mechanism runs there, it logs; if it doesn't, that's a documented coverage gap, not a blocker, since nothing here blocks.

## 3. The reset design → reference only, not implemented in observe mode

Everything in this section describes the **target design for enforcement**, preserved from the pre-narrowing plan for continuity so `mk-42j9.42` and the eventual promotion decision have a starting point. **None of it executes in this phase.** Observe mode implements only §1–§2 (detection) and the recording/frequency-estimate half of §4. Quilan is not contacted; no reset is requested; no context is replaced; no approval is re-established or withheld.

Retained design notes, unchanged from the prior revision, marked deferred:

- **Two independent triggers** (exposure trigger: coalesced 20-read/10-minute read-only research batch; approval trigger: fresh epoch before every sensitive action) — `→ enforcement deferred`. In observe mode, the same batch-window definition is used only to decide *when* to log a would-be-reset, so the frequency estimate in §4 reflects the actual proposed policy rather than a naive per-read count.
- **Carry-forward policy, re-establishing approval, operational sequence** — `→ mk-42j9.42` for the origin-tagging-dependent parts, and `→ promotion decision` for the rest (Quilan integration, restricted handoff, quiescing). None of this is built now.
- **Child-thread `BLOCKED`/reparenting for a forced reset (§4 of the prior revision)** — `→ promotion decision`. Since nothing is forced in observe mode, there is no `BLOCKED: SECURITY_CONTEXT_RESET` to report yet.

## 4. False-positive cost and the observe-mode deliverable

**This section is what Phase 2 actually builds.** The rest of this document is detection surface (§1–§2) plus design reference for later (§3).

Observe mode must produce, from real usage, per lane/coordinator/steward role and in aggregate:

- Count of exposure events (first untrusted read per epoch) and would-be research-batch boundaries, using the 20-read/10-minute coalescing rule from §3 so the count reflects the proposed batching, not raw read count.
- Count of would-be approval-trigger resets: an approval-gated action (§1) detected while the epoch is `exposed`/`unknown`, and separately, while `clean` (to show the cost of the broader "every sensitive action" reading mk has not yet ruled on).
- Estimated incremental cost per the existing cost model — `H × (cache-write price − cache-read price)` for a warm prefix of `H` tokens — applied hypothetically to each would-be reset, using actual epoch context size at the trigger point.
- A coverage-gap counter (§2) so the frequency estimate's confidence interval is honest about what the detector could not classify.

Recommend this data be reviewable via a simple query/report over the log store (a script, not a dashboard), so mk can set promotion/kill thresholds for `approval`→`full` from real numbers rather than guessing. This satisfies the frequency-estimate requirement from the prior review round without inventing new UI.

### Staged activation

| Mode | Behavior | Built in this phase? |
|---|---|---|
| `observe` | Record exposures, would-be resets, coverage gaps and estimated costs; nothing is enforced | **Yes — this is the entire deliverable** |
| `approval` | Enforce fresh contexts for sensitive actions | No — requires `mk-42j9.42` first |
| `full` | Also enforce research-batch exit resets | No — requires `mk-42j9.42` first |
| `off` | Disable recording | Yes (trivial: a config flag) |

`config/context-reset.yaml` ships with `mode: observe` and no path to `approval`/`full` in this phase's code — those modes are named in config for forward compatibility with `mk-42j9.42`'s work, but this phase's hooks only implement the `observe`/`off` behaviors and must refuse to start (log an error, not block anything else) if misconfigured to `approval` or `full`, since that code doesn't exist yet.

## 5. Rollback

Rollback in this phase is trivial, because nothing is enforced: set `mode: off` in `config/context-reset.yaml`, or remove the hook registrations from `hooks/hooks.json`. There is no approval state, no successor, no pin, and no claim to reconcile, because observe mode never rotates anything. Retain the log store for whatever history it already recorded.
