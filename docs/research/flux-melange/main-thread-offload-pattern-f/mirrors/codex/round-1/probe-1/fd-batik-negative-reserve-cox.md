## Findings

### positive-only-plan-cannot-hold-the-reserve

- **Severity:** P0. Concrete failure: a pilot adds a command that exposes a missing validation path in a shared helper; the fresh executor treats that task-caused omission as critical, changes the helper outside the intended behavioral boundary, and passes the requested command's verify block. Existing callers now behave differently, while the Opus validator re-runs only the frozen positive criteria and returns PASS. Users of those callers receive the corruption even though every named addition works.
- **Where:** `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:15-17`; `skills/writing-plans/SKILL.md:78-105`; `skills/executing-plans/SKILL.md:112-123`.
- **What:** Pattern F says an executor "Never expands scope," but its cited plan format has only positive marks—Truths, Artifacts, Key Links, and files to create/modify/test—and no negative reserve. The actual execution skill then authorizes task-caused bug fixes, error handling, validation, auth, indexes, dependencies, and build-config repairs without permission. At least three pilot-observable reserves therefore vanish in the fresh context: (1) files outside the task's `Files` list, (2) existing behavior in touched shared files that is not one of the new Truths, and (3) deliberately deferred validation/auth/build decisions that a fresh executor can classify as "critical functionality" or a blocker.
- **Evidence:** The target relies on `writing-plans` to make plans execution-grade and promises no scope expansion (`...pattern-f.md:15-16`). `writing-plans` specifies only desired behaviors and artifacts (`SKILL.md:83-95`) plus positive file operations (`SKILL.md:102-105`). `executing-plans`, which those plans require, explicitly says Rules 1-3 fix or add task-caused adjacent functionality with "No permission" (`SKILL.md:116-123`). Because Pattern F limits the validator to frozen plan criteria (`...pattern-f.md:17`), none of these three reserves is available as a rejection condition.
- **Suggestion:** Add one compact `## Reserve` block to the plan contract: `untouched_paths`, `preserved_behaviors`, and `deferred_decisions`. Amend Deviation Rules 1-3 with one sentence: crossing a declared reserve is a plan defect and must be reported before editing. Make each pilot record whether a proposed deviation hit one of those three reserve classes; do not copy the main thread's history into the plan.

### checkpoint-owner-disappears-at-the-batch-boundary

- **Severity:** P1. Concrete failure: a multi-batch `/execute-plan` pilot finishes batch 1 and commits. If the Sonnet executor continues, it has auto-approved a gate the command declares mandatory; if it stops, the Fable orchestrator must ingest the batch state, present it, retain the user's ruling, and construct a resumable handoff before batch 2. The first path removes user control; the second restores the very main-thread stage context Pattern F is meant to offload.
- **Where:** `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:3,15-17`; `commands/execute-plan.md:6-27,39`; `commands/work.md:35-44`.
- **What:** Pattern F names the `/execute-plan` authors as owners but describes only plan → executor commit/report → validator. The current command defines execution as review-gated batches, labels each checkpoint a mini-Validate, and forbids auto-approval. There is no Pattern F role or artifact for the state between immersions: who pauses, what the user inspects, which ruling becomes the reserve for the next batch, and how a fresh executor resumes without rereading the preceding layer.
- **Evidence:** `/execute-plan` requires a stop for user approval after every batch (`commands/execute-plan.md:8-15`) and makes the architect checkpoint part of the repeating OODARC sequence (`commands/execute-plan.md:19-27`). `/work` likewise requires all declared checkpoints to stop and wait (`commands/work.md:35-44`). Pattern F assigns the main thread only plan writing, reports, and landing, and places validation after executor completion (`...pattern-f.md:15-17`); it never maps these intermediate controls. Q-B's reports-versus-planning split (`...pattern-f.md:31`) consequently omits mandatory checkpoint coordination as a third residual context sink.
- **Suggestion:** Keep the first Pattern F pilots on autonomous `/work` items, or add a single checkpoint receipt file for `/execute-plan` containing batch completed, reserve inspected, user ruling, and next permitted stage. Explicitly assign the main thread only the user-facing pause and let a fresh executor resume from that receipt; do not call the pilot successful if it suppresses the existing checkpoint.

### q-a-confuses-model-value-with-observation-window

- **Severity:** P1. Concrete failure: the executor writes implementation before proving the planned test is red, then runs the final verify block and commits. Opus receives a green repository and repeats the green command. It cannot determine whether the test ever failed against the entry state, so a process violation that can admit a non-discriminating regression test is silently certified; the implementer and reviewer both appear successful while maintainers inherit a change whose intended red boundary was never observed.
- **Where:** `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16-17,30`; `skills/writing-plans/SKILL.md:107-142`; `commands/execute-plan.md:19-27`.
- **What:** Q-A has the wrong premise. Validator value is not a binary property of "Opus versus no Opus" after the executor has fixed all layers; it is a property of placement relative to the boundary's reveal-and-repair window. The standard plan itself is path-dependent: establish a failing test, observe red, edit implementation, observe green, then commit. Pattern F transmits only the final verify output, so the red-state evidence is gone before the validator arrives.
- **Evidence:** The required task sequence puts the failing-test observation before implementation and commit (`writing-plans/SKILL.md:107-132`), while `<verify>` is only the final task check (`writing-plans/SKILL.md:134-142`). Pattern F commits and reports before Opus re-runs that final block (`...pattern-f.md:16-17`). The existing command calls intermediate batch checkpoints mini-Validates (`commands/execute-plan.md:19-27`), confirming that the repository already treats stage placement as semantically meaningful.

  | Stage ledger | Entry state | Positive operation | Protected reserve | Observation window | Masking transition | Permitted recovery |
  |---|---|---|---|---|---|---|
  | Red boundary | Planned task, production code unchanged | Add the regression test | Production behavior and implementation remain untouched | Run the exact test and retain the expected failure before any implementation edit | Editing implementation can make the test green and erase proof that it discriminated the entry state | Repair the test or plan while product code is still untouched |
  | Green boundary | Recorded red result plus implementation edit | Make the smallest change that turns red to green | Unnamed existing behaviors outside the task's Truths | Run the focused test before commit and compare against the reserve | Commit plus later cleanup fixes the layer and makes attribution expensive | Revert the local implementation hunk or escalate the reserve conflict |
  | Final reveal | Committed item | Re-run `<verify>` | Only frozen positive criteria remain visible | Opus sees final outputs | PASS/FAIL cannot reconstruct whether either earlier boundary was observed | Whole-item rework; stage-local diagnosis is no longer available |

- **Suggestion:** Replace Q-A with: "At which declared transition does an independent observation catch a defect while repair is still local?" For stage-sensitive tasks, retain one tiny checkpoint receipt (command, expected boundary, actual result, pre-transition) and place validation there. If no failure-prone intermediate boundary is declared, omit Opus rather than repeating the final reveal.

### token-share-rewards-unobserved-layering

- **Severity:** P2.
- **Where:** `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:15,21-26`; `skills/writing-plans/SKILL.md:45-48,107-142`.
- **What:** The `≤50%` gate counts who generated output, not how much path-dependent work occurred between observations. A pilot can improve the ratio by moving a long chain of two-to-five-minute red/edit/green/commit operations off-thread even as the number of uninspected reserve boundaries rises. This is distinct from total cost or context-volume blindness: two runs with identical token share can have radically different diagnostic reversibility because one crosses one boundary and the other crosses ten before any independent inspection.
- **Evidence:** The target defines success solely as main-thread generated-token share (`...pattern-f.md:15,23`). The cited plan discipline deliberately decomposes work into many ordered actions (`writing-plans/SKILL.md:45-48`) and its canonical task has at least three state-changing/observing transitions before final verify (`writing-plans/SKILL.md:107-142`). The ratio contains no term for transition count, declared reserve coverage, checkpoint placement, or whether a repair happened before or after the next masking layer.
- **Suggestion:** Keep token share as the offload measure, but add three pilot columns rather than a broad dashboard: path-dependent transitions, transitions with a declared reserve/checkpoint receipt, and repairs first detected after the next transition. A run that meets `≤50%` but worsens the latter two is not evidence that Pattern F preserved quality.

## Verdict

Pattern F is not pilot-ready until the plan can carry a compact negative reserve and `/execute-plan` checkpoint ownership is explicit. Q-A is premised incorrectly: Opus adds information only when placed at a boundary whose evidence and cheap recovery disappear at the next stage; a final verify replay cannot establish that. The token-share gate should remain a throughput signal, not the sole acceptance gate for layered execution.
