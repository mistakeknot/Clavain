## Findings Index

- [P2] report-not-repair-leaves-the-correct-but-insufficient-middle-unresolved — the executor contract has no category between "defect, report it" and "apply it," and no stated strike granularity for multi-task plans (§The shape / Executor)

## Findings

### plan-omits-repo-state-precondition
- Severity: P0
- Where: "The shape" § Executor (line 16: "Receives one plan file path and the repo path... Applies the plan, runs the plan's verify block") and § Open questions Q-E (line 34, candidate answer: "plan drift — a plan written against stale repo state that a fresh executor cannot notice").
- What: The plan is the executor's only channel (line 16), yet neither the plan template this doctrine already uses (`skills/writing-plans/SKILL.md`) nor the verify-block format it defines gives the plan anywhere to record the repo state it was written against. The plan header (SKILL.md lines 50-74) carries `bead`, `Goal`, `Architecture`, `Tech Stack`, `Prior Learnings` — no commit SHA, no clean-tree assertion, no branch identity. The `<verify>` block (SKILL.md lines 134-139) is `run:`/`expect:` pairs checked against the code's current state after editing, not against the state the executor started from. A fresh executor spawned with only a path and a repo location (line 16) has no field to read and no step to run that would tell it the tree moved since the plan was authored.
- Evidence: Read `skills/writing-plans/SKILL.md` in full — the "Plan Document Header" and "Task Structure" sections are the entire plan-authoring contract this doctrine enforces, and neither contains a precondition or state-pinning field. Q-E (line 34) already names "plan drift" as the doc's own candidate failure mode, which confirms the design's authors see the risk in the abstract but the artifact that would close it — a precondition block — doesn't exist in the template it depends on.
- Suggestion: Add a required `Preconditions` field to the plan header template (commit SHA authored-against + clean-tree assertion) and a mandatory first `<verify>` step of a new `precondition:` kind that the executor runs before any edit — fail loud (return unopened) rather than silently apply against a mismatched SHA. This is the smallest change that makes Q-E's named risk detectable from inside a fresh executor's context rather than merely named in prose.

### strike-leaves-no-defined-safe-state
- Severity: P1
- Where: "The shape" § Executor (line 16: "commits with the plan's message file, reports the verify output verbatim") and § Escalation (line 19: "an executor that fails a plan twice... returns the item to the orchestrator").
- What: The doc specifies that a commit happens via "the plan's message file" — implicitly on success, since a message file for the finished change wouldn't fit a failed verify run. It never specifies what a FAILING attempt leaves in the working tree: uncommitted edits from a completed "write the implementation" step, a partial multi-task application, a created branch. Two-strikes (line 19) means a second executor spawns against the same "repo path" (line 16) after a first strike — if that path still carries the first attempt's half-applied edits, the second executor doesn't get the clean start the plan assumed; it gets a tree the plan doesn't describe and has no way to distinguish from an intentional partial commit.
- Evidence: Cross-reading lines 16 and 19 — the contract states what the executor must never do (expand scope, repair the plan) but has no clause for what it must do to its own edits before returning on failure. The writing-plans task template's own "Step 5: Commit" (SKILL.md lines 128-132) is per-task, implying multi-task plans commit incrementally — which makes a mid-plan failure's leftover state ambiguous by construction: some tasks committed, one half-applied, the rest untouched, with no field to record which.
- Suggestion: Add an explicit abort clause to the executor contract: on verify failure, revert or stash uncommitted edits and record, in the returned report, exactly which of the plan's tasks (if multi-task) reached a commit before the strike. That gives strike two — and the orchestrator's plan-fix decision — a known starting tree instead of an inherited unknown.

### concurrent-pilots-share-one-repo-path-with-no-stated-isolation
- Severity: P1
- Where: "The shape" § Executor (line 16: "Receives one plan file path and the repo path"); task context notes "Three pilots are planned once the design passes review."
- What: Line 16 hands the executor "the repo path" — singular, no mention of a dedicated worktree or a reservation step. With three pilots running as the next step after this review, if two pilot items' plans touch overlapping files (plausible: pilots are drawn from the same repo, same offload shape), nothing in Pattern F says whether each executor gets an isolated worktree or all three write into one shared checkout. This is not a hypothetical gap in this specific repo: Clavain already ships `interlock` for exactly this ("Multi-agent file coordination is generalizable | Shipped" — `docs/clavain-vision.md:365`) and `agents/codex-integration.md:12` documents the two available answers ("native worktrees isolate edits, interlock coordinates shared trees") as a considered design choice elsewhere in this same doctrine. Pattern F names neither.
- Evidence: `docs/clavain-vision.md:365` and `agents/codex-integration.md:12` (read directly) confirm worktree-isolation vs. interlock-coordination is an existing, named choice in this codebase's own multi-agent tooling — the target doc's single mention of "the repo path" at line 16 doesn't pick one, and "What makes it enforceable" (lines 21-26) doesn't mention either mechanism.
- Suggestion: State explicitly, in "The shape" § Executor, whether each pilot executor runs in its own worktree (isolation) or on a shared checkout coordinated by `interlock` (reservation) — one sentence, citing whichever of the two existing mechanisms Pattern F adopts, closes this before three concurrent pilots make it a live collision risk instead of a documentation gap.

### report-not-repair-leaves-the-correct-but-insufficient-middle-unresolved
- Severity: P2
- Where: "The shape" § Executor (line 16: "Never expands scope; a plan defect is reported, not repaired").
- What: This binary — apply the plan, or report a defect — has no category for a plan step that's correct but insufficient (works, but doesn't fully satisfy the verify block), a verify block with an obvious one-token typo, or a pre-existing failure unrelated to the plan's own edits. It also doesn't say whether "reported, not repaired" halts the whole plan or just the offending task — material for a multi-task plan (per `writing-plans`' own per-task commit structure) where tasks 1-2 might be sound and only task 3 is defective.
- Evidence: Line 16 is the entirety of the executor's decision rule; no other line in the doc qualifies it. The writing-plans task template (SKILL.md lines 97-140) is explicitly per-task with its own commit step, so a plan with N tasks has N points where this ambiguity could resolve differently without the doc specifying which way.
- Suggestion: Extend the executor contract with two clauses: (1) "insufficient but not wrong" gets reported as a defect like any other — no silent narrowing allowed — and (2) on a multi-task plan, a defect in task K halts at K and reports which earlier tasks already committed, rather than leaving "the whole plan" as the only unit of failure.

## Verdict
The handoff's single largest risk is that the plan file — the executor's only channel — has no way to assert the repo state it assumes, so Q-E's named drift risk stays silent through every downstream check the design specifies. The remaining gaps (undefined abort state, an unstated worktree/interlock choice for three concurrent pilots, and an unresolved report-vs-repair middle) are instances of the same pattern: the contract states what must not happen without stating what must be left behind or asserted first.
