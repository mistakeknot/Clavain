## Findings

### validator-re-runs-the-exact-configuration-pilot-1-showed-catches-nothing
- Severity: P0
- Where: "The shape" § Validator (line 17: "Receives the same plan and the executor's report. Re-runs the verify block itself. Judges ONLY against the frozen criteria in the plan") and § Open questions Q-A (line 30: "Does the validator add information, or only cost, when the plan's verify block is already executed by the executor?... the pilots will show whether Opus catches anything the verify block missed").
- What: The validator's contract, as written, differs from the executor's own run in zero dimensions that matter for the defect class this design cites as dominant: same plan, same frozen criteria, same verify block, same tree. This precise configuration — a second party re-running the same verify block the first party already ran — is not a hypothetical risk here; it's the configuration `commands/model-routing.md` reports pilot-1 already tested, by name, in this repo: "4/4 frontier-authored plan-executions struck out on the plan's OWN verify block, never on code... 6 gauge defects observed... Reviewing caught none of them across two rounds" (model-routing.md:99, 121-122). The doc even cites this same pilot ("per pilot-1's 6/6 gauge defects," line 19) to justify the escalation rule's "usual case" — but doesn't notice that pilot-1 also falsifies the validator design one line below it. Re-running an identical checker against an identical artifact cannot distinguish "the code is right" from "the checker always says yes"; both examinations return the same PASS for the same reason.
- Evidence: `commands/model-routing.md:114-119` (rule 9) states the fix pilot-1 actually validated: `plan-gauge-lint.py`, run BEFORE freeze, against the plan's own emitted output, blocking, by neither authoring arm — wired as "Step 0 — gauge lint (blocking)" in `commands/plan-review.md:14-26` (confirmed present in this checkout). That mechanism is absent from Pattern F: it appears nowhere in "The shape" § Validator (line 17) or in "What makes it enforceable" (lines 21-26). Q-A as posed asks the pilots to measure something ("catches anything the verify block missed") that the stated validator contract has no structural capacity to produce, for the same reason pilot-1 already found reviewing didn't: examining the same sample with the same standard by the same method tells you about re-execution variance, not verification value.
- Suggestion: Q-A cannot be answered by these pilots as specified — it needs a wrong-premise flag, not a wait-for-data deferral. Either (a) fold the already-proven fix into the validator step — run `plan-gauge-lint.py` against the plan's own emitted output as part of validation, not merely re-running the frozen verify block — or (b) reframe Q-A from "does re-execution catch missed defects" (unfalsifiable as specified) to "does a gauge-lint step run at validation time catch defects the freeze-time run missed" — a question the pilots' data actually can answer.

### the-standard-is-never-assayed-before-freeze
- Severity: P1
- Where: "What makes it enforceable rather than aspirational" (lines 21-26, the doc's own list of four controls) and § Escalation (line 19: "fixes the plan (usual case: the verify block was wrong, per pilot-1's 6/6 gauge defects)").
- What: The orchestrator is the sole author of both the plan and its verify block (line 15), and the validator is explicitly barred from applying anything but the frozen criteria (line 17: "never its own taste") — so no party in this shape checks whether a criterion measures what it claims before it's frozen and scored. The doc's own enforceability list (lines 21-26: the interstat meter, closed inheritance, plan-file transfer, the small-task-lane exception) has four bullets and none of them is a check on the criteria themselves — despite the doc citing, one paragraph later, the exact evidence (pilot-1's 6/6) that a checked-nowhere standard is this shape's dominant observed failure.
- Evidence: `commands/model-routing.md:123-128` names the specific defect shape pilot-1 found: "the plan's emitted text is simultaneously the artifact and an input to a checker the same author wrote, and nobody ever executed one against the other. Two frontier-tier authors, a frontier-tier reviewer, and the harness itself each shipped an instance — so this is not an author-tier weakness a better reviewer fixes." That is a direct statement that plan-author quality doesn't prevent this defect — only an independent, pre-freeze execution of the checker against known output does, and that step (rule 9, model-routing.md:114-119) is not named anywhere in Pattern F.
- Suggestion: Add criterion verification as a fifth "enforceable" bullet: require `plan-gauge-lint.py` (already built, already blocking in `/plan-review`) as a precondition of any plan entering Pattern F execution, distinct from and prior to the validator's re-run — the standard gets assayed once, independently, before either examination that depends on it.

### gate-denominator-cannot-distinguish-model-inherit-from-genuine-offload
- Severity: P2
- Where: "What makes it enforceable" bullet 2 (line 24: "Deliberate frontier-in-the-loop spawns name `model: inherit` explicitly") and bullet 1 (line 23, the interstat meter as the gate's instrument).
- What: `interstat/scripts/profile.py` classifies every message into the "subagent" lane purely by file path — `is_subagent_file()` checks for `/subagents/` in the path or an `agent-` filename prefix, or `entry.get("isSidechain")` (profile.py:38-39, 80) — never by model. The summary line the doc calls "the number the routing doctrine's offload gate reads" (profile.py:7, 136) is `main_output_share = lane_out["main"] / total_out`, where `total_out` sums every subagent's output regardless of which model produced it. A `model: inherit` spawn — which the doc itself permits for "deliberate frontier-in-the-loop" work (line 24) and the doctrine's own "hard-problem exception" requires for a whole class of items (`model-routing.md:68`) — runs the full frontier model but is counted, in the gate's denominator, identically to a genuine 20-40K-context Sonnet executor. A goal that legitimately escalates every item to frontier-in-the-loop can pass the ≤50% gate while running 100% frontier-tier reasoning, because the metric certifies which process emitted the tokens, not which model or context size did.
- Evidence: Read `interstat/scripts/profile.py` in full — `is_subagent_file` (lines 38-39) and the `lane` assignment (line 80) confirm classification is path/sidechain-based only; the `(lane, model)` key (line 82) preserves model detail per row, but the `main_output_share` summary (line 119) collapses across all subagent rows regardless of model before the gate reads it.
- Suggestion: Either split the summary's subagent bucket by model tier before computing the gate (report `main_output_share` alongside a `frontier_subagent_share` of the subagent total), or state explicitly in the doc that the gate is a volume-of-process check, not a volume-of-cheap-execution check — so a reader doesn't infer the second from a metric that can only certify the first.

### binary-pass-fail-has-no-channel-for-non-strike-failures
- Severity: P2
- Where: "The shape" § Validator (line 17: "Output: PASS / FAIL with the failing criterion quoted") and § Escalation (line 19: two-strikes counts "fails a plan twice").
- What: The doctrine already has precedent that not every failure should count toward escalation: `commands/model-routing.md:110-113` (rule 8, "Strike taxonomy") explicitly excludes "sandbox denials, approval-gate blocks, auth expiry, rate exhaustion, and infra errors" from counting as strikes, "because counting them escalates to the scarcest tier for problems that are not capability failures." Pattern F's validator has no equivalent for the verify-block-specific version of the same problem: a flaky check, a pre-existing failure unrelated to the plan's own edits, or a criterion that's marginally satisfied all produce the identical binary FAIL-with-quoted-criterion artifact as a genuine execution defect, and line 19 counts all of them the same way toward the two-strikes budget.
- Evidence: Rule 8 (model-routing.md:110-113) is the doc's own doctrine establishing that some failure classes are excluded from the strike count by kind, not by severity — the target doc inherits the two-strikes rule from this same doctrine (line 19: "per the doctrine") but its PASS/FAIL output format (line 17) has no field that could carry a "not a strike" classification for the verify-block-level equivalent of the classes rule 8 already names.
- Suggestion: Extend the strike taxonomy to cover verify-block outcomes: a validator-observed non-determinism (FAIL then PASS on identical re-run) or a failure the plan's own precondition didn't cause should be recorded and excluded from the two-strikes count, the same way rule 8 already excludes infra errors — otherwise a flaky check silently spends half an item's escalation budget before any genuine defect is examined.

## Verdict
Q-A carries the review's flagged wrong premise: the validator is specified to differ from the executor's own run in no dimension that matters, and this repo's own pilot-1 evidence already measured that exact configuration at zero — the fix that evidence produced (a pre-freeze, independently-run gauge check) exists in this codebase and is simply absent from Pattern F's shape. The remaining findings are smaller instances of the same gap: nothing here assays the standard before freeze, and the token-share gate can't tell frontier-inherited work from genuine offload or a flaky check from a real defect.
