## Findings

### validator-rerun-redundant-not-noisy
- Severity: P1
- Where: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:17 (§The shape, bullet 3, Validator)
- What: The two prior findings are not actually in tension over the same fact — they describe two different regimes of the same underlying gap (no isolation/idempotency contract for the validator's re-run), and one of them cites its supporting evidence imprecisely. Claim (2) is the dominant, structurally sound diagnosis for the common case: `writing-plans/SKILL.md`'s own canonical `<verify>` example (`pytest ...`, `python -c "..."`) is read-only/idempotent, and for a read-only verify block, running it a second time against the same (or an equivalent) tree necessarily reproduces the executor's exact PASS/FAIL — the validator adds zero information about whether the *criteria* were right, only whether the executor's report matched reality. That is a real, low-severity catch (misreporting) but not what "verification asymmetry" is sold as doing against a defective checker. However, claim (2)'s citation "this exact configuration is the one this repo's own pilot-1 evidence already measured at 0/6 gauge-defect catches" over-reaches: model-routing.md:99 attributes the 0/6 catch-rate specifically to the READING-based "review" step ("Reviewing caught none of them across two rounds"), not to re-*executing* the verify block. The mechanism doctrine credits with catching all 6 defects is `plan-gauge-lint.py` — mechanical execution of the verify block against the plan's own emitted output, done BEFORE freeze (rule 9, model-routing.md:114-119, "reading cannot see it and execution can"). Pattern F's validator does execute the verify block (unlike "review"), but post-hoc, against the executor's already-mutated real repo state — a third configuration pilot-1 never tested, and structurally closer to a no-op replay than to gauge-lint's decoupled dry-run. Claim (1)'s non-idempotency risk is real and additive but conditional: it requires a verify block with side effects or state-dependent assertions (not ruled out by the design, but not the canonical case either), and produces the opposite symptom — spurious noise (false FAIL) rather than redundant silence.
- Evidence: target:17 ("Re-runs the verify block itself. Judges ONLY against the frozen criteria..."); target:19 ("the verify block was wrong, per pilot-1's 6/6 gauge defects"); commands/model-routing.md:99 ("Reviewing caught none of them across two rounds — the linter replays all 6"); commands/model-routing.md:114-119 (rule 9: gauge-lint executes verify blocks "against the plan's own emitted output," blocking, before freeze, by a reviewer ≠ author); commands/model-routing.md:128 ("It is n=6 that reading cannot see it and execution can"); skills/writing-plans/SKILL.md:134-139 (canonical `<verify>` block is read-only: pytest + python -c print).
- Suggestion: Not a taste call — resolvable. Correct claim (2)'s citation (attribute the 0/6 to the review step, not to re-execution) while keeping its structural conclusion; treat claim (1) as an additive, narrower risk that applies specifically when a plan's verify block is non-idempotent.
- Remediation: State explicitly in §The shape that the validator's re-run cannot substitute for a pre-freeze gauge dry-run against the plan's own emitted output (doctrine rule 9), and specify that verify blocks must be idempotent/side-effect-free or the validator must run them against an isolated, freshly-checked-out tree.

### pattern-f-omits-doctrine-gauge-lint-gate
- Severity: P1
- Where: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:17,19 (§The shape / §Escalation)
- What: Pattern F's escalation rule invokes pilot-1's 6/6 gauge-defect finding by name ("the verify block was wrong, per pilot-1's 6/6 gauge defects") to justify *what happens after* two strikes, but Pattern F's three-role shape (orchestrator/executor/validator) never incorporates the mechanism doctrine itself built in direct response to that same finding: rule 9's mandatory gauge dry-run — mechanical execution of the plan's verify block against the plan's own emitted output, blocking, by a model other than the plan's author, before the plan is frozen (model-routing.md:114-119, wired as "step 0 of `/plan-review`"). Pattern F has no analogous pre-freeze step anywhere in §The shape or §What makes it enforceable — the orchestrator writes the plan (with its verify block) and the very first execution of that verify block happens inside the executor's own run, after the plan is already frozen and already being acted on. This means Pattern F silently drops the one mechanism its own cited evidence shows actually catches gauge defects, and substitutes a post-hoc validator re-run that the adjudication above shows cannot do the same job.
- Evidence: target:17,19; commands/model-routing.md:99 (role table row "Gauge dry-run + review... lint every plan... both before freeze"); commands/model-routing.md:114-119 (rule 9 text and "wired as step 0 of `/plan-review`").
- Suggestion: n/a (see remediation).
- Remediation: Add a mandatory pre-freeze gauge-dry-run step to Pattern F's shape — run the plan's verify block against the plan's own emitted output via the existing `plan-gauge-lint.py`, blocking, by a reviewer other than the orchestrator that authored the plan — before the plan is handed to an executor, per doctrine rule 9.

## Verdict
Not a taste call: claim (2) is the dominant, well-grounded diagnosis (self-referential re-run of an unchanged checker against an unchanged state adds no signal about the checker's own correctness) but slightly misattributes its evidence, while claim (1) survives as a real, narrower, additive risk conditioned on non-idempotent verify blocks. Resolving the citation exposes that Pattern F omits doctrine's own proven fix (rule 9's pre-freeze gauge dry-run) for the exact failure it cites as justification for escalation.
