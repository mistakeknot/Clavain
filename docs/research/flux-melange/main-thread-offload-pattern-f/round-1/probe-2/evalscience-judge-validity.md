## Findings

### no-precondition-field-confirmed

- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16 (executor contract), :17 (validator contract), :25 (enforceability bullet on plan location)
- **What:** CONFIRMED. I read the plan template end-to-end (`skills/writing-plans/SKILL.md`) and the execution scripts it feeds: the Plan Document Header (lines 50-74), the Must-Haves section (78-95), the Task Structure block including the `<verify>` spec (97-142), and the Execution Manifest (144-176) — none carries a field for base commit SHA, branch identity, or a clean-tree assertion. `executing-plans/SKILL.md` Step 1 ("Load and Review Plan") reads the plan and starts executing with no repo-state check. `orchestrate.py` has zero matches for `git rev-parse|git status|clean-tree|checkout|fetch|pull|stash` — it dispatches tasks with no baseline check at all. The one SHA-shaped artifact in the whole pipeline, `vetted_sha` (executing-plans/SKILL.md:77), is written *after* verification passes — a postcondition audit trail, not a precondition gate. So the claim is fully grounded, not speculative.
  Under this lens the finding is stronger than "an executor might apply a stale plan": it means the validator's PASS/FAIL — the design's sole enforcement instrument (line 17, "Judges ONLY against the frozen criteria") — cannot function as a correctness measurement when the tree has drifted, because (a) the executor's own verify block only checks the plan's declared behavioral assertions against whatever tree exists, and (b) the validator "re-runs the verify block itself" against that same (already-mutated, settled-fact-confirmed unisolated) worktree, so it inherits the identical blind spot. A plan whose file paths/line ranges were computed against commit X, applied cleanly-but-wrongly against commit X+n (a concurrent goal landed, or autosync pushed — both routine per this repo's own `git-autosync-repair.sh` cadence), produces a FAIL-with-quoted-criterion or PASS artifact that is bitwise identical to a genuine-correctness result. This is now the *third* indistinguishable cause feeding the same binary artifact alongside pilot-1's bad-criteria and re-execution-flakiness causes already on record — and unlike those two, this one has zero channel anywhere in the pipeline (plan, executor contract, validator contract, orchestrator script) that could even register it happened.
  This also answers Q-A further than the doc poses it: the pilots cannot show "whether Opus catches anything the verify block missed" for drift specifically, because the validator's re-run is constitutionally blind to the one class of error a fresh-context executor is uniquely exposed to (a frontier main thread holding continuous context would at least sometimes notice "wait, this file doesn't look like what the plan describes"; a 20-40K-context fresh executor per line 16 has no baseline to notice against).
- **Evidence:** `skills/writing-plans/SKILL.md:50-176` (full plan template, no SHA/branch/precondition field); `skills/executing-plans/SKILL.md:15-18` (Step 1 has no state check), `:77` (`vetted_sha` written post-hoc, not pre-flight); `scripts/orchestrate.py` (grep for git-state commands returns nothing); four independently-generated flux-melange lens agents in this same repo (`fd-distsys-state-coherence.md:34-36`, `fd-pilotage-handoff.md:39-41`, `fd-sumitsuke-plan-fidelity-cox.md:35`, `fd-distributed-systems-handoff-cox.md:84,89`) already flag this exact gap from other angles, corroborating it is a real, repeatedly-surfaced omission rather than one reviewer's speculation.
- **Suggestion:** Not this lens's fix to design (mechanics belong to the distributed-systems reviewer per this agent's own scope notes) — but from a measurement-validity standpoint, until some precondition channel exists, pilot PASS results cannot be read as evidence Pattern F's validator is doing its job; the pilots should log base-SHA-at-plan-time vs. base-SHA-at-execution-time out of band so post-hoc analysis can at least detect how often this occurred, even before the design grows a fix.

### verify-block-mechanism-could-encode-sha-but-template-never-prompts-for-it

- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16; skills/writing-plans/SKILL.md:99-142 (`<verify>` block spec), :216-222 ("Remember" checklist)
- **What:** The `<verify>` block's `run:`/`expect:` pair is a generic shell-command-plus-matcher — a plan author technically *could* write `run: git rev-parse HEAD` / `expect: contains "<sha>"` as a task's first verify step today, with zero new tooling. But nothing prompts for it: the Task Structure example (109-140) is entirely behavioral (pytest, function output), the Must-Haves section (78-95) enumerates Truths/Artifacts/Key Links with no state-precondition category, and the "Remember" checklist (216-222) — the document's own list of what a plan author must not forget — lists "exact file paths," "complete code," "exact commands," "DRY/YAGNI/TDD," and explicit-judgment-avoidance, but nothing about baseline state. As a measurement-instrument design question (this lens's frame): the checklist is the thing meant to make plans "machine-checkable... for a weaker executor" (line 222) complete by construction; its omission of a precondition category means every plan authored under this template inherits the gap identically, so the finding above isn't an occasional lapse a careful orchestrator could route around — it's what the instrument currently produces by default.
- **Evidence:** `skills/writing-plans/SKILL.md:134-139` (verify block example is purely behavioral); `:216-222` (Remember list, no state/precondition bullet); `:78-95` (Must-Haves has no state category).
- **Suggestion:** Add a `<precondition>` (or a fifth Must-Haves category, "State") slot to the template and one line to "Remember" — cheapest fix that closes the gap for every future plan rather than one pilot's plan.

### q-e-names-the-risk-enforceability-section-ignores-it

- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:21-26 ("What makes it enforceable rather than aspirational"), :34 (Q-E)
- **What:** Q-E's own candidate answer is verbatim: "plan drift — a plan written against stale repo state that a fresh executor cannot notice." That is the *exact* mechanism this probe was asked to confirm, already named by the document itself as the shape's likely novel failure mode. Yet the section titled "What makes it enforceable rather than aspirational" — the doc's own validity claim that the design is more than aspirational — lists four bullets (a meter, closed inheritance, plan-location-not-context, small-task carve-out) and none of them is a check that could catch what Q-E already predicts. As a measurement-validity matter: a document section claiming "enforceable, not aspirational" is itself an instrument-completeness claim, and it's falsified by the document's own open-questions section naming a mechanism the enforceability list doesn't cover. This isn't new information beyond finding #1 — it's the observation that the doc's author already knew, and the two sections were never reconciled before publication.
- **Evidence:** Line 34 quoted above; lines 21-26 read in full, no bullet mentions state, drift, staleness, or preconditions.
- **Suggestion:** Either move Q-E's candidate answer into a fifth "enforceable" bullet (with the concrete field from finding #2) before pilots run, or explicitly retitle Q-E from an open question to a known, accepted-for-pilot-1 gap — the current framing (four "solved" bullets, then a named-but-unaddressed fifth risk in "open questions") reads as more settled than the doc's own content supports.

## Verdict

CONFIRMED, with high confidence and stronger grounding than the prior finding stated: not only does no plan field, executor contract, or orchestrator script carry a repo-state precondition, but the mechanism that could carry one (`<verify>` block's generic shell command) is never prompted for by the plan template, and the doc's own Q-E already names this exact failure mode without the "enforceable" section (21-26) addressing it. This makes the validator's PASS/FAIL a construct-invalid measurement of correctness under drift — indistinguishable, by design, from the already-settled bad-criteria and re-execution-flakiness confounds — and should be closed (at minimum, logged for detection) before pilot data is read as evidence about Pattern F's validator.
