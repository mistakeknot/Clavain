## Findings

### granularity-fragmentation-gate-arbitrage
- **Severity:** P0
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:15 (gate definition), :16 (executor priming), :17 (validator priming)
- **What:** The gate's denominator is "the goal's output tokens" (l.15) — not the orchestrator's total, the goal's total, which on the doc's own role split (l.16-17) includes every executor's applied-diff/commit narration and verbatim verify output plus every validator's PASS/FAIL judgment. That denominator is *directly proportional to item count*: cut a goal into more, smaller plan files and the executor+validator layer generates strictly more output tokens, which mechanically shrinks the orchestrator's share — improving the score — with no requirement that the orchestrator write less or plan better. This is a distinct lever from the already-flagged "thinner plan content" gaming (settled fact re l.15,19,21-26): that one holds item count fixed and starves plan quality; this one holds plan quality fixed and multiplies item count. Both game the same metric, through orthogonal moves, and the doc bounds neither.
- **Evidence:** Arithmetic sketch, using the doc's own numbers. Per item, the design pays a fixed re-priming cost of ~20-40K context to spin up a fresh executor (l.16: "Starts at ~20–40K context, not 300K") plus a comparable re-priming cost for a fresh validator to independently re-derive enough context to re-run the verify block (l.17: "Re-runs the verify block itself" — no stated floor, but it cannot re-run a check meaningfully on less context than the executor needed to apply it, so ≥20-40K is the conservative floor, not the ceiling). At a plausible 6-item goal that is ~6 × (30K + 30K) ≈ 360K tokens of pure re-priming context — comparable to or exceeding a *single* main-thread turn's 220-320K (l.7) — none of which counts against the ≤50% output-token gate, because context tokens are cache read/write, not generated output (this is the same 85%-of-cost-is-context fact the doc itself leads with, l.7,9). Meanwhile every one of those 6 executors and 6 validators also emits some minimum of *output* tokens (diff summaries, verify transcripts, PASS/FAIL text) that pad the gate's denominator. So a goal sliced into 6 items scores better on the gate than the same goal sliced into 2, even though the 6-item version paid 3x the fixed re-priming overhead the doc's own diagnosis (l.7,9) identifies as 85% of the cost problem Pattern F exists to fix. The pilots (per commands/model-routing.md:71, "run 2-3 items through the full loop") cannot surface this: three items scored well is exactly what fine slicing produces, so the evaluation method and the exploit point in the same direction.
- **Corollary on Q-B (l.31):** this lever also destabilizes any pilot answer to Q-B ("where does the orchestrator's context actually go — reading executor reports, or its own planning?"). Report count scales with item count (l.16-17: one report per executor, one per validator), so an orchestrator that fragments a goal to game the l.15 gate simultaneously grows the "reading reports" side of Q-B's own binary. A pilot run at one granularity cannot generalize an answer to Q-B, because granularity is an unbounded free variable the orchestrator controls and has an incentive to move.
- **Suggestion:** Smallest viable fix is not a rewrite of the gate — it's a floor. State a minimum item size (or maximum items-per-goal) so the gate can't be satisfied by fragmentation alone, and have `interstat/scripts/profile.py` (l.23) report total context tokens spent per goal (all roles, cache read+write) alongside the output-token share, so a goal that "passes" via fragmentation is visibly worse on the number that actually matters, right next to the number that doesn't.

### unexamined-batching-alternative
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16 ("fresh subagent"), :17 ("Validator (Opus, fresh subagent)")
- **What:** Freshness is mandated for both non-orchestrator roles with no stated reason and no examined alternative: could one executor session process the N plan files of a single goal sequentially, amortizing its ~20-40K prime across all N instead of paying it N times? Could one validator batch-check a goal's items in one session instead of independently re-deriving context per item? The doc never asks. This is the largest lever on total fixed cost in the whole design (see arithmetic above: ~40-80K per item just for the two priming events) and it's spent by default, not by decision.
- **Evidence:** l.16 and l.17 each assert "fresh subagent" flatly, once per role, with zero justification anywhere in the doc. The doctrine text this design implements (commands/model-routing.md, Capability-routing doctrine) states rule 6 — "pilot before batching: before fanning a plan backlog out to cheap executors, run 2-3 items through the full loop" — which already contemplates a *later* batching phase for the executor side, but Pattern F's own text never carries that forward into a stated per-goal item ceiling or a batch-validation mode; it just re-asserts freshness. If cross-item context poisoning within one goal is the reason batching is forbidden, that's a legitimate call — but it's a call the doc doesn't make, so the reader can't tell fixed-cost-by-decision from fixed-cost-by-default.
- **Suggestion:** Add one line naming the tradeoff explicitly: either "batching was considered and rejected because [X]" or "batching within a goal is an open question for the pilots to probe" — sitting next to Q-A..Q-E as a sixth open question, since it prices out larger than several of the five that made the cut.

### shakedown-cost-conflated-with-steady-state
- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:19 (pilot-1's 6/6 gauge defects); commands/model-routing.md:99,121-130 (pilot-1 rounds 1+2 detail)
- **What:** pilot-1's headline result — cited in-doc as the reason escalations "usual case" fix the verify block (l.19) — is itself, by the cited source's own account, a first-run-under-a-new-shape number: "4/4 frontier-authored plan-executions struck out on the plan's OWN verify block... 6 gauge defects observed... round 2 struck out both arms again, on a third gauge defect each" (model-routing.md:121-130). That means every execution in that pilot round incurred at least one full extra strike cycle — a second fresh executor spawn plus a second fresh validator spawn, i.e. a second complete re-priming payment by this lens's own accounting — driven by template immaturity, not by the steady-state per-item cost this design will settle into once the verify-block-authoring habit matures. The doc treats "pilot-1's 6/6" as a settled fact about how escalations behave (l.19) without separating shakedown cost (tooling/template still being broken in) from steady-state cost (the cost this design should be judged on once it's running normally) — a "take-up and draw-in" allowance no line in the doc names.
- **Evidence:** l.19's parenthetical treats pilot-1's defect rate as descriptive of the escalation path going forward ("usual case: the verify block was wrong, per pilot-1's 6/6 gauge defects"), but model-routing.md:121-130 frames the same number as diagnostic of an immature *process* (the gauge dry-run rule, item 9, was added *because of* pilot-1) rather than a stable property of the design. If Pattern F's cost/ratio claims are later benchmarked against pilot-1-shaped data without flagging which fraction of that data is shakedown, the design will read as more expensive than its steady state (if the fix landed) or hide a real defect rate (if it didn't) — and there's no line in the doc that says which.
- **Suggestion:** Before citing pilot numbers as representative, tag each pilot run's defects as shakedown (template/tooling immaturity, expected to zero out) or steady-state (structural, expected to recur), and don't fold the first tag into any go/no-go comparison against the 30-day baseline (l.7).

## Verdict
The doc bounds neither the number of items a goal is cut into nor whether executor/validator freshness is a priced decision or an unexamined default — and because the ≤50% gate is defined on output-token share of a denominator that item count itself inflates, fragmenting a goal into more, smaller plan files is a free, undetectable way to pass the gate while increasing total re-priming cost, exactly the cost class the doc's own 85%-context diagnosis says is the real problem. The batching question and the shakedown/steady-state split are both cheap to name now and expensive to discover after three pilots have already been read as clean.
