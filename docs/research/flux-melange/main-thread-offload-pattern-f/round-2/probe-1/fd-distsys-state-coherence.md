## Findings

### lane-blind-to-model-tier
- **Severity**: P1
- **Where**: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:23-24 ("A meter that sees lanes" / "Inheritance closed"); interstat/scripts/profile.py:38-39, 80-82, 119, 136
- **What**: CONFIRMED. `is_subagent_file()` (profile.py:38-39) and the lane assignment at line 80 (`lane = "subagent" if (sub_file or entry.get("isSidechain")) else "main"`) classify a transcript entry purely by file path / sidechain flag. The `model` field is captured at line 81-82 only as a grouping key for the per-row table — it is never consulted by the lane assignment, by `main_output_share` (line 119: `lane_out["main"] / total_out`), or by the printed gate line (line 136: "Main-thread share of generated tokens"). The doc's own line 24 names the exact escape hatch this blindness interacts with: "Deliberate frontier-in-the-loop spawns name `model: inherit` explicitly" — permitted per-item by the doctrine's hard-problem exception, with no per-goal cap named anywhere in this design.
- **Evidence**: Worked case — orchestrator (main) turns generate 40% of a goal's output tokens; every executor/validator spawn for that goal names `model: inherit`, resolving to Fable, and generates the remaining 60% (subagent lane). `main_output_share = 0.40 ≤ 0.50` → the gate reports PASS, while 100% of both main and subagent turns ran the frontier model. The per-`(lane, model)` rows computed at profile.py:106-113 *do* contain the data to catch this (a human reading the full table would see a `subagent claude-opus-…` row with large output), but the single scalar the doc treats as the gate (line 15's "≤50% of the goal's output tokens", realized at line 119/136) never reads that column.
- **Suggestion**: Surface a second summary number alongside `main_output_share` — e.g. `subagent_frontier_share` (subagent-lane output tokens attributed to a model NOT in the routing table's cheap-tier list, over subagent-lane total) — computed from the `rows` data that already exists, and gate on the pair rather than the lane ratio alone.
- **Remediation**: Amend "What makes it enforceable" to state that the ≤50% gate, as `profile.py` currently computes it, measures main-vs-subagent *thread* share only and does not verify that subagent-lane tokens came from the routed cheap model — `model:inherit` spawns must be tracked and reported separately from the gate's pass/fail number, not folded into the same denominator as genuine Sonnet executors.

### gate-has-no-goal-scope
- **Severity**: P1
- **Where**: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:15, 23; interstat/scripts/profile.py:93-98 (argparse), 71 (session filter), 119, 136
- **What**: The doc defines the gate's unit as "the goal's output tokens" (line 15), and calls `profile.py` "the meter" that turns this into "a number on that report, not a feeling" (line 23). But `profile.py`'s argparse block (lines 93-98) offers only `--days`, `--session`, `--since`/`--until`, and `--json` — no `--bead`/`--goal` flag, and `collect()` filters on the transcript's per-session `sessionId` (line 71), not on any goal or bead identifier. This design's own settled failure mode elsewhere ("a compaction or fresh orchestrator invocation on the same goal" resetting the two-strikes counter) already establishes that a goal routinely spans more than one orchestrator session. For such a goal, `--session <id>` silently excludes every other session belonging to the same goal (undercounting main-thread share, false PASS on partial data), while `--days`/`--since` co-mingles whatever *other* goals were worked in the same window (contaminating the number with unrelated work). Neither flag produces the number the doc names.
- **Evidence**: interstat's own `metrics.db` schema v2 and `scripts/cost-query.sh by-bead`/`session-cost` (per interstat/CLAUDE.md) already resolve a bead/goal to its session set via `/tmp/interstat-bead-{session_id}` and `scripts/set-bead-context.sh` — `profile.py` is a separate script in the same repo that does not reuse this plumbing, so the specific tool the brainstorm names as "the meter" for Pattern F's gate has no path from "goal" to "the sessions that belong to it."
- **Suggestion**: Add a `--bead <id>` (or `--goal <id>`) flag to `profile.py` that resolves the goal's session-id set the way `cost-query.sh session-cost` already resolves bead context, and union usage across every session tagged to that bead before computing `main_output_share` — reuse `scripts/set-bead-context.sh`'s existing bead↔session linkage rather than adding new logic.
- **Remediation**: Amend "What makes it enforceable" to state that `profile.py` has no goal/bead scoping today (only `--session`/`--days`), so the stated target "≤50% of *the goal's* output tokens" cannot currently be computed as a single number for any goal spanning more than one orchestrator session.

### subagent-lane-conflates-role-and-format
- **Severity**: P2
- **Where**: interstat/scripts/profile.py:38-39, 80
- **What**: The main/subagent split is three independent, undocumented proxies OR'd together — `"/subagents/" in path`, `basename(path).startswith("agent-")` (lines 38-39), and `entry.get("isSidechain")` (line 80) — with no semantic tie to "this is a Pattern F executor or validator turn" specifically, and no version pin to the transcript-layout convention they depend on. Two distinct consequences follow: (a) any other Task-tool subagent spawned in the same session/window for an unrelated purpose (a flux-drive review agent, a brainstorm helper, an interspect evidence-gathering subagent) lands in the same "subagent" bucket as a genuine Pattern F executor/validator, diluting or inflating `main_output_share`'s denominator with work the gate was never meant to measure; (b) if Claude Code's transcript directory or file-naming convention for subagents ever changes, every classification silently flips with no assertion, minimum-row-count check, or cross-reference against the plan's own known executor/validator spawn count to surface the drift.
- **Evidence**: `is_subagent_file()` (profile.py:38-39) returns a boolean from string matching alone; `collect()` never cross-checks the resulting `lane` counts against any independent source of "how many Pattern F role-spawns actually happened for this goal" (e.g. the plan file's own executor/validator dispatch count), so a silent misclassification in either direction would be invisible in the tool's own output.
- **Suggestion**: Tag Pattern F role-spawns at dispatch time (a marker written per spawn, mirroring `scripts/set-bead-context.sh`'s pattern) and have `profile.py` key its lane assignment off that tag rather than path/flag heuristics, so the gate measures Pattern F's own executor/validator turns specifically rather than "every subagent turn in the window" — and add a sanity check comparing counted spawns to the plan's declared dispatch count.

## Verdict
The prior finding is CONFIRMED: `profile.py`'s lane classification is purely path/flag-based and never reads the `model` field, so a `model:inherit` frontier subagent — which the doc itself permits per-item with no stated per-goal cap — contributes to the "subagent" bucket exactly like a genuine cheap executor, letting the ≤50% gate pass on a goal running frontier-tier compute throughout. Two further, distinct gaps in the same code compound it: the meter has no goal/bead scoping (only session/day-window), so the gate's stated unit — "the goal's output tokens" — cannot actually be computed as one number once a goal spans sessions; and the lane heuristic itself is unversioned and role-blind, so it silently absorbs unrelated subagent spawns and would silently misclassify everything if the harness's transcript-layout convention ever changes. All three point at the same root cause: the gate treats "subagent lane" as a proxy for "cheap, goal-scoped, Pattern F execution," but the code that produces the number never establishes any of those three properties.
