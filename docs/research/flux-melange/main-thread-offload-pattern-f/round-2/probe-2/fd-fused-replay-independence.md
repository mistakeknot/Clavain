# fd-fused-replay-independence — round 2

## Findings Index
- [P1] verdict-register-integration-gap — Pattern F verdicts have no stated path into the doctrine's own durable evidence register, and the register's schema can't tell replay from independent confirmation even when written (§What makes it enforceable / §The shape)
- [P2] unpinned-plate-plan-drift — frozen criteria freeze text, not repo state, so Q-E's "candidate" plan-drift failure is really two counted separately as one: a coordination gap (no commit pin/lease across three temporally separated spawns) whose only fix collapses straight back into claim 2's replay problem (§The shape; §Open questions Q-E)

## Findings

### verdict-register-integration-gap
- **Severity:** P1
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:12-19 (§The shape) and :21-26 (§What makes it enforceable); crossed with commands/execute-plan.md:44-52 and interspect/hooks/lib-interspect.sh:3021-3048 (`_interspect_insert_evidence`)
- **What:** The doctrine already has a durable, population-level verdict register — `execute-plan.md`'s completion step calls `_interspect_insert_evidence` with `author_model`, `executor_model`, `validator_model`, `criteria_total`, `criteria_failed`, `pass`, `escalation_count` — which is exactly the counter-assay mechanism a defective-checker-across-many-items pattern would need to surface (this is the P0 exemplar in this lens's own charter: "the resulting PASS is written to no durable register, so the gauge that produced it can never be assayed"). But Pattern F's shape (three fresh-context subagent roles, thin autonomous orchestrator) is never stated to run through `/execute-plan`'s checkpoint-gated control flow that contains this write — the design doc doesn't say what dispatch path Pattern F items take, and `/execute-plan`'s own behavioral rules ("Stop at checkpoints for user approval... never auto-approve") sit in tension with the thin, autonomous orchestrator Pattern F describes. Even where the write IS reached, it is fail-open at every layer (`_interspect_insert_evidence`'s own `[[ -f "$db" ]] || return 1`, wrapped in `2>/dev/null || true` at the call site) and its schema records a `pass` boolean and `validator_model` tier but nothing distinguishing "validator re-ran the verify block independently" from "validator's re-run replayed the executor's own already-passed checker" — the exact axis Q-A and this lens's parent-1 finding turn on. `escalation_count` is also hardcoded to `0` at the call site regardless of actual strike state, so even a landed write can't answer how many strikes an item consumed.
- **Evidence:** `commands/execute-plan.md:44-52` — the `_interspect_insert_evidence` call, gated behind three levels of `2>/dev/null` / `|| true` / `[[ -n "$interspect_root" ]]`; `interspect/hooks/lib-interspect.sh:3047-3048` — `[[ -f "$db" ]] || return 1` (silent no-op if the DB file is absent); `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:12-19` names the three roles and their dispatch (fresh subagent, plan path + repo path) with no mention of routing through `/execute-plan` or writing to any evidence store; `commands/execute-plan.md:9` ("Stop at checkpoints for user approval. Batch review checkpoints are mandatory — never auto-approve") reads as the opposite of the thin, autonomous orchestrator the Pattern F doc describes.
- **Suggestion:** Before the pilots run, state explicitly which control path Pattern F's executor/validator spawns take, and if it isn't `/execute-plan`, either route it through that evidence-insertion step or add an equivalent call at Pattern F's own completion point — with a `validator_mode` field (`independent` | `replay` | `unknown`) instead of a bare `pass` boolean, so pilot data can later be queried for "did any validator PASS that was structurally a replay" rather than requiring that judgment be reconstructed after the fact.
- **intersection_justification:** The distsys-state-coherence half supplies the concrete fact that a durable log exists but is call-site-bound (to `/execute-plan`'s specific completion block, itself gated by mandatory checkpoints) and fails open/silently at every layer — a pure assay reviewer, without tracing the shell script and its DB-existence check, would only be able to say "log the verdicts somewhere," a generic ask that doesn't diagnose why an existing mechanism might silently not fire for Pattern F specifically. The assay-independence half supplies the fact that even a successful write is diagnostically inert for the design's central question, because its schema conflates two assay strengths (replay vs. independent confirmation) under one boolean — a pure distsys reviewer, without that framing, would consider the integration "fixed" once the write reliably lands, without noticing the schema still can't support the counter-assay this lens's parent-1 finding says the design needs. Neither parent alone reaches "wire it up AND redesign the schema's independence field before the pilots start" — that requires tracing both the call-site/durability fact and the assay-validity fact together.

### unpinned-plate-plan-drift
- **Severity:** P2
- **Where:** docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:15-17 (§The shape) and :34 (Q-E); crossed with `commands/model-routing.md:102` ("Validation | opus, against FROZEN criteria only... criteria frozen before execution") and `:114-119` (gauge dry-run runs "against the plan's own emitted output" at authoring time)
- **What:** "Frozen" in this doctrine (model-routing.md:102, and the design doc's own "Judges ONLY against the frozen criteria" at line 17) means the criteria's *text* doesn't change after authoring — it says nothing about pinning the *repo state* the criteria are evaluated against. Pattern F puts the plan through at least three temporally separated touches on a shared trunk — gauge-lint/authoring time, executor dispatch, and validator re-run — with no version pin or lease named at any of them. Q-E already names "plan drift" as a *candidate* failure mode but frames it as executor-side ("a fresh executor cannot notice"); the design doesn't extend the same concern to the validator's later re-run, which re-examines a plate that may have moved again since the executor's own pass (e.g., a sibling item landing on trunk between executor commit and validator spawn). This is a genuine two-sided trap rather than a single overlooked case: pin the repo state and the validator's re-run becomes an even more perfectly deterministic replay of the executor's exact inputs (reinforcing this lens's parent-1 finding that the re-run then certifies nothing); leave it unpinned and drift-induced FAIL becomes indistinguishable from a genuine defect, silently spending strike-taxonomy budget the doctrine's own §8 (model-routing.md:110-113) reserves for capability failures only — drift is a fourth non-strike class the taxonomy doesn't name. The doc's phrasing of Q-E as one candidate under-states this: there are two distinct sub-questions (does drift corrupt the executor's run; does drift corrupt the validator's *re-verification* of an already-landed run) and the design's own escalation and freeze machinery has no answer to either.
- **Evidence:** `docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:34` — Q-E's phrasing ("a plan written against stale repo state that a fresh executor cannot notice") scopes drift to the executor only; `commands/model-routing.md:102` — "criteria frozen before execution" names only content-freeze, no state/commit pin; `commands/model-routing.md:114-119` — gauge-lint executes "against the plan's own emitted output" at authoring time, a third temporal point with its own implicit, unpinned repo snapshot; `commands/model-routing.md:110-113` — strike taxonomy explicitly excludes sandbox denials, auth expiry, and infra errors as non-strikes, with no fourth category for trunk drift between spawns.
- **Suggestion:** Reframe Q-E as two questions (executor-side drift vs. validator-side re-verification drift) and decide, on the record, whether the plan pins a commit/tree hash it was authored against — naming explicitly that pinning trades away the last shred of validator independence this design has left, rather than treating drift and replay as separable problems with separable fixes.
- **intersection_justification:** The distsys-state-coherence half supplies the mechanical fact that three separate spawns touch a shared, unpinned trunk with no version pin or lease named at any of them, and that the strike taxonomy has no category for the resulting spurious FAIL — a pure assay reviewer would see "frozen criteria" and reasonably assume freeze already covers reproducibility, missing that freeze is scoped to text only. The assay-independence half supplies the fact that the obvious coordination fix (pin the commit) is not a free lunch — it collapses the validator's re-run into a guaranteed-identical replay, which is exactly the condition under which this lens's parent-1 finding says a verdict certifies nothing — a pure distsys reviewer would recommend the pin as a clean fix without noticing it resolves one failure mode by fully realizing the other. Only tracing both together shows the design is choosing between two failure modes without saying so, rather than missing an obvious fix.

## Verdict
Both findings extend, rather than restate, the settled replay/idempotency diagnosis: one shows that the ecosystem's existing counter-assay mechanism (interspect evidence) is neither demonstrably wired to Pattern F's dispatch shape nor schema-capable of recording the independence-vs-replay distinction the pilots exist to measure; the other shows that "frozen criteria" freezes text but not repo state, so Q-E's plan-drift candidate is under-scoped to the executor and the design has no free way to fix validator-side drift without re-triggering the replay problem it's already been charged with. Both require reading the doc simultaneously as a coordination protocol and an assay register — neither reading alone reaches either finding.
