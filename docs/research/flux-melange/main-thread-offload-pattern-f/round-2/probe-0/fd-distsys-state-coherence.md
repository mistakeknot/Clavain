## Findings

### confirmed-worktree-isolation-gap-pilot-evidence
- **Severity**: P1
- **Where**: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16 (§The shape/Executor: "Receives one plan file path and the repo path"), cross-referenced against docs/clavain-vision.md:365 (interlock: "Multi-agent file coordination is generalizable | Shipped") and agents/codex-integration.md:12 (worktree-first coordination contract: "native worktrees isolate edits, interlock coordinates shared trees").
- **What**: CONFIRMED, and elevated from design-time risk to observed fact. The executor contract at line 16 names neither a worktree spawn nor an interlock `reserve_files`/`release_files` step for the repo path it hands the Sonnet-subagent lane, even though both mechanisms already exist in this exact plugin ecosystem for exactly this purpose (vision.md:365, codex-integration.md:12). The gap is not hypothetical: this goal's own five-pilot run already hit it twice. Pilot 1's executor found its checkout on branch `sweep/2026-09-02` when the plan's verify block assumed `main`, forcing a manual cherry-pick (`50f47b3` → `8672cc3`) instead of a direct land — a live demonstration of the "repo state moved under the executor" failure mode the design names no precondition-pin for. Pilot 1b's verify block hit a whole-table-state assertion made unreachable by "pruned files and a concurrent old-parser writer" — the journal's own phrase names the identical collision class (concurrent writer, unisolated shared tree) that f-005/f-018 predicted, not a paraphrase of it. Both incidents were caught by the specific verify assertion that happened to notice, not by any reservation or isolation mechanism — the design got lucky twice in five runs, at pilot scale of one goal.
- **Evidence**: docs/goals/2026-09-03-main-thread-offload-journal.md:9 ("plan asserted branch `main`; checkout was on `sweep/2026-09-02`"); :10 ("verify asserted a whole-table state that pruned files + a concurrent old-parser writer make unreachable; corrected to a parsed_at-scoped assertion"); design doc line 16 names only "the repo path", and "What makes it enforceable" (lines 21-26) still names no reservation/isolation step after these pilots ran.
- **Suggestion**: Add a required precondition-pin (base commit SHA or branch assertion, checked before apply) plus a reservation step (interlock `reserve_files` for the plan's touch-set, or a per-executor worktree) to the Executor bullet and to "What makes it enforceable" — the smallest version is one interlock call wrapping "Applies the plan."

### pilot-postmortem-misclassifies-isolation-gap
- **Severity**: P2
- **Where**: docs/goals/2026-09-03-main-thread-offload-journal.md:9-10 (Gauge defects column) versus docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:19 (Escalation: "which fixes the plan (usual case: the verify block was wrong...)").
- **What**: Both collisions above were triaged into the same bucket as ordinary plan-authoring mistakes — "gauge defects" fixed by correcting that one plan's verify assertion (pilot 1b: "corrected to a parsed_at-scoped assertion") — rather than by adding an isolation step to the executor contract itself. Because the fix lives in the individual plan and not in the contract, the next queued pilot against a different file or table set inherits the identical exposure; the postmortem records that the collision happened once, but nothing in the design or its "What makes it enforceable" section closes the class. This is the same per-plan-vs-contract-level distinction the design already draws for gauge defects generally (Escalation, line 19), applied here to a failure class that isn't actually a verify-block-authoring mistake — it's a missing precondition check — so folding it into the same bucket hides a recurring structural gap inside a count of one-off plan fixes.
- **Evidence**: journal.md rows for pilots 1 and 1b list the fix as a plan/verify-block correction, not a contract change; design doc's enforceability section (lines 21-26) is unchanged by the pilot run that surfaced both incidents.
- **Suggestion**: Track concurrent-writer/stale-checkout defects as a distinct category from plan-authoring gauge defects in the pilot log, so a second occurrence across future goals is visible as a recurring systemic gap rather than being absorbed into "verify block was wrong" each time.

### heterogeneous-isolation-across-executor-lanes
- **Severity**: P2
- **Where**: docs/brainstorms/2026-09-03-main-thread-offload-pattern-f.md:16 ("Executor (Sonnet, fresh subagent; or the codex lane for classes with parity)"); agents/codex-integration.md:12.
- **What**: The design names two executor lanes as interchangeable by class ("or the codex lane for classes with parity"), but only the codex lane inherits worktree isolation by an existing, already-documented contract (codex-integration.md:12: sandboxes/worktrees isolate edits, interlock coordinates shared trees, isolation is per nested repo). The Sonnet-subagent lane gets neither. Q-C explicitly asks which pilot classes should route to codex first — as written, that routing decision silently changes the isolation guarantee a pilot class gets, with nothing in the design surfacing the difference to whoever makes the call.
- **Evidence**: design line 16's parenthetical lane-equivalence claim; codex-integration.md:12's worktree-first contract applies only to codex sandboxes on nested repos, not to the plan-file-and-repo-path handoff the Sonnet lane uses.
- **Suggestion**: When Q-C's codex-vs-Sonnet routing is decided, record isolation guarantee as an explicit axis (alongside cost/speed) rather than treating the two lanes as parity-equivalent by default.

## Verdict
CONFIRMED, and more strongly than the original claim stated: this goal's own pilot run already produced two live instances of the predicted collision class (a stale-branch checkout and a "concurrent...writer" table-state conflict), both caught by luck rather than by any named reservation or isolation mechanism, and both closed as one-off plan fixes rather than as the contract-level gap they actually are.
