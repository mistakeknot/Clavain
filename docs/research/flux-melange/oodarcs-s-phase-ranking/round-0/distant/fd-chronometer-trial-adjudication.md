## Findings

### no-observation-discrimination-limit

- **Severity:** P0
- **Where:** charter :36 ("Rank the five main policy claimants ... against each other and no-S"), :37 ("Compare the strongest survivor from each class")
- **What:** The discrimination limit of the available evidence has never been stated, and once stated it disposes of most of the ranking. Every entry in the live field is a *contract*, not an observation: none of Fallow, Stint, Slacken, Season, Divert, Survey, Reprove, Melt, Retire, Assay, Warrant, Trace, Register, Frontier or Ash has been run once. The only measurements the run produced are code facts about the incumbent (which I re-verified independently: `session.go:78` discards the turn index; `autocompact.go:149` elides only `tool_result`; `ResetRateCounts` has one caller and it is `registry_test.go:484`). Under that limit, the honest pairwise resolution between any two candidates is **tie**. The one quantity that *can* be ordered is cost-to-instrument, which is a different quantity and must be labelled as such.
- **Evidence:** `docs/research/flux-melange/oodarcs-s-phase-tournament-v2/2026-08-24-synthesis.md` §Caveats item 2: "No comparative scoring ever ran." `heat-ledger.jsonl` carries zero findings with a measured candidate outcome. `docs/research/flux-melange/oodarcs-s-phase-ranking/heat-ledger.jsonl` is 0 bytes.
- **Failure scenario:** Requirement 4 is discharged with an ordered five-row table. Readers anchor on row order — that is what the format teaches them to do — and read "Fallow first" as "Fallow is the most valuable policy," when the only defensible content is "Fallow is the cheapest to instrument and must run first for sequencing reasons." Six months later the ordering is cited as a comparative result it never was.
- **Suggestion:** Open the requirement-4 and requirement-5 sections with one sentence before any table: *"No candidate in this field has a single observation; every ordering below is on cost-to-instrument, and every value ordering is a declared tie."* Then present tiers, not ranks, and for each declared tie name the one observation that would break it (for Stint vs Season: whether a doubled yield under a fixed rate is distinguishable from a looser licence — the identification argument in D6).

### null-threshold-measured-on-a-biased-subpopulation

- **Severity:** P0
- **Where:** charter :30 (f-063 in the priority four), :36 (rank "against ... no-S"); source finding f-063
- **What:** The charter requires the no-S null to be beaten, and the field supplies exactly one candidate threshold for it: Fallow's losing condition — "if spontaneous exploration already meets the proposed quota, the null wins and takes every S candidate with it." Re-examined as a rate sheet, the conditions this number can be observed under are much narrower than the claim. f-063 field (3) says the rate is "countable today from the existing evidence record's `tool_calls` with zero new instrumentation." Verified: `Evidence.ToolCalls []string` exists at `internal/agent/deps.go:66`. But the aggregation that turns evidence into a signal fires only at `internal/agent/agent.go:247` (`if phase == tool.PhaseCompound && a.evidenceDir != ""`), and phase advance has exactly one caller — the human `/advance` command. So the number is a rate over *sessions a human chose to drive to Compound*. The sessions that most inform an exploration base rate — the ones abandoned in a rabbit hole — contribute nothing. Second bound: the numerator has no denominator anywhere. Nothing counts sessions started. Third: the "proposed quota" the reading is compared against is a number that appears in neither charter nor ledger.
- **Evidence:** `agent.go:247` verified; `deps.go:61-86` verified (`ToolCalls` is names only); `inferTaskType` (`internal/mutations/aggregate.go:112-136`) verified to have no case for `web_search`/`web_fetch`, so a purely exploratory session buckets as `TaskDocs` or `TaskGeneral`. f-065 independently reaches the manual-`/advance` entry condition.
- **Failure scenario:** Fallow runs as the cheap first pilot, returns a low spontaneous-exploration rate, and the field is retained on the strength of it — when the low reading is an artifact of a completed-session sample that excludes exactly the exploratory sessions. Or the reverse: a high reading retires the whole field on the same bias. Either way the run that was supposed to settle the null settles nothing, and it is the one pilot the synthesis calls cheapest and recommends first.
- **Suggestion:** Before Fallow is nominated as first pilot, add two lines to its contract: (a) name the quota numerically, (b) name the denominator and how it is counted — the minimal fix is a terminal evidence record written on session exit regardless of phase, so started-but-abandoned sessions enter the sample. Certificate form: *"observed over N completed sessions in bucket B for window W; re-rate when the terminal-record fix lands; revoked if the completed/started ratio is below X."*

### f-066-admitted-only-under-serial-single-session

- **Severity:** P1
- **Where:** charter :30 (f-066 is in the priority four), :64 ("multi-agent/topology coherence"); source finding f-066
- **What:** f-066's plumbing half survives re-examination cleanly and is **admitted**: `loop.go:189-195` passes `TurnCount: turn`, `agent.go:349` forwards only `hints.Budget`, `session.go:78` is `SystemPrompt(phase tool.Phase, _ int)` — all three verified verbatim. Its *comparative* half — "every re-strike after the first is provably zero-information ... an unpriced per-turn survey tax" — depends on a condition the sheet does not state: that the stock changes only once per session at Compound. That holds only for a single session running alone. `Store.ReadRecent` (`internal/mutations/store.go:56-68`) re-opens `quality-signals.jsonl` under `~/.skaffen/mutations/` on **every** call, and that directory is per-user, not per-session. Any concurrent Skaffen session that reaches Compound mutates the stock mid-read. Under the charter's own multi-agent criterion (:64) and under any parallel-arm pilot, the per-turn re-strike is therefore not zero-information — it is a per-turn injection channel for *other arms' rows*, which is strictly worse and points the remedy somewhere else.
- **Evidence:** `store.go:56-68` verified (open-per-call, `signalFile = "quality-signals.jsonl"`, `dir` "typically `~/.skaffen/mutations/`"); `session.go:79-90` verified re-reading through `formatQualityHistory`/`Inspire` on every Orient turn.
- **Failure scenario:** The one-hunk fix f-066 recommends — "thread `TurnCount` and gate on `turn == 0`" — is adopted. Under serial single-session use it is correct and saves work. Under the pilot (arms sharing the store, possibly run in parallel) it silently *freezes* each session's view of a store that other arms are writing, converting a live contamination into a first-turn snapshot contamination — still contaminated, now undetectable, and now the arms differ by whichever arm happened to write first.
- **Suggestion:** Admit f-066 as two separate sheets. Sheet A (plumbing discarded, one-hunk fix) — admit unconditionally, ship as a bug. Sheet B (100% regret) — **bound** to "serial, single-session operation with no concurrent writer," and state that under pilot conditions the same code path is a cross-arm channel, which is f-028's contamination arriving through a route f-028 did not name. The pilot's store isolation must therefore be per-arm directories, not a shared file, and that decision must be made before the `turn == 0` gate is added.

### identical-stores-and-identical-compaction-cannot-both-hold

- **Severity:** P1
- **Where:** charter :40 ("minimal pilots for the top two actionable designs and the no-S null using identical task buckets, stores, budgets, and compaction treatment")
- **What:** One chamber, one programme — but the programme as published specifies two equalizations that the verified code makes mutually exclusive, and a third that is a known contaminant. (1) *Identical stores*: the store is `~/.skaffen/mutations/quality-signals.jsonl`, re-read on every Orient turn (above), so identical stores means arm A's rows enter arm B's Orient prompt — the contamination f-028 already records, mandated here as a control. (2) *Identical budgets and identical compaction treatment*: compaction fires at `threshold := effective - cfg.BufferTokens` (`autocompact.go:106`, `BufferTokens: 13000` at :57), so an equal-token budget does **not** give equal compaction — the arm that produces more distinct content crosses the threshold sooner and gets snipped more. Holding token budget equal and compaction schedule equal at the same time is not possible without making compaction cadence itself an explicitly-set arm variable.
- **Evidence:** `autocompact.go:55-62` and `:106` verified; `store.go:56-68` verified; `agent.go:227-229` verified (`acCfg` built once per `Run`, no mutation path).
- **Failure scenario:** Pilots are run as specified. The retained-disconfirmation measure — the thing the S arms are supposed to be good at — is anti-correlated with the treatment by construction (f-071), and the null arm reads S-arm quality rows in its own Orient prompt. Both effects push the same direction: the null wins, and the result is uninterpretable rather than merely noisy.
- **Suggestion:** Rewrite :40 as three explicit controls rather than one word "identical": per-arm store directory (isolation, not sharing); budget equalized on the *context* meter with the currency named; and compaction cadence pre-declared per arm with `snip` count and `microCompact` bytes-elided logged as a predeclared covariate. Certificate: any pilot result is revoked if the per-arm snip counts differ by more than a pre-registered margin.

### fallow-arm-has-a-constructible-trial-tuned-instrument

- **Severity:** P1
- **Where:** charter :75-76 ("failure/Goodhart mode; losing pilot outcome"), :40 (pilots)
- **What:** For the arm the synthesis nominates as the cheapest first pilot, the trial-tuned instrument is easy to build, which means the pilot as specified can be won without helping the loop. Fallow scores on spontaneous exploration turns counted from `Evidence.ToolCalls` — and `ToolCalls` is `[]string` of tool *names* (`internal/agent/deps.go:66`), with no arguments, no results, and no dedup. The implementation that maximises the score while helping least is: emit many cheap `web_search` calls with truncated or near-duplicate queries and read none of the results. The incumbent already demonstrates the shape — `cassSearch` shells out on a truncated keyword query and injects the result verbatim. The metric cannot tell twelve probes at one target from twelve targets. Symmetrically, an implementer who wants the null to win tunes the same counter the other way by counting generously, since the quota it is compared against is unnamed.
- **Evidence:** `deps.go:61-86` verified (`ToolCalls []string`, `FileActivity` only); `cassSearch` verified at `internal/mutations/inspire.go:62`; `internal/tool/builtin.go:19-22` verified registering `web_search`/`web_fetch` for Orient/Decide/Act, so the probe surface is available in three of six phases with no rate constraint (`defaultGates`, `registry.go:49-71`, gives these phases `nil` constraints).
- **Failure scenario:** The pilot reports a spontaneous exploration rate that clears the quota, requirement :48 resolves for the null, the whole field is retired — on a count that a duplicate-query loop would have produced identically.
- **Suggestion:** Pre-declare the counter as *distinct probe targets* with a dedup key (normalized query or fetched URL) recorded in the evidence record before the pilot runs — one field added at `deps.go:66`. If that field is not added, say plainly in the write-up that Fallow's reading is an upper bound on exploration and cannot discriminate breadth from repetition, and do not let the null win on it.

## Verdict

The two sheets the charter marks as load-bearing split on re-examination: f-070 and f-066's plumbing half are admitted outright on independently re-verified code, while f-066's comparative half must be bounded to serial single-session conditions and f-063's number must be bounded to the human-completed subpopulation. Nothing in the field carries a single observation, so requirement 4 can only honestly produce tiers ordered on instrumentation cost with the discrimination limit stated first. Requirement 8's "identical stores, budgets, and compaction treatment" is not one control but three mutually incompatible ones and must be rewritten before any arm runs.
