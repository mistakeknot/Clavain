## Findings

### checkout-resolution-has-no-wrong-target-check

- **Severity:** P1
- **Where:** plan §W5 step 2 (`docs/plans/plan-clavain-rd9f-f0mz.md:66`) and step 5 (`:69`)
- **What:** Step 2's checkout resolution is a fallback chain — `readlink -f` on `~/.local/bin/clavain-cli` stripped of `bin/clavain-cli`, else `~/projects/Sylveste/os/Clavain`, else `~/projects/Clavain` — gated only on "is a git repo" (exit 2 if none is). Step 3 then `git fetch`es *that* repo's own `origin main`, step 4 hashes cache files against *that* repo's own tree, and step 5 checks the CLI file against *that* repo's own blob. Nothing anywhere asks whether the resolved repo's `origin` actually points at `mistakeknot/Clavain`. A repo that is a valid git checkout, on a branch called `main`, with its own coherent `origin/main`, passes every single check — even if it is a fork, a stale rename-in-progress clone, or an unrelated project that happens to occupy one of the two hardcoded fallback paths. This is the bee-drift failure exactly: the equipment confirms *a* queen is present and mated, never that she is *this* colony's queen.
- **Evidence:** The sibling tool this design explicitly copies ("same shape and exit contract as `rig-dotfiles-deployed.py`", plan line 63) already treats this identical failure mode as first-class and named: `common/.local/bin/rig-dotfiles-deployed.py` docstring line 51 lists `WRONG-TARGET a symlink, but not into this checkout` as one of five named failure kinds, implemented at line 651 (`return "WRONG-TARGET", f"-> {os.readlink(dst_abs)} ({where})"`). But `~/.local/bin/clavain-cli` is not a dotfiles-declared `link` target — `grep -n clavain-cli install-server.sh install-macos.sh` returns nothing — so `rig-dotfiles-deployed.py`'s WRONG-TARGET check, which is the one existing piece of equipment in this exact toolchain built for exactly this problem, does not and cannot cover the CLI resolution W5 performs on its own. The W5 test harness (plan line 78) confirms the gap is structural, not incidental: its six fixture scenarios (fresh-pass, edited-hook→STALE, deleted-file→MISSING, off-branch CLI→CLI-OFF-MAIN, behind-by-one→CLI-BEHIND, permissive-probe→CLI-PERMISSIVE, missing-record→exit 2) all construct the fixture clone from the *same* bare origin the check compares against by fixture construction — none constructs a clone with a *different* origin URL, so even the harness's own design has no room for a CLI-WRONG-REPO case to be tested into existence later.
- **Suggestion:** One `git remote get-url origin` (or `git ls-remote --get-url origin`) call in step 2, compared against the known canonical URL, reported as `CLI-WRONG-REPO <url>` — same shape, same naming convention as `WRONG-TARGET`, and cheap: it rides the same `git` invocation family step 3 already pays for. Add one harness fixture (a clone with a foreign origin, otherwise identical) so the check that would catch this is itself frame-of-eggs rather than another look-for-the-queen the harness never exercises.

### cli-behind-has-a-magnitude-the-content-signature-lacks

- **Severity:** P2
- **Where:** plan §W5 step 4 (`:68`) vs step 5 (`:69`), wiring at line 74
- **What:** The plan already solved the magnitude problem once, for one of its five finding kinds, and didn't notice it needed the same fix for the other four. `CLI-BEHIND <n>` (step 5) embeds a literal commit count in the finding string, so if that string feeds the `--signature` (line 74: "sorted finding kinds and paths"), a CLI that falls one commit further behind each day changes its own signature every day and never goes STANDING. But `STALE <path>`, `MISSING <path>`, and `EXTRA <path>` (step 4) carry only a path, no magnitude — a file that is stale on day 1 and stale-and-further-diverged on day 40 produces the textually identical finding string both times. Under mk-rd1x, that means: warn on day 1 (or fail once, per the plan's deliberate fail-on-drift choice), STANDING by day 2, and permanently quiet from then on regardless of how much further the content diverges — the same "reads healthy" failure the goal describes, reproduced inside the one finding class (content drift) that is the actual reason this check exists, while the CLI check sitting one line below it in the same file is immune by construction.
- **Evidence:** Plan line 74's own justification text — "so an unchanged drift becomes warn + STANDING under mk-rd1x and a grown one fails again" — asserts growth re-fires the check. That claim is true for `CLI-BEHIND <n>` and false for `STALE`/`MISSING`/`EXTRA`, because only the former's string carries a variable magnitude. Nothing in step 4's finding format (`STALE <path>`, plan line 68) or the wiring line names a count.
- **Suggestion:** Fold an aggregate magnitude into the same `--signature` string at zero extra cost — the findings are already fully enumerated at the point the summary is built. `STALE:3 MISSING:1 EXTRA:0` (or per-path byte-diff size buckets, if per-path granularity is wanted) both use data step 4 already has in hand; either is enough for a growing divergence to produce a new signature the way `CLI-BEHIND <n>` already does, with no new git calls and no new network round trip.

## Verdict

Both findings are the same shape: a piece of equipment or a magnitude term that the plan's own toolchain already builds correctly *somewhere adjacent* — `rig-dotfiles-deployed.py`'s WRONG-TARGET for symlink identity, `CLI-BEHIND <n>` for drift magnitude — but does not carry over to the new check's checkout-resolution step or its dominant (content-hash) finding class. Neither is speculative: the first is confirmed absent by grepping the installer for `clavain-cli` and by the harness's own fixture list; the second is confirmed by the asymmetry between two finding formats in the same plan paragraph. Both are cheap, narrow fixes — one `git remote` call plus one fixture, one aggregate count already sitting in memory — not new architecture.
