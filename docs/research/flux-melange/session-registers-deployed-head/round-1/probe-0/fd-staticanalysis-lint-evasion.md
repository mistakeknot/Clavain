## Findings

### compact-resume-breaks-claim-triad
- Severity: P1
- Where: Clavain `hooks/session-start.sh:24-27` (unconditional `CLAUDE_SESSION_ID` export) and `:31-36` (comment: "session_id may change" on compact/resume, so BD_ACTOR is startup-only); interphase `hooks/bead-autoclaim.sh:43,69,78` (PostToolUse, writes `claimed_by=$SESSION_ID` and marker `/tmp/interphase-bead-$SESSION_ID`), `hooks/heartbeat.sh:11,18` (PostToolUse, no identity check), `hooks/session-end-release.sh:16,20-23` (SessionEnd, release gated on `_claimer == _our_session`).
- What: **CONFIRMED.** session-start.sh's own comment is the plan's own evidence that a single continuous user session can present two different `session_id` values to hooks: one at the original `startup` (used by `bead-autoclaim.sh` to write `claimed_by`) and a possibly different one after a `compact` or `resume` SessionStart re-fire (used by `session-end-release.sh` at actual exit). This is not a register-precedence bug — it exists independent of which of {stdin, `CLAUDE_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`} wins, because W4's fix still resolves "the session id this specific hook invocation currently sees," and that is exactly the value session-start.sh documents as unstable across compact/resume. Concretely: (1) `bead-autoclaim.sh` fires on the first `bd update --status=in_progress`, sets `SESSION_ID=A` from whatever register resolves at that PostToolUse call, writes `claimed_by=A` and marker `interphase-bead-A`. (2) A compact happens; SessionStart re-fires with `source=compact`; session-start.sh's `_hook_source != "startup"` guard skips `BD_ACTOR`, but nothing skips the `CLAUDE_SESSION_ID` export at line 24-27 — it fires whenever `_session_id` is non-empty, regardless of `_hook_source`. If the compact/resume payload's `session_id` differs from `A` (the exact condition the comment warns about), the ambient `CLAUDE_SESSION_ID` for every subsequent tool call becomes `B`, and W4's stdin-first resolution at each subsequent hook's own invocation would resolve to the current (post-compact) id too, since Claude Code hands each hook its *own* invocation's `session_id` on stdin — the same volatile value, just delivered by a different register. (3) `heartbeat.sh` keeps running (PostToolUse), discovers `CLAVAIN_BEAD_ID` from the still-exported env var (not the marker), and blindly calls `bd set-state ... claimed_at=$now` — it never compares `claimed_by` to its own resolved id, so it does not notice or correct the drift. (4) At SessionEnd, `session-end-release.sh` resolves `_our_session=B`, reads `_claimer=A` from `bd state`, and the release condition (`_claimer == _our_session`) at line 20-23 is false — the claim is left `claimed_by=A`, never released on this clean exit. W4's helper conversion (stdin > `CLAUDE_SESSION_ID` > `CLAUDE_CODE_SESSION_ID`) changes nothing about this: it fixes the "start hook never fired at all" case (mk-hxgi's original bug) but does not address "the start hook fired twice with two different ids in one logical session," which is the same defect class (wrong/mismatched session identity silently corrupting interphase claim state) surfacing through a path the plan's Why section never names.
- Evidence: `hooks/session-start.sh:24-27` (`if [[ -n "${CLAUDE_ENV_FILE:-}" ]]; then if [[ -n "$_session_id" ]]; then echo "export CLAUDE_SESSION_ID=${_session_id}" >> "$CLAUDE_ENV_FILE"; fi` — unconditional on `_hook_source`); `:34-36` comment "Only set on startup, not compact/resume (session_id may change on those)"; interphase `hooks/bead-autoclaim.sh:43,69,78`; `hooks/heartbeat.sh:11,17-25` (no `claimed_by` check anywhere in the file); `hooks/session-end-release.sh:16-23` (identity-gated release); plugin manifests confirming `bead-autoclaim.sh`/`heartbeat.sh` are `PostToolUse` and `session-end-release.sh` is `SessionEnd`, i.e. the three hooks fire at genuinely different times with a compact/resume window open between them.
- Suggestion: n/a for this finding — see the remediation field for the plan-level amendment; see `bd-actor-is-the-cheaper-fix-at-a-different-altitude` below for the concrete code fix.

### w4-tests-never-exercise-compact-boundary
- Severity: P2
- Where: plan §W4 Test (`tests/shell/session.bats`, new), lines 59.
- What: The stated test only feeds `bead-autoclaim.sh` a single stdin payload (`{"session_id":"s-real",…}`) with `CLAUDE_SESSION_ID` unset, then checks `session-end-release.sh` "fed the same session releases it and fed another session does not." That second clause tests the *wrong* scenario for this defect class: it verifies deliberate cross-session non-interference (session X can't release session Y's claim), which is working-as-intended isolation, not the compact-drift case where X and Y are the *same logical session* under two different resolved ids. A test that actually pinned this down would run `bead-autoclaim.sh` with id A, then simulate a compact (re-run session-start.sh's compact path or just change the resolved id) before running `session-end-release.sh` with id B, and assert the claim still releases. As written, W4's test suite goes green for the identity-drift bug this finding confirms, so CI reports the interphase session-identity work "done" (DONE WHEN: "interphase state is written in a session whose start hook did not fire") while the sibling case (state written by a session whose start hook fired more than once) ships unverified — the exact pattern this lens watches for: a check that closes the ticket on the fix's headline scenario while a differently-shaped instance of the same defect survives untested.
- Evidence: plan line 59: "`session-end-release.sh` fed the same session releases it and fed another session does not."
- Suggestion: Add a `session.bats` case that runs `bead-autoclaim.sh` with stdin id A, then `session-end-release.sh` with stdin id B where B is what a compact/resume would hand the SAME logical session (not an unrelated concurrent session), and assert on whether release happens — pin down the intended behavior for this case explicitly rather than leaving it implied by the cross-session test.

### bd-actor-is-the-cheaper-fix-at-a-different-altitude
- Severity: P3
- Where: `hooks/session-start.sh:29-33` (BD_ACTOR computation); plan §W4, §A1.
- What: Clavain's own session-start.sh already solves "give me an identity that is stable across compact/resume within one continuous session" — that is precisely why `BD_ACTOR` is guarded by `_hook_source == "startup"` and never overwritten on later SessionStart re-fires. It is exported into the same `CLAUDE_ENV_FILE` that `CLAUDE_SESSION_ID` uses, so it is already visible to every hook in the ambient Bash-tool environment for the life of the session, including interphase's. W4 nonetheless has interphase key `claimed_by`, the marker filename, and the heartbeat filename on the raw session-id chain (stdin → `CLAUDE_SESSION_ID` → `CLAUDE_CODE_SESSION_ID`), which is the exact value the plan's own comment says is unstable across the boundary this finding is about. Reordering which register wins cannot fix a triad that spans a compact, because every candidate register reflects "current" identity; only a value pinned once at true session start and held fixed — which `BD_ACTOR` already is — survives a compact. This is cheaper than anything at the register-precedence altitude: no new precedence rule, no new test matrix, just point interphase's existing `${CLAUDE_SESSION_ID:-unknown}` reads at `BD_ACTOR` (falling back through the same chain when unset, e.g. for `claude -p` or non-interactive runs where BD_ACTOR is never set at all).
- Evidence: `hooks/session-start.sh:29-33` (`if [[ "$_hook_source" == "startup" && -n "$_session_id" ]]; then _bd_actor="${_session_id:0:8}"; echo "export BD_ACTOR='${_bd_actor}'" >> "$CLAUDE_ENV_FILE"; fi`); plan §W4 (interphase hooks convert to the session-id chain, not to `BD_ACTOR`).
- Remediation: Have interphase's W4 rewrite key `claimed_by`/marker/heartbeat filenames on `BD_ACTOR` (with the existing session-id chain only as the fallback for runtimes where `BD_ACTOR` is never set), not on the raw per-invocation session-id chain, since `BD_ACTOR` is the one value in this codebase already designed to survive a compact/resume boundary.

### heartbeat-blind-refresh-extends-crash-fallback-to-every-clean-compacted-exit
- Severity: P2
- Where: interphase `hooks/heartbeat.sh:17-25` (refreshes `claimed_at` with no `claimed_by` comparison); `hooks/bead-autoclaim.sh:53-65` (2700s/45-min freshness window used to decide whether another session's claim blocks a new claim); `hooks/session-end-release.sh:2-3` (comment: "May not fire on crash — heartbeat TTL (45min) is the fallback").
- What: Given the drift in the confirmed finding above, `session-end-release.sh` fails its identity check and leaves `claimed_by=A`, but the *timestamp* on that stale claim is fresh (heartbeat.sh refreshed it moments before session end, unconditionally). That means a second session trying to claim the same bead right after the first session's clean exit will see, via `bead-autoclaim.sh`'s collision check, a claim that is `< 2700s` old and treat it as "actively claimed by another session," blocking the new claim for up to 45 minutes — the exact behavior the codebase reserves in comments for a *crash*. Because heartbeat.sh never compares its own resolved identity to `claimed_by` before refreshing, it cannot detect that it is heartbeating a claim it can no longer prove ownership of, so the crash-only fallback silently becomes the routine path for any session that compacted even once.
- Evidence: `hooks/heartbeat.sh:24-25` (`touch "$_hb_file" ...; bd set-state "$CLAVAIN_BEAD_ID" "claimed_at=$now"` — no read or compare of `claimed_by` anywhere in the file); `hooks/bead-autoclaim.sh:56-64` (`AGE < 2700` gate); `hooks/session-end-release.sh:2-3`.
- Suggestion: Have `heartbeat.sh` read `claimed_by` before refreshing and skip the refresh (or self-correct it) when it no longer matches the resolved identity, so a drifted claim ages out at its true last-legitimate-refresh time instead of being kept artificially warm until the moment of a failed release.

## Verdict
The prior finding is CONFIRMED, and confirmed more strongly than stated: session-start.sh's own comment is direct proof of the premise, the three interphase hooks fire at genuinely different times (PostToolUse ×2, SessionEnd ×1) spanning any compact that occurs mid-session, and the release step's identity gate has no tolerance for drift — no register-precedence choice among stdin/`CLAUDE_SESSION_ID`/`CLAUDE_CODE_SESSION_ID` closes this, because all three describe "current" identity, which is exactly what the comment says changes. W4's own test plan does not exercise this path, so CI would go green on a defect of the same class and severity as the one this whole plan exists to fix. A cheaper fix exists one altitude up: `BD_ACTOR`, already pinned at true session start and already exported for the session's lifetime, is the value interphase should key on instead of the volatile session-id chain.
