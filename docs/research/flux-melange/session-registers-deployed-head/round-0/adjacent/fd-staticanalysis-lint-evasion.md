## Findings

### python-os-environ-invisible-to-regex
- Severity: P1
- Where: `tests/structural/test_session_registers.py`, `READ = re.compile(r"\$\{?CLAUDE_SESSION_ID\b|env\.CLAUDE_SESSION_ID\b")`; `SCANNED_SUFFIXES = {".sh", ".md", ".py", ".json", ".bash"}`.
- What: The READ pattern only fires on a `$`-prefixed shell dereference or the literal substring `env.CLAUDE_SESSION_ID` (jq's idiom, and it happens to also match Node's `process.env.CLAUDE_SESSION_ID` by accident of substring search). It has no form for Python's `os.environ.get("CLAUDE_SESSION_ID", ...)` or `os.environ["CLAUDE_SESSION_ID"]` — neither contains `$CLAUDE_SESSION_ID` nor the literal `env.CLAUDE_SESSION_ID` (the substring `environ.get(` or `environ[` breaks the `env.` + immediate-`CLAUDE` adjacency the regex requires). `.py` is a scanned suffix, and `scripts/` already contains real Python (`scripts/orchestrate.py`, `scripts/gen-catalog.py`, `scripts/executor-parity-eval.py`, `scripts/gen-rig-sync.py`, `scripts/backfill-decomposition-events.py` — confirmed present in this checkout). None of those currently read the variable, but the moment one of them (or a new one) does, via `os.environ`, the line is invisible to `_bare_reads()` — not merely unflagged-by-ACCEPTED, but never matched by READ at all, so it produces no offender line and CI stays green while the exact single-register bug ships again.
- Evidence: regex definition in `test_session_registers.py`; `find hooks scripts commands skills agents -name '*.py'` lists five real Python files today.
- Suggestion: Add a third READ alternative for Python attribute/dict access, e.g. `os\.environ(\.get\(|\[)\s*['"]CLAUDE_SESSION_ID['"]`, with a matching ACCEPTED form for `os.environ.get("CLAUDE_SESSION_ID") or os.environ.get("CLAUDE_CODE_SESSION_ID")`. Pin it with a `test_classifier_examples` case the way the shell/jq forms already are, so the next regex edit can't silently drop it either.

### anti-pattern-already-live-in-dotfiles-unwalked
- Severity: P1
- Where: `dotfiles` repo (`/Users/sma/projects/dotfiles`) — `common/.claude/hooks/lib-hook-log.sh:56`, `common/.claude/hooks/session-start-signal.sh:22`, `common/.claude/hooks/check-plugin-peers.sh:21` (all: `"${HOOK_LOG_SESSION_ID:-${CLAUDE_SESSION_ID:-?}}"` — no `CLAUDE_CODE_SESSION_ID` in the chain at all), and `common/.claude/hooks/log-tool-invocation.sh:42` (`session_id: process.env.CLAUDE_SESSION_ID || "",` in JavaScript, also no fallback).
- What: This is not a hypothetical bypass — it is the plan's own target defect, present today, unfixed, in the exact sibling repo (dotfiles) that W5 is about to add new code to (`rig-clavain-deployed.py`). `lib-hook-log.sh`'s own comment even names the symptom: "CLAUDE_SESSION_ID env var — often missing in SessionStart hooks" — the maintainers know the register is unreliable but the fallback never got added here. W3 only walks Clavain's `hooks/ scripts/ commands/ skills/ agents/`; it has no reach into dotfiles at all, and W5's plan text doesn't propose extending register-safety (or even a copy of the structural test) to the repo it is landing new, health-check-relevant code into. This is precisely "a new hook that reads the wrong register" returning silently — it already has, right next to where this plan's own new work item lands.
- Evidence: file/line citations above, read directly from the dotfiles checkout at `/Users/sma/projects/dotfiles`.
- Suggestion: File a follow-up (the plan already anticipates this pattern for "Other plugins' readers" — extend that line to explicitly include dotfiles, since W5 puts new session-adjacent code there this same cycle) and fix the four call sites with the same `${CLAUDE_SESSION_ID:-${CLAUDE_CODE_SESSION_ID:-?}}` chain — cheap, and removes a live instance of the bug from the codebase this plan is actively touching.

### rig-health-write-run-kind-bare-read
- Severity: P2
- Where: `dotfiles` `common/.local/bin/rig-health-write.py:173` (`if os.environ.get("CLAUDECODE") or os.environ.get("CLAUDE_SESSION_ID"):`), with the header comment at lines 78-79 asserting "CLAUDECODE / CLAUDE_SESSION_ID: set in every Claude Code Bash environment. VERIFIED present in this session."
- What: `determine_run_kind()` uses a bare `CLAUDE_SESSION_ID` read (no `CLAUDE_CODE_SESSION_ID` fallback) to classify a run as `"session"` (non-authoritative, cannot overwrite a scheduled failure — this is the exact mechanism that fixed the sylveste-sfgi health-laundering bug). It is saved from misclassifying a start-hook-less Claude session only because the check is `or os.environ.get("CLAUDECODE")`, and CLAUDECODE is presumed unconditional. The header comment's claim that CLAUDE_SESSION_ID itself is "set in every Claude Code Bash environment" is the identical false premise mk-hxgi disproved for Clavain's own next-goal receipts — it just hasn't caused a visible failure here yet because of the `or`.
- Evidence: lines cited above, read directly.
- Suggestion: No functional fix required today (the `or CLAUDECODE` branch covers it), but the comment should be corrected so a future edit that removes or reorders that `or` doesn't reintroduce the exact bug this plan is fixing elsewhere. Two-line comment fix, not a code change.

### go-cli-chain-unwalked-and-unpatterned
- Severity: P2
- Where: `cmd/clavain-cli/sideband.go` lines 15-23 (`os.Getenv("CLAUDE_SESSION_ID")` then `os.Getenv("CLAUDE_CODE_SESSION_ID")`), `cmd/clavain-cli/sideband_test.go`.
- What: `cmd/` is not one of W3's five scanned directories (`hooks scripts commands skills agents`), and even if it were, none of the three ACCEPTED regex forms (shell `${...:-${...:-`, jq `env.X // env.Y`, or an assignment) match Go's `os.Getenv` idiom. The chain here is correct today, but a future refactor that drops the second `os.Getenv` call (e.g., someone "simplifying" `writeBeadSideband` to take a required `sessionID` parameter and inlining the fallback elsewhere) would regress the exact bug class with zero test coverage from this plan's W3 — the CLI binary this envelope comes from is also the one W5's `policy audit --zzz` probe is checking for staleness/behavior, so a silent regression here is arguably higher-stakes than most of the shell hooks W2 converts.
- Evidence: `sideband.go:15-23`; `cmd/` absence from `SCANNED_DIRS` in `test_session_registers.py`.
- Suggestion: Either extend `SCANNED_DIRS` to include `cmd` with a Go-shaped READ/ACCEPTED pair (`os\.Getenv\("CLAUDE_SESSION_ID"\)` / two-call chain), or add a narrow Go-specific unit test asserting `writeBeadSideband("", ...)` still falls through both env vars — cheaper than extending the general-purpose walker for one file.

## Verdict
The structural test's per-line, same-expression accepted-forms check is correctly implemented (no same-file-only loophole was found — the hypothetical P0 in this lens's brief does not reproduce against the actual regex), but its pattern set is scoped to shell and jq syntax while its scanned-suffix list already includes Python, and its scanned-directory list stops at the Clavain plugin boundary while the exact anti-pattern it targets is already live, unfixed, in the sibling repo (dotfiles) that this very plan's W5 work item extends. The gap is coverage, not cleverness: nobody has to game the regex when whole languages and one whole companion repo are outside its reach by construction.
