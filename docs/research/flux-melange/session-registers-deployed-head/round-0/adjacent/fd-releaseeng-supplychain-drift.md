## Findings

### standing-downgrade-defeats-fail-on-drift
- Severity: P0
- Where: dotfiles `common/.local/bin/rig-health-write.py` on branch `origin/fix/mk-rd1x-standing-vs-new` (not yet merged to `main`), lines ~287-306 (`if standing: status = "warn"` inside the "Standing vs new (mk-rd1x)" block); plan §W5 "Wiring in `rig-health-check.sh`" ("exit 1 **fail** with `--signature`... so an unchanged drift becomes warn + STANDING under mk-rd1x and a grown one fails again").
- What: Read directly from the mk-rd1x branch: when a check reports `fail` with a `--signature` whose item set is IDENTICAL to the previously-stored signature, `rig-health-write.py` unconditionally rewrites `status` from `"fail"` to `"warn"` before the record is persisted — the only trace of how long the problem has stood is a sentence fragment in the summary text ("STANDING (unchanged, N item(s), unresolved D.D d)"), not a re-escalation of severity. Concretely: the auto-publish wave (the mechanism this whole plan exists to make sure is running) dies silently. Day 1, `clavain-deployed` correctly reports `fail: STALE hooks/x.sh`. If no further commits land on `origin/main` that touch a file under the seven-or-eight compared roots for a few days (plausible over a weekend, or once the last drift-causing commit has already landed), Day 2 onward reports the SAME signature → `warn STANDING` — for as long as the wave stays dead, with no upper bound on how many days it may silently sit as `warn`. This is the review goal's own framing turned inside out: the plan worried about "a check that goes red so often it gets ignored," but the mechanism it's opting into does the opposite — it goes GREEN-ish (warn, typically deprioritized in a dashboard relative to fail) after exactly one recurrence, for the one check in the whole rig-health suite whose entire reason to exist is to catch a repair going quietly dead over weeks (per the CHANGELOG's own account of mk-hxgi: "silently dead from 2026-08-14 to 2026-09-01").
- Evidence: `rig-health-write.py` on `origin/fix/mk-rd1x-standing-vs-new` (`git show origin/fix/mk-rd1x-standing-vs-new:common/.local/bin/rig-health-write.py`), the `standing = (len(new_items) == 0 and len(signature) > 0)` / `if standing: status = "warn"` block; plan line 74.
- Suggestion: Don't route `clavain-deployed` through the generic `--signature` downgrade as-is. Either (a) omit `--signature` for this check specifically, so a standing failure keeps reading `fail` every day (accept the "noisy" cost — this is the one check where noise is the point), or (b) extend `rig-health-write.py`'s STANDING logic with a re-escalation threshold (e.g., STANDING for >N days flips back to `fail` with a "still broken after N days" summary) shared by every check that opts in, not just this one. Either is a small, testable change; shipping W5 against the mechanism as it stands today defeats the stated design intent in §W5's own last paragraph.

### fetch-staleness-has-no-multi-run-escalation
- Severity: P1
- Where: plan §W5 step 3 ("On failure keep the existing `origin/main` and carry its last-fetch age into the summary as a caveat; a verdict against a stale ref is still a verdict, and the caveat says which.").
- What: `rig-health-write.py`'s STANDING mechanism gives the `status` field a "how long has this been true" clock (`first_failed_at_epoch`) and a signature-diff. Nothing analogous exists for fetch failures: each run that fails to fetch reports "a caveat" independently, with no persisted count of consecutive fetch failures and no threshold at which the caveat becomes load-bearing (e.g., downgrading the verdict, or escalating severity). Under a multi-day network problem (Tailscale blip, GitHub outage, credential expiry — the kind of thing `feedback_zklw_autosync_token_expiry` already documents happening to this exact class of check), the comparison silently runs against a frozen `origin/main` for every one of those days: real drift that happened on the actual `origin/main` after the last successful fetch is invisible to the check by construction, while the check itself keeps reporting a verdict (pass or fail) as if its ground truth were current. This is the review goal's own P0 shape ("a check... noticing" a drift it structurally cannot see) but for the FETCH step rather than the comparison step.
- Evidence: plan lines 67 and 111 (Question 4 asks whether a failed fetch should downgrade to warn, but doesn't address the *consecutive*-failure case, only a single run).
- Suggestion: Persist `last_successful_fetch_epoch` in the check's own state (a sidecar file next to the status JSON, since `rig-health-write.py`'s authoritative-fields model doesn't have a slot for this) and have the check itself escalate its own summary/verdict once that age crosses a threshold (say, 3x the daily interval) — independent of whatever `rig-health-write.py`'s STANDING logic does to the reported status. Answers Question 4 more completely than "warn vs caveat": a single stale fetch is a caveat, three-in-a-row is a different, louder claim.

### plan-vs-goal-root-count-mismatch
- Severity: P1
- Where: plan §W5 step 4 (`git ls-tree -r origin/main -- hooks scripts bin commands agents skills config .claude-plugin`) vs. the review goal's own text ("whether the seven compared roots are enough").
- What: Counting the plan's actual path list gives EIGHT roots — `hooks, scripts, bin, commands, agents, skills, config, .claude-plugin` — not seven. `config` is present in the plan's own command but absent from both the review goal's framing and this lens's generated brief ("comparing exactly hooks, scripts, bin, commands, agents, skills, and .claude-plugin"). This matters beyond pedantry: a plan review that answers "are seven roots enough" without first re-deriving the actual list from the plan text risks approving coverage for a surface that isn't the one being shipped. Separately, at either count, `cmd/` (the Go *source* compiled into the `bin/` binaries that ARE compared) and repository-root loose files (e.g., `interlab-*.sh`, `test-interspect-overlay.sh` — confirmed present at Clavain's root, currently unreferenced by any installer and not part of the shipped plugin surface, so correctly out of scope today) sit outside every version of the list. Comparing compiled artifacts (`bin/`) rather than source (`cmd/`) is very likely the right call — `bin/` is what actually executes — but the plan never states that rationale, so there's no record distinguishing "deliberately excluded" from "not considered."
- Evidence: direct count of plan line 68's path list; lens brief text; `ls` of Clavain repo root showing `interlab-*.sh` and `test-interspect-overlay.sh` present and unwired into any installer.
- Suggestion: Fix the miscount in whichever doc is downstream of the other (plan or goal) before using "seven" as a review anchor elsewhere. Add one sentence to W5 stating explicitly that `cmd/` is out of scope because compiled artifacts, not source, are what's deployed — turning a silent gap into a documented one.

### binary-hash-cost-unbounded-and-ungrown
- Severity: P2
- Where: plan §W5 step 4 (git-blob-style local hashing of every file under the compared roots); real `bin/` contents confirmed via `ls -la` on the live checkout: `clavain-cli-go-darwin-arm64` (17.7MB), `clavain-cli-go-linux-amd64` (18.4MB), `clavain-cli-go-windows-amd64` (18.8MB), all `git ls-tree`-confirmed tracked blobs.
- What: Because `bin/` is one of the compared roots, every run of the new check must SHA-1-hash roughly 55MB of committed platform binaries (three architectures) in addition to every hook/script/command file, on top of the 60s-bounded `git fetch`. The plan states a bound only for the whole check (300s) and for the fetch (60s), not for the local hashing pass specifically. This is unlikely to be a problem today (SHA-1 over 55MB is sub-second on any real machine), but the binaries are release artifacts that only grow, this check runs daily inside a shared 2400s ceiling across ~20 checks (per `rig-health-check.sh`'s own `RUN_CEILING`), and nothing in the test plan (`test-rig-clavain-deployed.sh`) asserts a time bound on the hashing pass the way the fetch step is explicitly bounded — so a regression here (e.g., someone accidentally commits a debug build with symbols, ballooning binary size 5-10x) would be caught by content drift, not by the check's own resource discipline.
- Evidence: `ls -la bin/` and `git ls-tree -r HEAD -- bin` on the live Clavain checkout.
- Suggestion: Not blocking — a one-line assertion in the new test ("hashing completes in under Xs against a fixture of realistic binary size") would catch a future regression cheaply, consistent with how the rest of this plan already treats every bound as something to test rather than assume.

## Verdict
W5's design is otherwise well-matched to the real deployment shape (the cache is confirmed not a git repo, the CLI symlink resolves as described, the stale `gitCommitSha` claim is confirmed byte-for-byte against the live `installed_plugins.json`), but the severity policy it leans on — mk-rd1x's STANDING downgrade — silently undoes the plan's own stated fail-on-drift design choice after the very first recurrence, which is the single highest-leverage fix here: either opt this check out of the downgrade or give STANDING a re-escalation clock before this ships.
