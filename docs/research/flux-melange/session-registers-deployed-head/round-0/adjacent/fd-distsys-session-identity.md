## Findings

### compaction-changes-session-id-mid-claim
- Severity: P0
- Where: `hooks/session-start.sh` lines 24-27 (unconditional `CLAUDE_SESSION_ID` export, gated only on `$_session_id` being non-empty, NOT on `_hook_source`) vs. line 34's own guard (`if [[ "$_hook_source" == "startup" ...`) with the comment "Only set on startup, not compact/resume (session_id may change on those)"; interphase `hooks/bead-autoclaim.sh`, `heartbeat.sh`, `session-end-release.sh` (all in the sibling worktree at `/Users/sma/projects/Sylveste/interverse/interphase/.claude/worktrees/session-registers/hooks/`).
- What: session-start.sh's own BD_ACTOR guard proves that Claude Code can hand a *different* `session_id` to the SessionStart hook on a `compact` or `resume` event than it handed at `startup`. Nothing in W1-W4 accounts for this: `clavain_session_id`/`_interphase_session_id` correctly resolve "the current call's session id" every time they're invoked, but interphase's claim lifecycle spans multiple hook invocations that are NOT guaranteed to see the same id. `bead-autoclaim.sh` writes `bd set-state $ISSUE_ID claimed_by=$SESSION_ID` (id at claim time, S1) and a marker `/tmp/interphase-bead-S1`. If a compaction happens later in the same logical work session (S1→S2), `session-end-release.sh` resolves `_our_session=S2` from ITS OWN stdin at exit time and compares it against `_claimer` (still S1, read back from `bd state`). The release condition `"$_claimer" == "$_our_session"` fails (S1 != S2), and none of the other release branches (empty/no-state/"released") match either — so the claim is never released cleanly. The file's own header says this is exactly the gap the heartbeat TTL exists to paper over ("May not fire on crash — heartbeat TTL (45min) is the fallback"), but a clean compaction is not a crash, and 45 minutes of a bead reading falsely-claimed is a real regression for anyone else trying to pick it up. This is the "wrong register" class of bug the plan exists to prevent, reintroduced by the precedence rule's implicit assumption that "the session's id" is a constant across the claim's lifetime.
- Evidence: `session-start.sh:24-27` (unconditional write) vs `session-start.sh:34` and its comment (`session_id may change on those [compact/resume]`); `bead-autoclaim.sh` ("Write claiming state" block, marker `/tmp/interphase-bead-${SESSION_ID}`); `session-end-release.sh` (`if [[ -z "$_claimer" ... || "$_claimer" == "$_our_session" ]]`).
- Suggestion: give the claim triad a stable anchor that survives compaction — either (a) key the claim/marker on the *first* session id seen for this claim (persist it in the marker filename or in bd state itself, e.g. `claimed_by_root_session`, and have heartbeat/release resolve against that stored value rather than re-deriving "current" each call), or (b) have session-start.sh's compact/resume path explicitly carry forward `CLAVAIN_BEAD_ID` and the OLD session id into the new CLAUDE_ENV_FILE so release can still match. Either is a few lines, not a redesign — but ship a bats case that compacts mid-claim (writes state under id A, calls session-end-release.sh with stdin id B) before calling W4 done, since none of the new `session.bats` cases currently exercise a change of identity between claim and release.

### precedence-fix-doesnt-cover-stdin-churn
- Severity: P1
- Where: plan `docs/plans/plan-clavain-rd9f-f0mz.md` §Assumptions A1 and §Questions for review #1.
- What: A1 and Question 1 both frame the resume/compaction risk purely as "which of the two ENV registers is fresher" ("Is there a resume or compaction path where CLAUDE_SESSION_ID from the env file is the old id and CLAUDE_CODE_SESSION_ID is the new one"). But `session-start.sh`'s own comment says the thing that changes on compact/resume is `_session_id` itself — the value read straight off **stdin**, the register the whole design treats as unconditionally authoritative ("always the right answer for the hook that received it"). A precedence reorder among the two env vars cannot fix an identity that churns at the top of the chain; the design needs to either treat "the session" as the thing that gets a stable anchor once (see the previous finding) or explicitly declare compaction/resume as a case where per-hook-call `clavain_session_id()` resolution is known to be locally-correct-but-not-lifecycle-stable, and design consumers accordingly.
- Evidence: `hooks/session-start.sh:31-36` comment; plan lines 24 (A1) and 108 (Question 1).
- Suggestion: Rewrite Question 1 to ask the sharper version — "does ANY hook-call-to-hook-call span inside this plan (claim→release, sentinel-check→sentinel-clear, throttle-write→throttle-read) assume the resolved id is constant across calls, and if so does compaction/resume break that assumption regardless of which register wins?" — and answer it before W4 ships, since the answer is already "yes, at least for interphase's claim triad" (previous finding).

### interband-sideband-writer-not-in-inventory
- Severity: P1
- Where: `cmd/clavain-cli/sideband.go` (`writeBeadSideband`, commit `9696538 feat(sideband): retire legacy /tmp/clavain-bead path; env session keying (Sylveste-zlc, Sylveste-23k)`) vs. plan §Register facts table, §A2, §Question 5.
- What: The Go CLI already writes a session-keyed statusline-facing envelope — `namespace: "interphase"`, `type: "bead_phase"`, keyed by `sessionID` resolved via the identical `CLAUDE_SESSION_ID` → `CLAUDE_CODE_SESSION_ID` chain the plan introduces — to `~/.interband/interphase/bead/<sessionID>.json`, and its commit message says explicitly this is done "so the statusline keeps working as interphase retires (brainstorm KD 11)," replacing a "legacy /tmp/clavain-bead path." The plan's Assumption A2 reads "interphase statusline state" as the bead-claim state (`claimed_by`/`claimed_at`/`/tmp/interphase-bead-<session>`) that `bead-autoclaim.sh` writes, and Question 5 explicitly asks "is there a sideband writer this plan did not find?" — there is one, and it is not a hypothetical: it is shipped, tested (`sideband_test.go`), and its own commit message frames interphase's mechanism as the thing being phased out. If interline's statusline is migrating (or has migrated) to read the interband envelope rather than interphase's claim state, then W4's fix — entirely correct on its own terms — is hardening a register bug in a subsystem whose statusline-facing role may already be superseded, which is exactly the "fix that would be cheaper at a different altitude" the review goal asks to surface: fixing (or re-verifying) `writeBeadSideband`'s callers and the interband envelope's session-keying once may cover more of "statusline state" than instrumenting every interphase hook.
- Evidence: `cmd/clavain-cli/sideband.go:11-59`; `git log --oneline -- cmd/clavain-cli/sideband.go` → `9696538`; envelope shape (`namespace: "interphase"`, path `~/.interband/interphase/bead/<sessionID>.json`); plan lines 25 (A2) and 112 (Question 5).
- Suggestion: Before treating A2 as settled, trace who currently reads `~/.interband/interphase/bead/*.json` for interline's statusline (grep interline's source for `.interband` or `INTERBAND_ROOT`) and confirm whether it or the `/tmp/interphase-bead-<session>` + `claimed_by` state (or both) is the live statusline input today. If interband already is, extend W4's DONE WHEN proof to also assert the interband envelope carries the stdin-resolved session id under a start-hook-less session — likely already true since sideband.go's chain matches, but currently unverified and untested by this plan.

### discovery-cache-key-skips-stdin-by-construction
- Severity: P3
- Where: `hooks/lib.sh`, `_discover_all_companions` (cache-key line: `_expected_key="# session=$(clavain_session_id "" "$$")"`), noted in plan §W1 ("the library's own companion-cache key... moves to the helper with `$$` as the fallback").
- What: This call always passes an empty stdin argument, so the resolution is env-chain-then-`$$` only — correct for this call site, since `_discover_all_companions` has no hook payload in hand, but it means the "stdin wins" property the helper advertises is silently opted out of here by construction (an empty string, not an absent argument). Not a bug today, but the pattern ("pass `''` to skip stdin") is easy to copy into a future call site that DOES have stdin available, silently dropping the highest-priority register there too, and W3's structural test would not catch it (the call site never spells `CLAUDE_SESSION_ID` literally).
- Evidence: `hooks/lib.sh` `_discover_all_companions()`, the `_expected_key=` line; plan line 41.
- Suggestion: A one-line comment at the call site ("no stdin here — this runs outside any hook's payload") would keep the next port of this idiom honest; not worth a test.

## Verdict
The plan's precedence fix (stdin > CLAUDE_SESSION_ID > CLAUDE_CODE_SESSION_ID) is sound for a single hook call, but the codebase's own comments show the session identity Claude Code hands out is not stable across compact/resume within one logical work session — and interphase's claim/heartbeat/release triad depends on exactly that stability across multiple calls, which the plan's assumptions and open questions don't surface. A second, already-shipped sideband mechanism (clavain-cli's interband envelope) independently resolves the same chain and may already be the real statusline input A2 is reasoning about; that gap is worth closing before W4 is called done.
