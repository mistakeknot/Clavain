## Findings

### resume-compaction-split-untested

- **Severity:** P1
- **Where:** plan §A1 (precedence: stdin, then `CLAUDE_SESSION_ID`, then `CLAUDE_CODE_SESSION_ID`) and §Questions item 1; `hooks/session-start.sh:31-33`; `hooks/lib-sprint.sh` non-stdin sites (`:420`, `:646`, `:1283`, `:1732`, `:1799`, `:1901`); `scripts/dispatch.sh`, `scripts/lib-routing.sh`; every command/skill running inline in the Bash tool.
- **What:** `hooks/session-start.sh` fires on `startup`, `resume`, `clear`, and `compact` (line 11: `_hook_source=$(echo "$HOOK_INPUT" | jq -r '.source // "startup"')`), and its own comment at lines 31-33 says explicitly: *"Only set [BD_ACTOR] on startup, not compact/resume (session_id may change on those)."* That is direct, in-repo acknowledgment that the value keyed at session start is not stable across the session's lifetime. The `CLAUDE_SESSION_ID` export itself (line 27-28) is *not* gated the same way — it re-fires and appends a fresh `export CLAUDE_SESSION_ID=<new-id>` into `CLAUDE_ENV_FILE` on every trigger, including resume/compact. That closes the gap for anything reading fresh stdin (every hook) or a freshly-re-sourced `CLAUDE_ENV_FILE`. It does not establish — and nothing in W1-W4 tests — what a no-stdin, env-chain-only caller sees in the window around that re-fire, nor whether `CLAUDE_CODE_SESSION_ID` (set by the runtime itself, not by this hook) tracks the same transition at the same moment. A1 answers "which register wins when both are set" but not "what happens when they're set to *different, both-valid* values because one was refreshed and the other wasn't yet, or wasn't at all."
- **Evidence:** W1's test list (plan line 43) is: *"stdin wins over both env registers; `CLAUDE_SESSION_ID` wins over `CLAUDE_CODE_SESSION_ID`; `CLAUDE_CODE_SESSION_ID` alone resolves; nothing set gives the fallback; malformed stdin falls through to env; the helper is silent on stderr."* Every case either sets one register or sets both to presumably-identical stand-ins — none pins `CLAUDE_SESSION_ID=old` and `CLAUDE_CODE_SESSION_ID=new` simultaneously and asserts what a *non-stdin* caller (the six `lib-sprint.sh` sites, `dispatch.sh`, `lib-routing.sh`, every inline command chain) resolves to. The plan's own Question 1 asks this exact thing and is left open for review rather than answered in the design.
- **Suggestion:** Answer Question 1 now, not as a review artifact: add one `session_registers.bats` case that sets both registers to different values and asserts the env-chain-only path's output (this is cheap — it documents current behavior, `CLAUDE_SESSION_ID` first, per A1). Separately, since the session-start.sh comment already proves session_id churn is a known, real event, add a lightweight divergence log (one line, not a hard failure, consistent with "hooks stay fail-open") when the helper or the inline chain sees both registers set and non-equal — that turns an invisible split into a visible one at the cost mk-hxgi already paid for once. Reversal cost: near zero, it's an additive log line behind an existing conditional.

### standing-downgrade-blind-to-drift-magnitude

- **Severity:** P1
- **Where:** plan §W5 wiring ("exit 1 **fail** with `--signature` = the sorted finding kinds and paths so an unchanged drift becomes warn + STANDING under mk-rd1x and a grown one fails again"); dotfiles `common/.local/bin/rig-health-write.py` (commit `6284fd9`, branch `origin/fix/mk-rd1x-standing-vs-new`, not yet merged to local `main`), function `parse_signature` and the standing-computation block in `build_record`.
- **What:** I read the actual mk-rd1x implementation the plan stacks on. `parse_signature(text)` returns `sorted({i for i in items if i})` — a set of opaque item strings (e.g., `STALE hooks/lib.sh`). The standing computation is: `new_items = sorted(set(signature) - set(prev)); standing = (len(new_items) == 0 and len(signature) > 0)`. Nothing in this comparison is sensitive to *how far* an existing item has drifted — only to whether the *set of names* changed. Apply this to `clavain-deployed`: day 1, `hooks/lib.sh` is one commit behind `origin/main`, signature = `{"STALE hooks/lib.sh"}`, first-ever fail, `standing=False`. Day 2, the auto-publish wave still hasn't run and the file is now five commits behind — the finding kind and path are unchanged, so the signature string is byte-identical, `new_items` is empty, `standing=True`, status downgrades to `warn`. Every day after, for as long as nobody edits a *different* file, the signature never changes and the check stays a STANDING warn — exactly the shape mk-f0mz names in the Why section ("how the Mac ran a five-week-old permissive CLI"). The mechanism built to stop one alarm-fatigue failure (dotfiles-deployed, autosync-repair going red for 17 days over the same two refused repos) reproduces the identical blind spot in the one check whose entire purpose is to catch a slow-growing gap.
- **Evidence:** `rig-health-write.py` docstring for `parse_signature` (added in 6284fd9) states the intended semantics directly: *"A check that is always red carries no more information than one that is silent... The signature is what lets the writer tell an UNCHANGED failure (standing: warn) from one that GREW (new_items: fail)."* "Grew" here is defined and implemented as *new distinct items appearing*, never as an existing item's distance increasing — confirmed by re-reading the diff: no field carries commit-count, byte-diff, or timestamp into the signature or its comparison.
- **Suggestion:** Answer Question 2 directly: fail-on-drift is the right call for the *first* occurrence, but the mk-rd1x downgrade as written is not safe enough for this check specifically, because (unlike a refused-repo list, which is naturally bounded and rarely worsens invisibly) `STALE <path>` is a proxy for an unbounded, silently-growing distance. Cheapest fix: fold the commits-behind count (already computed in W5 step 5's `CLI-BEHIND <n>` check, and derivable for content staleness via `git rev-list --count <cache-blob-commit>..origin/main` if the recorded `gitCommitSha` is trusted, or more simply a coarse bucket like `STALE hooks/lib.sh (1-5)` / `(6-20)` / `(20+)`) into the signature string itself, so magnitude *is* identity for this check's purposes and growth past a bucket boundary re-triggers fail. Reversal cost: one string-formatting change in `rig-clavain-deployed.py`'s signature emission; no change to the shared `rig-health-write.py` primitive, so other STANDING consumers (autosync-repair, publish-drift) are unaffected.

### a2-proxy-misses-real-statusline-consumers

- **Severity:** P1
- **Where:** plan §A2 ("interphase statusline state... is the bead-claim state (`claimed_by`, `claimed_at`, the `/tmp/interphase-bead-<session>` marker) that `bead-autoclaim.sh` writes and that heartbeat, session-end-release and interline's lane resolver key on"); §W4's DONE WHEN proof (bats asserting `claimed_by=s-real` and the marker file); `~/projects/Sylveste/interverse/interline/scripts/statusline.sh:299-380`; `~/projects/Sylveste/interverse/interline/scripts/lib-lane.sh:36-58`; `cmd/clavain-cli/sideband.go`, `cmd/clavain-cli/phase.go:226-227`.
- **What:** I traced A2's claim to its consumers instead of accepting it. `statusline.sh`'s "Active beads" layer (its actual bead-display code) does two things, neither of which is reading `claimed_by`: (1) it runs `bd list --status=in_progress --json` globally — no session or claim filtering at all — and (2) it merges phase/age from `"$_il_interband_root/interphase/bead/${session_id}.json"` (line 308), a sideband file written *exclusively* by `cmd/clavain-cli/sideband.go`'s `writeBeadSideband()`, called once from `phase.go:227` with the comment *"so the statusline keeps working as interphase retires (brainstorm KD 11)."* Separately, `lib-lane.sh`'s `_il_lane_resolve()` — the function A2 explicitly names as "interline's lane resolver" — reads a *third*, different path: `"${INTERBAND_ROOT:-$HOME/.interband}/interphase/lane/${sid}.json"` (line 48). I searched Clavain, interphase, and interline for any writer of `interphase/lane/*.json` and found none — that sideband may be entirely unwritten today, which is itself a gap A2 doesn't surface. None of the three real inputs I found is the `claimed_by`/marker-file mechanism W4's test proves. That proof is correct on its own terms (`bead-autoclaim.sh` does write a session-keyed claim), but it does not exercise what actually renders on screen.
- **Evidence:** `writeBeadSideband` (verified via `cmd/clavain-cli/sideband.go:17-23`) already resolves its own session id through the correct two-register chain independent of this plan's changes, so there is no live statusline-bead-display bug today from the register defect specifically — but the *lane* sideband having no confirmed writer, and the bead sideband being a wholly separate code path from the one W4 converts and tests, means the DONE WHEN could be marked satisfied by a green `tests/shell/session.bats` while the two files interline's own code reads (`interphase/bead/<id>.json`, `interphase/lane/<id>.json`) are untouched by W4 and unasserted by any test in this plan.
- **Suggestion:** Answer Question 5 directly: yes, there are sideband writers this plan did not find — `cmd/clavain-cli/phase.go`'s call into `sideband.go`, and whatever (if anything) is meant to write `interphase/lane/*.json`. Before closing W4, add one bats or Go test that runs `clavain-cli sprint-advance` (or the internal function it calls) with `CLAUDE_SESSION_ID` unset and a stdin-equivalent id, and asserts the interband bead JSON lands at the right path with the right id — this is a small addition since the underlying function is already register-correct, it just isn't proven by anything in this plan. The lane-sideband gap is cheaper to flag than fix: a one-line note in the plan's Out of Scope naming it as an open question, so it isn't silently assumed solved.

### fail-open-unknown-terminal-unobservable

- **Severity:** P2
- **Where:** plan §Constraints ("Hooks stay fail-open. The helper never exits non-zero and never prints to stderr.") and §W1 (fallback default `unknown`, cache-key fallback `$$`).
- **What:** By design and for good reason (hooks must not break a session), `clavain_session_id` produces no signal — no exit code, no stderr line, nothing logged — when it falls all the way through stdin, both env registers, to the literal string `unknown`. That means a correctly-resolved session id and a fully-collapsed one are structurally identical outputs, distinguishable only by a human noticing the literal text "unknown" in a downstream artifact (a claim file, a receipt) well after the fact — which is exactly how mk-hxgi's original defect went unnoticed. The plan converts every currently-known reader, but per the collation-lens findings in this same round, it does not convert `cmd/clavain-cli`'s 7 bare Go sites — meaning the silent-collapse path this constraint deliberately keeps quiet is, right now, still live and reachable via `clavain-cli bead-heartbeat`/`bead-release` calls from `commands/work.md` and `hooks/lib-recovery.sh`.
- **Evidence:** No test in W1-W4 asserts on *absence* of signal (there's no way to, by the fail-open contract as written) — the constraint is self-consistent but means the class of defect this whole plan targets has, by design, no telemetry hook for its own recurrence. The Why section's diagnosis method for the *first* occurrence was manual discovery (mk-hxgi), not any check firing.
- **Suggestion:** Keep the hook contract fail-open and silent (constraint is correct for hooks) but consider a narrow escape valve outside the hot path: a periodic (not per-invocation) rig check — sibling to `clavain-deployed` — that greps recent claim/evidence records for the literal sentinel values (`unknown`, a bare `$$`-derived pid string) and reports a *rate*, not a hard failure, so a return of the register defect shows up as a trend line rather than requiring another five-week outage to notice. This is a genuinely different, cheaper-altitude fix than converting every possible future caller: instead of exhaustively enumerating readers (the collation lens's concern), watch the *output* for the sentinel shape the defect always produces.

## Verdict

A1's precedence choice is reasonable but untested at the one boundary (differing, simultaneously-valid registers on a no-stdin path) that the codebase's own comments say occurs; the mk-rd1x standing-downgrade, verified against its actual implementation, silences the specific failure mode this plan exists to catch after its first occurrence; and A2's proxy, traced to interline's real code, is not what renders the statusline — two of three real consumers are untouched by W4, and one may have no writer at all. All three are answerable now, cheaply, without re-architecting: a differential test, a magnitude-aware signature, and one more assertion plus an honest open-question note.
